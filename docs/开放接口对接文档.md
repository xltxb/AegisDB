# 开放接口对接文档 —— 外部系统提交 SQL 升级单

面向要把变更单推给网关的外部系统:DevOps 平台、CI 流水线、变更管理系统。

接口契约见 `backend/docs/openapi.yaml`(运行时 `GET /openapi.yaml`)。本文讲的是那份
契约说不清的部分:怎么拿凭据、重试怎么算、单子卡住了怎么办、失败各代表什么。

---

## 一、先拿一把凭据

由网关管理员在【系统设置 · 开放接口】签发,交给你两样东西:

```
key    = ak_e1026cc86fe60da7        (公开半段,可以写进日志和配置)
secret = 9tK2…                      (私密半段)
token  = ak_e1026cc86fe60da7.9tK2…  (两段用点连接,直接放进 Authorization)
```

**明文密钥只在签发那一刻回显一次**,库里只存 bcrypt 哈希。丢了只能重新签发一把、
替换掉旧的,没有"找回"。

签发时管理员要选一个**服务账号**,你的每一次调用都以它的身份执行:

- 它的角色决定你能发布到**哪些实例**(标签范围)、**什么变更要走审批**(能力矩阵);
- 审计链记 `actor = 服务账号`、`operator = API:<凭据名>` —— 谁的身份、哪个系统要求的,两个都留痕;
- 它被停用,你的凭据立刻失效。这是有意的:停用一个账号就能切断所有借用它的集成。

跟管理员确认服务账号的权限范围,**不要请求绑定管理员账号** —— 那等于把改任何实例的
权力发给你的系统。

### 权限范围(scope)

签发时按需勾选,少即是好:

| scope | 能做什么 |
|---|---|
| `release:create` | 提交升级单、终止自己提交的单 |
| `release:read` | 查询单据状态、列可用实例与流程 |
| `review:check` | 只做规范审查预检,不建单 |

一个只读看板不该拿到能在生产建变更的凭据。

## 二、调用方式

```
POST https://<gateway>/api/v1/open/releases
Authorization: Bearer ak_e1026cc86fe60da7.9tK2…
Content-Type: application/json
```

也支持 `X-Vela-Key` + `X-Vela-Secret` 两个请求头(给那些把 Authorization 占了的客户端)。

**所有响应都是 HTTP 200**,业务结果在包体的 `code` 里:

```json
{ "code": 0, "msg": "ok", "data": { } }
```

判断成功请看 `code === 0`,不要看 HTTP 状态码。

## 三、提交一张升级单

实例和流程都可以用**名字**寻址 —— 你知道的是 `order-cluster`,不是网关内部的行号:

```bash
curl -X POST https://<gateway>/api/v1/open/releases \
  -H "Authorization: Bearer $VELA_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "title": "订单表增加备注字段",
        "externalRef": "CHG-2026-0001",
        "instance": "order-cluster",
        "database": "orders",
        "pipeline": "标准发布流程",
        "sql": "ALTER TABLE tbl_order ADD COLUMN memo VARCHAR(64) NOT NULL DEFAULT \"\" COMMENT \"备注\";",
        "reason": "需求 #123"
      }'
```

`pipeline` 留空则用目标分层的默认流程。可用的实例名与流程名分别用
`GET /open/instances`、`GET /open/pipelines` 查 —— 前者已经按你的服务账号过滤过。

### 传脚本文件

三种写法,任选:

```bash
# 1) multipart 直传(CI 里最顺手)
curl -X POST https://<gateway>/api/v1/open/releases \
  -H "Authorization: Bearer $VELA_TOKEN" \
  -F "title=季度归档" -F "externalRef=BUILD-8842" \
  -F "instance=order-cluster" -F "pipeline=标准发布流程" \
  -F "file=@migrations/V12__archive.sql"

# 2) JSON 里内联脚本全文
{"script": "-- upgrade\nALTER TABLE …;", "filename": "V12__archive.sql", …}

# 3) JSON 里传 base64(避免你那边模板引擎的转义 bug 改坏 SQL)
{"scriptBase64": "LS0gdXBncmFkZQpBTFRFUiBUQUJMRSDigKY7", "filename": "V12__archive.sql", …}
```

脚本会**落盘并记录 SHA-256**;执行阶段重新读文件、校验哈希后才下发 —— 审查过的字节
和执行的字节是同一份。上限 15MB。

### 幂等:一定要带 `externalRef`

填你自己的单号(变更号、构建号都行)。**同一凭据 + 同一 `externalRef` 重试,返回的是
第一次创建的那张单**,不会重复下发变更。

这层保证由数据库唯一索引兜底,不是"先查再插",所以两个并发的重试也只会产生一张单。
超时、网络抖动、流水线重跑,直接原样重发即可。

## 四、查状态

```bash
curl -H "Authorization: Bearer $VELA_TOKEN" \
     https://<gateway>/api/v1/open/releases/REL-42
```

```json
{ "code": 0, "data": {
  "relNo": "REL-42", "status": "waiting", "risk": "mid",
  "instance": "order-cluster", "env": "prod", "pipeline": "标准发布流程",
  "externalRef": "CHG-2026-0001",
  "stages": [
    { "order": 1, "name": "规范审查", "type": "review",  "status": "success",
      "log": "· 命中 0 错误 / 2 警告 / 1 提示…" },
    { "order": 2, "name": "人工审批", "type": "approve", "status": "waiting",
      "approvalNo": "AP-2296" },
    { "order": 3, "name": "执行变更", "type": "execute", "status": "pending" }
  ]
} }
```

单据状态 `status`:

| 值 | 含义 | 你该做什么 |
|---|---|---|
| `pending` | 已受理,排队中 | 继续轮询 |
| `running` | 某个阶段正在跑 | 继续轮询 |
| `waiting` | **卡在人身上**(等审批 / 等人工确认) | 继续轮询,但别催 —— 可以把 `approvalNo` 展示给你的用户 |
| `success` | 全部阶段通过 | 收工 |
| `failed` | 某阶段失败 | 看 `error` 与失败那个阶段的 `log` |
| `aborted` | 被终止 | —— |

**轮询建议 10~30 秒一次。** 审批通过后网关最多 15 秒把流水线推下去,更密的轮询不会更快。

失败时不要只看 `error`:失败阶段的 `log` 里才有真正的原因,比如规范审查会把命中的
规则名和语句序号原样列出来。

## 五、合并前先审(不建单)

CI 的门禁场景 —— 只要结论,不要单据:

```bash
curl -X POST https://<gateway>/api/v1/open/sql-review \
  -H "Authorization: Bearer $VELA_TOKEN" \
  -F "instance=order-cluster" -F "file=@migrations/V12__archive.sql"
```

```json
{ "code": 0, "data": { "result": {
  "dialect": "mysql", "statements": 3,
  "errors": 1, "warnings": 2, "infos": 0,
  "passed": false,
  "findings": [
    { "level": "error", "name": "建表必须有主键", "stmt": 2, "line": 14,
      "message": "表 tbl_archive 未定义主键", "sql": "CREATE TABLE tbl_archive (…" }
  ]
} } }
```

`passed` 的含义是**没有 error 级命中**,不是"零命中" —— 警告从不拦截。拿 `passed`
当门禁的判据即可,警告数留给人看。

方言由目标实例决定:同一段 SQL 在 Oracle 实例上和在 TiDB 实例上,命中的规则不一样。

## 六、错误怎么读

| code | 含义 | 处理 |
|---|---|---|
| `0` | 成功 | —— |
| `40100` | 凭据无效 | key/secret 拼错、凭据被吊销。**不要重试** |
| `40300` | 无权 | 三种可能,`msg` 会说清:scope 不够 / 服务账号无权动这个实例 / 查的不是自己提交的单 |
| `40301` | 来源 IP 不在该凭据的白名单 | 找管理员加白 |
| `42800` | 目标分层要求二次验证 | 服务账号绑了 TOTP 才会出现;通常应让管理员给服务账号免除 MFA |
| `40001` | 参数问题 | `msg` 指名道姓:实例不存在、流程不存在、内容为空、**所选流程不含审批阶段** |
| `42600` | 网关未配置脚本保存路径 | 找管理员配置后重试 |
| `50000` | 服务端错误 | 可退避重试 |

几个容易踩的 `40001`:

- **"该变更命中「…」需审批,请选择包含审批阶段的发布流程"** —— 你选的流程没有审批阶段,
  而这条变更按规则必须有人批。换一条含审批阶段的流程重提。这个检查在**提交时**做,
  所以不会给你留下一张注定失败的单。
- **"实例名 x 不唯一,请改用 connectionId"** —— 拒绝猜,因为猜错就是变更打到了另一个库。

## 七、几条别误解的约定

- **开放接口不是执行旁路。** 你提交的变更走的是和控制台完全相同的一条流水线:同样的
  流程模板、同样的规则库、同样的审批链、同样的审计链。执行阶段**下发前会再判一次**
  三层闸门 —— 单子在审批里停了两小时,期间规则、实例归属、账号角色都可能变,以下发那
  一刻的判定为准。
- **审批通过 ≠ 已执行。** 审批只是放行,执行由流水线的执行阶段完成。所以你看到
  `approve` 阶段变成 `success` 之后,还要等 `execute` 阶段。
- **终止只对没开跑的单有效**(`pending` / `waiting`)。`running` 的单子拒绝终止 ——
  它的执行阶段可能已经打到目标库上了,一个假的"已终止"比没有这个按钮更危险。
- **网关重启后**:`running` 的单会被判为失败并写明"执行结果未知,请人工确认"(不会
  重跑);`waiting` 的原样保留;`pending` 的重新入队。

## 八、最小可用接入清单

1. 管理员签发凭据,确认服务账号的实例范围与 scope;把 token 放进你那边的密钥管理。
2. `GET /open/instances` + `GET /open/pipelines` 拉一次,把实例名和流程名做成你系统里的下拉。
3. 合并前调 `POST /open/sql-review` 做门禁(可选但强烈建议)。
4. 发布时调 `POST /open/releases`,**带上你自己的单号作 `externalRef`**。
5. 按 10~30 秒轮询 `GET /open/releases/{relNo}`,直到 `success` / `failed` / `aborted`。
6. 失败时把失败阶段的 `log` 展示给你的用户 —— 那里面才有原因。
