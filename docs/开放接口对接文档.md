# 开放接口对接文档 —— 外部系统提交 SQL 升级单

面向要把变更单推给网关的外部系统：DevOps 平台、CI 流水线、变更管理系统。

接口契约见 `backend/docs/openapi.yaml`（运行时 `GET /openapi.yaml`，本地开发另有
Swagger UI `GET /docs`）。本文讲的是那份契约说不清的部分：怎么拿凭据、重试怎么算、
单子卡住了怎么办、失败各代表什么。

---

## 零、五分钟跑通

拿到 token 之后，照这四条走一遍，你就知道整条链是通的：

```bash
export AEGISDB=https://<gateway>/api/v1/open
export TOKEN=ak_xxx.yyy

# 1. 我能访问哪些实例(已按你的服务账号的实例范围过滤)
curl -s -H "Authorization: Bearer $TOKEN" $AEGISDB/instances

# 2. 合并前门禁:只要结论,不建单
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
     -F "instance=order-cluster" -F "file=@V12.sql" $AEGISDB/sql-review

# 3. 提单(externalRef 填你自己的单号)
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d @body.json $AEGISDB/releases

# 4. 轮询到终态
curl -s -H "Authorization: Bearer $TOKEN" $AEGISDB/releases/REL-42
```

六条接口，就这些：

| 方法 | 路径 | 需要的 scope | 干什么 |
|---|---|---|---|
| `POST` | `/open/releases` | `release:create` | 提交升级单 |
| `GET` | `/open/releases/{relNo}` | `release:read` | 查状态与各阶段日志 |
| `POST` | `/open/releases/{relNo}/abort` | `release:create` | 终止自己提交的单 |
| `POST` | `/open/sql-review` | `review:check` | 只审不建单（CI 门禁） |
| `GET` | `/open/instances` | `release:read` | 可访问的实例清单（不代表都能发布，见第三节） |
| `GET` | `/open/pipelines` | `release:read` | 流程清单（仅供了解，见第三节） |

## 一、先拿一把凭据

由网关管理员在【系统设置 · 开放接口】签发，交给你两样东西：

```
key    = ak_e1026cc86fe60da7        (公开半段,可以写进日志和配置)
secret = 9tK2…                      (私密半段)
token  = ak_e1026cc86fe60da7.9tK2…  (两段用点连接,直接放进 Authorization)
```

**明文密钥只在签发那一刻回显一次**，库里只存 bcrypt 哈希。丢了只能重新签发一把、
替换掉旧的，没有"找回"。

签发时管理员要选一个**服务账号**（设置 → 开放接口里一键创建，`kind=service` 的专用
机器主体）—— 凭据**只能**绑服务账号，网关不接受把新凭据绑到人类账号上。你的每一次调用
都以它的身份执行：

- 它的角色决定你能发布到**哪些实例**（标签范围）、**什么变更要走审批**（能力矩阵）；
- 审计链记 `actor = 服务账号`、`operator = API:<凭据名>` —— 谁的身份、哪个系统要求的，两个都留痕；
- 它被停用，你的凭据立刻失效。这是有意的：停用一个账号就能切断所有借用它的集成；
- 它**不能登录控制台**（没有口令，也设不上），唯一的门就是你手里这把凭据；
- 平台的"强制 MFA"策略不约束它 —— 机器注册不了 TOTP，它的第二因子就是凭据本身
  （bcrypt secret + 每凭据 IP 白名单），所以对接**不需要**处理 42800。

跟管理员确认服务账号的权限范围。服务账号**不能带平台管理员角色**：建服务账号时选了 admin
会被拒；一个账号只要还被启用中的凭据绑定着，网关也不允许再给它加 admin —— 那等于把改任何
实例、改权限矩阵的权力发给你的系统。

> 早期版本允许把凭据绑在人类账号名下。那批**存量**凭据不追溯、照常工作，但请尽快让管理员
> 改绑到服务账号；新签发和改绑都只接受服务账号。

### 权限范围（scope）

签发时按需勾选，少即是好：

| scope | 能做什么 |
|---|---|
| `release:create` | 提交升级单、终止自己提交的单 |
| `release:read` | 查询单据状态、列可用实例与流程 |
| `review:check` | 只做规范审查预检，不建单 |
| `grant:read` | 查询授权：列可授权的实例与库名、查询已有授权（见第九节） |
| `grant:write` | 查询授权：下发、更新、撤销授权（见第九节） |
| `release:approve` | 外部审批：替审批链上的人通过 / 驳回发布单、替确认人放行人工确认（见第四节「外部审批」「外部确认」；执行变更不开放） |

一个只读看板不该拿到能在生产建变更的凭据。

管理员勾选时填了网关不认识的范围（拼错、本版本没有的），签发/修改会直接报错（`40001`），
不会静默丢掉。

`grant:read` / `grant:write` / `release:approve` **不在默认勾选里**：签发凭据时没勾任何范围，
得到的是前三个。它们只该发给外部审批系统那一把凭据 —— 尤其 `release:approve`，别勾给提单的
CI 凭据：提单和审批是职责分离的两半。

### 还可以按凭据配的两样

- **IP 白名单**：只允许你那套 CI 的出口地址调用。每一项必须是合法的 IP 或 CIDR
  （逗号、空格或换行分隔，如 `10.20.0.0/16, 192.168.1.8`），有一项写错整条拒绝保存。它是**每凭据**的，与控制台的登录
  IP 白名单是两回事 —— 后者回答"哪些办公室能开控制台"，把 CI 的出口网段并进去等于
  为了一台机器放宽整个控制台的边界。
- **绑定流程**：管理员把一条发布流程钉在你的凭据上（见第三节）。

## 二、调用方式

```
POST https://<gateway>/api/v1/open/releases
Authorization: Bearer ak_e1026cc86fe60da7.9tK2…
Content-Type: application/json
```

也支持 `X-AegisDB-Key` + `X-AegisDB-Secret` 两个请求头（给那些把 `Authorization` 占了的客户端）。

**所有响应都是 HTTP 200**，业务结果在包体的 `code` 里：

```json
{ "code": 0, "msg": "ok", "data": { } }
```

判断成功请看 `code === 0`，不要看 HTTP 状态码。

> **Windows 联调提醒**：在 Windows 终端（含 Git Bash / PowerShell）用 curl 联调时，
> 不要把中文写在命令行参数里（`-d '{"title":"中文标题"}'`）—— 命令行参数会先过系统
> ANSI 代码页转换，中文在发出前就变成了字面 `?`，网关会忠实存下这些问号，升级单
> 标题和审批待办里就会出现乱码。把 JSON 放进 UTF-8 文件再 `-d @body.json`，或直接
> 用你们系统的 HTTP 客户端库（不经命令行，无此问题）。

> **认证失败有频控，成功调用不限速。**
>
> 同一个来源 IP 在 5 分钟内**认证失败** 10 次，会被锁 5 分钟，期间一律返回 `42900`。
> 计数只看失败：凭据对得上就立刻清零，所以正常集成永远碰不到它 —— 一把凭据用到底，
> 偶尔配错一次也不会累积。
>
> 它挡的是两件事：拿字典猜 secret，以及**把 CPU 打满** —— 每次认证都要跑一次 bcrypt，
> 那是故意慢的，而这一步在任何鉴权之前，谁都能打。
>
> 成功的调用本身不限速，但仍请不要把它当压测目标，也不要用密集轮询代替退避（见第四节）。
>
> **拿到 `42900` 怎么办**：等一会儿再试（至少 5 分钟），并**先去检查凭据是不是配错了** ——
> 绝大多数情况下，连续的认证失败意味着配置问题，而不是网关的问题。

## 三、提交一张升级单

实例和流程都可以用**名字**寻址 —— 你知道的是 `order-cluster`，不是网关内部的行号：

```bash
curl -X POST https://<gateway>/api/v1/open/releases \
  -H "Authorization: Bearer $AEGISDB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "title": "订单表增加备注字段",
        "externalRef": "CHG-2026-0001",
        "instance": "order-cluster",
        "database": "orders",
        "changeType": "ddl",
        "sql": "ALTER TABLE tbl_order ADD COLUMN memo VARCHAR(64) NOT NULL DEFAULT \"\" COMMENT \"备注\", ALGORITHM=INPLACE, LOCK=NONE;",
        "reason": "需求 #123"
      }'
```

可用的实例名用 `GET /open/instances` 查 —— 已经按你的服务账号的**实例范围**过滤过。
注意它回答的是"能访问哪些实例"，不是"能往哪些实例发布"：一个只读角色的服务账号也会
看到实例，但对它提交变更会按网关的能力矩阵被拒（`40300`）或要求走审批。能不能发，以
提交那一刻（以及执行前复判）的判定为准。发布流程不在请求里指定（见下）。

### 传脚本文件

三种写法，任选：

```bash
# 1) multipart 直传(CI 里最顺手)
curl -X POST https://<gateway>/api/v1/open/releases \
  -H "Authorization: Bearer $AEGISDB_TOKEN" \
  -F "title=季度归档" -F "externalRef=BUILD-8842" \
  -F "instance=order-cluster" \
  -F "file=@migrations/V12__archive.sql"

# 2) JSON 里内联脚本全文
{"script": "-- upgrade\nALTER TABLE …;", "filename": "V12__archive.sql", …}

# 3) JSON 里传 base64(避免你那边模板引擎的转义 bug 改坏 SQL)
{"scriptBase64": "LS0gdXBncmFkZQpBTFRFUiBUQUJMRSDigKY7", "filename": "V12__archive.sql", …}
```

脚本会**落盘并记录 SHA-256**；执行阶段重新读文件、校验哈希后才下发 —— 审查过的字节
和执行的字节是同一份。**上限 15MB**：multipart 的 `file`、JSON 的 `script`、解码后的
`scriptBase64` 在同一个尺寸上拒绝，返回同一句 `40001`「脚本超过 15MB 上限」，不会建单。

### 幂等：一定要带 `externalRef`

填你自己的单号（变更号、构建号都行）。**同一凭据 + 同一 `externalRef` 重试，返回的是
第一次创建的那张单**，不会重复下发变更。

这层保证由数据库唯一索引兜底，不是"先查再插"，所以两个并发的重试也只会产生一张单。
超时、网络抖动、流水线重跑，直接原样重发即可。

### 变更类型：`changeType`

一张升级单只能是一种变更：`dml`（数据订正）或 `ddl`（结构变更）。建议**总是显式
声明** —— 声明与语句不符会当场拒绝（错误会点名第几条、什么动词），两类语句混在一张
单里也会拒绝（拆成两张）。不带 `changeType` 时网关按语句推断并回带在响应里。分类
口径：SELECT 计入 DML；GRANT/REVOKE 计入 DDL；BEGIN/COMMIT/SET 等事务与会话控制语句
是中性的，不参与判定。

### 发布流程：你**不用也不能**指定

一张单走哪条流水线（审查/审批/备份/执行/校验怎么组合）是网关侧策略：管理员把
流程绑定在你的凭据上，或者不绑 —— 那就走目标分层的默认流程（默认含人工审批）。
请求里**不要**带 `pipeline` / `pipelineId`：带了会整单拒绝，错误信息会指路。
`GET /open/pipelines` 仍可用于了解各流程长什么样，但仅供了解。想换流程，找网关
管理员改凭据配置，不改你的代码。

### 执行要网关侧点击确认

审批回答"可不可以做"，执行确认回答"现在做"。你的单走到**执行阶段会停下**
（轮询看到 `execute` 阶段 `waiting`），由网关侧操作员在控制台点击「确认执行」后
才真正落库 —— 这是正常流转，不是卡单。你的系统应把它呈现为"待执行确认"而非
超时失败；何时点击由变更窗口决定，与你无关。

## 四、查状态

```bash
curl -H "Authorization: Bearer $AEGISDB_TOKEN" \
     https://<gateway>/api/v1/open/releases/REL-42
```

```json
{ "code": 0, "data": {
  "relNo": "REL-42", "status": "waiting", "risk": "mid",
  "instance": "order-cluster", "env": "prod",
  "externalRef": "CHG-2026-0001",
  "stages": [
    { "order": 1, "name": "规范审查", "type": "review",  "status": "success",
      "log": "· 命中 0 错误 / 2 警告 / 1 提示…" },
    { "order": 2, "name": "人工审批", "type": "approve", "status": "waiting",
      "approvalNo": "AP-2296",
      "approvers": [
        { "name": "陈浩", "account": "chenhao@aegisdb.io", "status": "active" },
        { "name": "王磊", "account": "wanglei@aegisdb.io", "status": "waiting" }
      ] },
    { "order": 3, "name": "执行变更", "type": "execute", "status": "pending" }
  ]
} }
```

单据状态 `status`：

| 值 | 含义 | 你该做什么 |
|---|---|---|
| `pending` | 已受理，排队中 | 继续轮询 |
| `running` | 某个阶段正在跑 | 继续轮询 |
| `waiting` | **卡在人身上**（等审批 / 等人工确认） | 继续轮询，但别催 —— 可以把 `approvalNo` 展示给你的用户 |
| `success` | 全部阶段通过 | 收工 |
| `failed` | 某阶段失败 | 看 `error` 与失败那个阶段的 `log` |
| `aborted` | 被终止 | —— |

阶段 `type` 一共七种，你会在 `stages` 里见到它们的任意组合（由网关侧的流程配置决定）：

| type | 中文名 | 它在等什么 |
|---|---|---|
| `review` | 规范审查 | 不等人，跑完就有结论 |
| `approve` | 人工审批 | 等审批链上的人；`approvalNo` 可展示给你的用户 |
| `backup` | 备份/回滚点 | 不等人 |
| `execute` | 执行变更 | 停在这里 = 等网关侧点「确认执行」 |
| `verify` | 执行后校验 | 不等人 |
| `manual` | 人工确认 | 等一个人放行；停着时 `approvers` 列出能放行的人（见「外部确认」） |
| `notify` | 结果通知 | 不等人 |

**轮询建议 10~30 秒一次。** 审批通过后网关最多 15 秒把流水线推下去，更密的轮询不会更快。

失败时不要只看 `error`：失败阶段的 `log` 里才有真正的原因，比如规范审查会把命中的
规则名和语句序号原样列出来。

**只能查同一个服务账号名下凭据提交的单。** 轮换凭据（签新凭据、删旧凭据）后，新凭据可以
继续查旧凭据提交的在途单；不同服务账号之间互相看不到：查别的服务账号的凭据提交的单、或在
控制台建的单，返回 `40300`；单号根本不存在返回 `40001`。终止仍只能终止**本凭据**提交的单。

### 终止

```bash
curl -X POST -H "Authorization: Bearer $AEGISDB_TOKEN" \
     https://<gateway>/api/v1/open/releases/REL-42/abort
```

只对**没开跑**的单有效（`pending` / `waiting`），且只能终止**你自己这把凭据提交的**单。
`running` 的单拒绝终止 —— 它的执行阶段可能已经打到目标库上了，一个假的"已终止"比没有
这个按钮更危险。

### 外部审批

给外部审批系统（OA、工单平台）用：审批人在你那边点了「同意 / 驳回」，你替他把结论交给网关。
需要凭据勾选 `release:approve`。

```bash
curl -X POST -H "Authorization: Bearer $AEGISDB_TOKEN" -H "Content-Type: application/json" \
     https://<gateway>/api/v1/open/releases/REL-42/approval \
     -d '{"approver":"chenhao@aegisdb.io","action":"approve","comment":"已核对变更窗口"}'
```

```json
{ "code": 0, "data": {
  "relNo": "REL-42", "approvalNo": "AP-2296",
  "status": "approved", "alreadyDecided": false, "releaseStatus": "waiting"
} }
```

| 字段 | 说明 |
|---|---|
| `approver` | 审批人的**网关账号邮箱**（不分大小写）。从状态查询里审批阶段的 `approvers[].account` 取 |
| `action` | `approve` 或 `reject`。故意不用布尔值：漏传的 `false` 会把一次"同意"变成驳回 |
| `comment` | 审批意见，记入审计，最多 200 字 |

几条规则：

- **凭据不是审批人。** 网关会核对 `approver`：必须在这张单的审批链上、不是发起人、不是服务账号、
  没有停用 —— 和控制台审批按钮同一条规则。审批链是**任一人通过即生效**，`approvers` 里任意一人都行。
  不满足返回 `40300`，`msg` 说明是哪一条（不在链上要找管理员加角色，是发起人要换人批）。
- **能批哪些单：** 服务账号实例范围内的发布单都能批，**不要求是本凭据提交的**（外部审批系统通常
  不是提单的那个系统）。范围外的返回 `40300`。
- **决定的是当前在等的那个审批阶段。** 还没走到审批阶段、或流程里根本没有审批阶段，返回 `40001`。
- **先到先得。** 控制台照样能批。单子已经被决定过（控制台先批了、或你重试了），返回 `0`、
  `alreadyDecided: true`，`status` 是已有的结论，本次请求不改变任何东西。所以**重试是安全的**。
- 通过后流水线继续往下走（最多 15 秒）；驳回后发布单停止，不会执行。
- 每次调用（含被拒的）都进审计：actor = 服务账号，operator = `API:<凭据名>`，并记下审批人账号与意见。

> 注意：状态查询（含 `approvers`）只能查**本服务账号**提交的单。审批的单如果是控制台或别的系统提的，
> 开放接口看不到它的审批人名单 —— 这时 `approver` 直接填你那边审批人的网关账号即可，网关会核对他在不在链上。

### 外部确认（人工确认）

流程里的「人工确认」阶段会把发布单停在 `waiting`，等一个人放行。外部平台的「待人工确认」卡片上，
确认人点了按钮，你替他把放行交给网关。同样需要凭据勾选 `release:approve`。

**卡片发给谁：** 发布单停在人工确认时，状态查询里该阶段带 `approvers`，字段与审批阶段相同，
`confirmer` 填其中任一人的 `account`。任一人放行即生效。

```json
{ "order": 2, "name": "人工确认", "type": "manual", "status": "waiting",
  "approvers": [
    { "name": "陈浩", "account": "chenhao@aegisdb.io", "status": "active" }
  ] }
```

- 阶段配了确认角色：名单是该角色里的在职真人成员；没配：名单是所有有审批能力的在职真人。
- 两种都不含发起人（未开自审批时）、服务账号、停用账号 —— 名单上的人调本接口一定过得了授权核对。
- 名单是**此刻**的：只在阶段停着（`waiting`）时给，放行之后不再给；角色成员变了，下次查询就变。
- 「执行变更」阶段不给名单 —— 它只能在网关上确认，不归外部卡片。

```bash
curl -X POST -H "Authorization: Bearer $AEGISDB_TOKEN" -H "Content-Type: application/json"      https://<gateway>/api/v1/open/releases/REL-56/confirm      -d '{"confirmer":"chenhao@aegisdb.io","comment":"已核对"}'
```

```json
{ "code": 0, "data": {
  "relNo": "REL-56", "stage": "人工确认",
  "alreadyConfirmed": false, "releaseStatus": "running", "executePending": false
} }
```

| 字段 | 说明 |
|---|---|
| `confirmer` | 确认人的**网关账号邮箱**（不分大小写） |
| `comment` | 备注，记入审计，最多 200 字 |

几条规则：

- **只管人工确认，不管执行变更。** 「执行变更」的确认执行是打到目标库上的那一下，**只能在网关上由人操作**，
  本接口永远不放行它。发布单停在执行变更上时返回 `40001`；人工确认放行后流水线若停到执行变更，
  响应里 `executePending: true` —— 卡片上可以据此提示"请到 DB Gateway 确认执行"。
- **凭据不是确认人。** 网关按控制台「继续」按钮同一条规则核对 `confirmer`：发起人本人不能放行自己的单
  （除非管理员开了自审批）；阶段配了确认角色的须在该角色里，没配的须有审批能力。不满足返回 `40300`，
  `msg` 说明原因。服务账号、停用账号、不存在的账号返回 `40001`。
- **当前没有停在人工确认上**（还在审批、已经结束、流程里没有这一步），返回 `40001`。
- **先到先得，重试安全。** 控制台照样能点。已经放行过的，返回 `0`、`alreadyConfirmed: true`，本次请求不改变任何东西。
- **只有放行，没有驳回。** 不想放行的单用「终止」（`/abort`，只能终止本凭据提交的单），或在控制台终止。
- 能碰哪些单、审计口径与外部审批相同：服务账号实例范围内的都行；每次调用（含被拒的）写 `open.release.confirm`。

## 五、合并前先审（不建单）

CI 的门禁场景 —— 只要结论，不要单据：

```bash
curl -X POST https://<gateway>/api/v1/open/sql-review \
  -H "Authorization: Bearer $AEGISDB_TOKEN" \
  -F "instance=order-cluster" -F "file=@migrations/V12__archive.sql"
```

```json
{ "code": 0, "data": { "result": {
  "dialect": "mysql", "statements": 3,
  "errors": 1, "warnings": 2, "infos": 0,
  "passed": false,
  "findings": [
    { "level": "error", "name": "建表必须有主键", "stmt": 2, "line": 14,
      "message": "表 tbl_archive 未定义主键", "sql": "CREATE TABLE tbl_archive (…" }
  ]
} } }
```

`passed` 的含义是**没有 error 级命中**，不是"零命中" —— 警告从不拦截。拿 `passed`
当门禁的判据即可，警告数留给人看。

方言由目标实例决定：同一段 SQL 在 Oracle 实例上和在 TiDB 实例上，命中的规则不一样。
不带实例时可以用 `dialect` 指定，只认 `mysql` / `tidb` / `dws` / `oracle`（大小写不敏感），
其他值返回 `40001` —— 不会再拿一个认不出的方言只跑通用规则、然后回你一个误导人的
`passed: true`。带了实例时以实例为准。脚本同样受 15MB 上限约束。
每条规则在网关侧都标着**出处**（公司规范的第几条，或"平台内置"），被拦下来的人能回去
读原文；规则的级别与开关是网关侧可调的，所以同一段 SQL 在不同部署上的结论可以不同。

## 六、错误怎么读

| code | 含义 | 处理 |
|---|---|---|
| `0` | 成功 | —— |
| `40001` | 参数问题 | `msg` 指名道姓：实例不存在、流程不存在、内容为空、**所选流程不含审批阶段**、单号不存在、`dialect` 非法、脚本超过 15MB |
| `40100` | 凭据无效 | key/secret 拼错、凭据已被**吊销（删除）**。**不要重试** |
| `40300` | 无权 | `msg` 会说清：凭据**已停用** / 绑定的服务账号已停用 / scope 不够 / 服务账号无权动这个实例 / 查或终止的不是**本凭据**提交的单 |
| `40301` | 来源 IP 不在该凭据的白名单 | 找管理员加白 |
| `42600` | 网关未配置脚本保存路径 | 找管理员配置后重试 |
| `42800` | 目标分层要求二次验证 | 仅当凭据错误地绑定了**人类账号**且其已注册 TOTP 时出现；绑定专用服务账号（推荐做法）不会遇到 |
| `42900` | 认证失败次数过多，暂时锁定 | 同一来源 IP 5 分钟内认证失败 10 次触发，锁 5 分钟。**先查凭据配置**，再等待重试 |
| `50000` | 服务端错误 | 可退避重试 |

几个容易踩的 `40001`：

- **"该变更命中「…」需审批，请选择包含审批阶段的发布流程"** —— 你选的流程没有审批阶段，
  而这条变更按规则必须有人批。换一条含审批阶段的流程重提。这个检查在**提交时**做，
  所以不会给你留下一张注定失败的单。
- **"实例名 x 不唯一，请改用 connectionId"** —— 拒绝猜，因为猜错就是变更打到了另一个库。

**哪些该重试**：`50000` 和网络层错误退避重试（带着同一个 `externalRef`，幂等兜底）。
`42900` 也该退避重试，但**退避之前先确认凭据没配错** —— 它是被自己的失败次数锁住的，
不改配置就重试，只会在解锁后再锁一次。
`40100` / `40300` / `40301` / `40001` 都是**确定性拒绝**，重试只会得到同一个答案。

## 七、几条别误解的约定

- **开放接口不是执行旁路。** 你提交的变更走的是和控制台完全相同的一条流水线：同样的
  流程模板、同样的规则库、同样的审批链、同样的审计链。执行阶段**下发前会再判一次**
  三层闸门 —— 单子在审批里停了两小时，期间规则、实例归属、账号角色都可能变，以下发那
  一刻的判定为准。
- **审批通过 ≠ 已执行。** 审批只是放行，执行由流水线的执行阶段完成。所以你看到
  `approve` 阶段变成 `success` 之后，还要等 `execute` 阶段。
- **网关重启后**：`running` 的单会被判为失败并写明"执行结果未知，请人工确认"（不会
  重跑）；`waiting` 的原样保留；`pending` 的重新入队。
- **你的调用进审计链**：提交升级单（及其各阶段）、终止、规范预检、查询授权的下发/撤销、
  巡检报告上传都会留痕，`actor` 是服务账号、`operator` 是 `API:<凭据名>`；终止与预检被拒
  也会记一笔。审计不记 secret，预检只记结论不记 SQL 原文。管理员签发、修改、吊销凭据同样
  进审计。审计行带着来源 IP —— 也就是你那套系统的出口地址，这对事后追查很有用，同时也意味
  着换出口网段要顺带更新凭据的 IP 白名单。

## 八、最小可用接入清单

1. 管理员签发凭据，确认服务账号的实例范围与 scope；把 token 放进你那边的密钥管理。
2. `GET /open/instances` 拉一次，把实例名做成你系统里的下拉（流程由网关侧配置，无需展示）。
   列出的是可访问的实例，能否发布由网关在提交时判定。
3. 合并前调 `POST /open/sql-review` 做门禁（可选但强烈建议）。
4. 发布时调 `POST /open/releases`，**带上你自己的单号作 `externalRef`**。
5. 按 10~30 秒轮询 `GET /open/releases/{relNo}`，直到 `success` / `failed` / `aborted`。
6. 失败时把失败阶段的 `log` 展示给你的用户 —— 那里面才有原因。
7. 把 `waiting` 呈现为"等待网关侧处理"，别让它在你的界面上看起来像超时。

## 九、查询授权（业务方数据查询）

业务方（运营、财务、客服等）要查生产数据时，在**审批魔方**里提申请、走审批；
审批通过后，由你的系统调网关接口**下发授权**。网关不审批，只执行授权并做边界校验。

授权的粒度是：**某人，在某段时间内，可以只读查询某个实例上的某个库**。

### 9.1 凭据

请管理员签发一把勾了 `grant:read` + `grant:write` 的凭据，绑定一个**专用的服务账号**。
服务账号的实例范围（标签）决定你能授权哪些实例：请管理员给业务查询用的从库打上同一个标签，
并把这个标签授予该服务账号。不要为了省事给它挂 DBA 负责人这类不限实例的角色 —— 那类角色
还带着审批等别的权力，与"下发查询授权"无关。

### 9.2 调用顺序

```
# 1. 可授权的实例(只有管理员标记为「业务查询源」的从库,主库不会出现)
GET  /api/v1/open/query-sources
→ [ { "id": 12, "name": "orders-replica", "engine": "MySQL 8.0", "env": "prod", "status": "online" } ]

# 2. 这台实例上的库名(给审批单的"库"下拉用)
GET  /api/v1/open/query-sources/12/databases
→ [ "finance_db", "orders_db" ]

# 3. 审批通过后,下发授权
PUT  /api/v1/open/query-grants
{
  "externalId": "OA-20260925-001",          // 你的审批单号,必填
  "email": "zhang.san@bssrvc66.com",         // 被授权人,必填
  "name": "张三", "dept": "财务部",          // 可选,网关里还没有这个人时用来建号
  "sourceId": 12,                            // 第 1 步的 id,必填
  "database": "orders_db",                   // 第 2 步列出的名字之一,必填,区分大小写
  "maxRows": 0,                              // 每次查询最多返回多少行;0 = 网关默认(1000)
  "timeoutSec": 0,                           // 单条查询最长执行秒数;0 = 网关默认(30)
  "allowExport": false,                      // 是否允许导出
  "startsAt": "2026-09-25T09:00:00+08:00",   // 可选,不填 = 现在
  "endsAt":   "2026-10-25T09:00:00+08:00",   // 必填
  "approver": "李经理",
  "reason": "月度对账"
}
→ { "created": true, "grant": { "id": 31, "status": "active", ... } }

# 4. 撤销(离职、转岗、提前结束)
DELETE /api/v1/open/query-grants/31                  // 按网关的授权 id
DELETE /api/v1/open/query-grants?externalId=OA-…     // 或按你的审批单号

# 5. 查询
GET  /api/v1/open/query-grants?email=zhang.san@bssrvc66.com&status=active
```

### 9.3 规则

- **一个人对一个库只有一条授权，按审批单号（`externalId`）区分每次 `PUT`：**

  | 这次的 `externalId` | 网关怎么做 | 响应 |
  |---|---|---|
  | 与这条授权**当前**的单号相同（重试） | 什么都不改，原样返回；已撤销的**不会**因此恢复 | `code 0`，`created: false` |
  | 一张**新**单（续期、改条件） | 更新这一条：上限、有效期、导出开关、单号都换成新的；已撤销或已过期的重新生效 | `code 0`，`created: false` |
  | 以前作用过这条授权、**已被新单取代**的旧单 | 拒绝，不改动 | `40001`，`msg` 说明被哪张单取代 |

  所以网络重试是安全的（同一张单发几次都一样），一次延迟到达的旧请求也不会把新批的条件改回去。
  **续期、恢复被撤销的授权，都要用一张新的审批单。**
- **网关只接受边界内的请求**，越界直接拒绝（`40001`，原因在 `msg`）：
  - 实例必须是业务查询源；库名必须真实存在于这台实例；
  - `maxRows` 不超过 10000，`timeoutSec` 不超过 300；
  - `endsAt` 必填，晚于现在和 `startsAt`，有效期不超过 90 天；
  - 被授权人不能是服务账号或网关里已停用的账号。

  上面的数值是网关的默认上限，管理员可以调整。
- **被授权人在网关里没有账号时，网关会自动建号**，只挂「业务查询」角色。这个角色本身不开放
  任何实例和操作，查询权只来自授权。已有账号会追加这个角色，原来的权限不变。
  自动建的账号没有口令：业务方要等网关接入 SRD 授权登录后才能登录使用，在此之前下发的授权会先落库、生效期照常计算。
- **到期自动失效**，不需要你来撤销。
- **你只看得到、撤得掉你这把凭据下发的授权。** `GET /open/query-grants` 只列你下发的；按 id
  或按审批单号撤销别的系统下发的授权，回"授权不存在"。审批单号是各系统自己的编号。
- 每一次下发、更新、撤销、到期都写进网关的审计链，记下是哪个外部系统、哪张审批单、谁批的。

### 9.4 状态

列表里的 `status` 是**生效状态**：

| status | 含义 |
|---|---|
| `active` | 生效中 |
| `pending` | 已下发，还没到 `startsAt` |
| `expired` | 已过 `endsAt` |
| `revoked` | 已撤销 |

### 9.5 接入清单

1. 请管理员签发带 `grant:read` + `grant:write` 的凭据，并把业务查询用的从库实例标记为「业务查询源」。
2. 审批单上"实例""库"两个字段，用 9.2 的第 1、2 步拉取，不要让人手填。
3. 审批通过后调 `PUT /open/query-grants`，**带上审批单号作 `externalId`**；`code != 0` 时把 `msg` 展示给审批发起人。
4. 离职、转岗时调 `DELETE` 撤销；续期用**新的审批单号**再 `PUT` 一次新的 `endsAt`（同一个单号重发不会改任何东西）。
