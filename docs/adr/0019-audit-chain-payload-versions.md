# ADR 0019:审计链哈希的 payload 版本,以及 v5 为什么是另一类改动

- 状态:已采纳
- 日期:2026-09-15
- 相关:`backend/internal/service/audit_chain.go`(`currentAuditPayloadVersion`、
  `auditPayloadFor`、`matchAuditRow`、`VerifyAuditChain`)、
  `backend/internal/service/audit_payload_history_test.go`、
  `backend/internal/bootstrap/audit_verify_test.go`、`backend/pkg/crypto`

## 背景

每条审计记录带着上一条的哈希,`prev_hash` 上有唯一索引防分叉。这条链存在的全部理由是
"事后有人动过库,查得出来"。

它被写了两个月才第一次被**读**。在此之前没有 verify 端点、没有定时校验,谁也没验过一次
—— 而一条没人验的链和没有链的区别,只在出事那天才显出来:那天你才发现它从三个月前就断了。

要"照着写的时候那样再算一遍",就得知道当时算的是什么。而这个 payload 的形状变过五次。
`docs/adr/` 下此前没有一篇写这件事(代码注释一度指向 ADR 0006,那篇其实是开放接口提单),
于是这个机制唯一的记录就是 git 历史。本 ADR 补上。

## 决定

### 1. 每次改 payload,历史行一律不重算

往哈希里加一个字段,最省事的做法是把全表重算一遍。**不做。** 重算等于把证据重新签一遍,
那就不是证据了 —— 签名的意义全在于"签的时候是什么样,现在还是什么样"。

代价是:一个从 2026-07 跑到今天的部署,链上并存着好几个年代的行。所以读侧必须认全每一版,
逐版去试。

| 版本 | 日期 | 变化 |
|---|---|---|
| v1 | 2026-07-17 | `time actor instance command risk result ap` |
| v2 | 2026-07-21 | + `database`(命令落在哪个库) |
| v3 | 2026-07-30 | + `operator`(外部审批人,EA4) |
| v4 | 2026-08-07 | + `env` + `tier`(双快照) |
| v5 | 2026-09-15 | `time` 改为 UTC 归一(迁 PostgreSQL 时的时区无关化) |

逐版尝试**不放宽任何东西**:每一版都得拿出一个真实的 SHA-256 前像,而那只有当时那个
写入器才拿得出来。但它确实改变了结论的含义,所以报告按版本分别计数(`ByVersion`):
**一行按 v1 校验通过,只说明 v1 里那七个字段没被动过** —— 它的 `database` / `operator` /
`env` / `tier` 当时不在哈希里,事后被填进去或改掉,这个校验看不出来。看的人据此知道自己
手里的保证到哪一层为止。

### 2. v5 是**算法变更**,不是字段增补 —— 这个区别要守住

v1→v4 每一次都是加字段,所以读侧写成 `if version >= n`,老行走老分支照样算得出来。

v5 改的是同一批字段里**时间的写法**。而算法改动没有"只对新行生效"的写法:归一化
(`a.OccurredAt.UTC().Format(time.RFC3339)`)对每一版都生效,它不在任何 `if` 里。
版本号在这里剩下的唯一用处,是让读侧的逐版尝试先试新写法。

于是 v5 和 v4 对**同一行**算出的字节完全一样。`TestAuditPayloadVersions_EachIsDistinctAndGrows`
里因此有一条无条件的「v4 与 v5 必须完全相同」断言,而它看起来很像写错了 —— 一个认为
"非 UTC 的行上 v4/v5 输出可区分"的人,会顺手给它加个条件。加了,就把「加了字段却点名成
算法版」这道防线拆了。把这件事写进 ADR,是为了让下一个人在改那条断言之前先读到这里。

**守着这条区分的机制住在哪里**:`audit_payload_history_test.go` 里的 `algorithmOnlyVersions`
注册表 —— 一个版本落在表里,就等于声明它与前一版对同一行算出的字节相同,那条无条件断言
正是照着这张表走的。改本 ADR 说的任何一件事之前,先去改那张表。

它有一条**进表的硬条件**:这个版本改的那点算法差异,必须在 `audit_chain_test.go` 里有一条
用例钉住。v5 的那一条是 `TestAuditPayload_IsTimezoneIndependent`(同一时刻、两种 Location,
必须算出同一个哈希)。硬条件之所以必要:这张表挡得住"偷偷加字段"(加了就与前一版不同,
断言当场红),**挡不住空版本** —— 一个什么也没改的版本塞进表里,整组测试照样全绿,代价是
链上从此多一个什么也不区分的版本(每次校验每行白算一次哈希,`ByVersion` 上多一个永远为 0
的桶),而"版本号是假的"这件事再没人看着。那条用例是这个版本确实区分了什么的唯一证据。

("Location 若已是 UTC 才一样"说的是另一回事:那是老库里按**旧 v4 算法**签下的哈希对不
对得上,不是这两个版本今天的输出。)

具体表现:`ByVersion` 里 **v4 从此报不出来**。逐版尝试从新往旧走,v4 的行一律记在 v5 名下,
包括当年真由 v4 写入器写下的老行。两者覆盖的字段集相同,所以这个字段要表达的"保证到哪
一层"没有变。

### 3. 2026-09-15 之前写下的真实审计行,从此任何版本都验不过

这是本 ADR 最要紧的一句,写在这里是为了没有人日后把它当成 bug 去"修"。

老行的哈希签的是**写入进程当时那个 Location** 印出来的时间字符串。而那个 Location
**哪儿也没存**:读回来挂什么时区,由驱动、列类型和进程 TZ 决定。所以前像重建不出来 ——
救不回来,不是"还没想到办法"。

为什么不把归一化限定给 v5、让 v1..v4 保持老写法以救回老行:那样"老行验不验得过"就取决于
读的时候恰好碰上哪个 Location,也就是把一个**恒假**的警报换成一个**随机**的警报。随机的
更坏 —— 恒假的会被查清并写进文档,随机的会让人学会无视整个校验。这次刻意选了确定的那一边。

本次迁移**无存量数据**(生产未上线,开发库是演示数据,直接重建),所以现实影响是零:
新库里第一行就是 v5 写的,`matchAuditRow` 第一次尝试就命中。

**但如果日后要把旧库的审计行搬进来**,这件事需要单独决定,不能顺手 `INSERT` 完事。搬进来
的老行会让 verify 从第一条就红,而那正是"天天喊狼来了"的起点。可选的路大致三条,各有各的
代价,到时候按当时的需要挑:

- 搬进来但**明确标记**为不可校验(加一列或一个起算 ID,verify 从那一行之后开始算),
  老行只作为可读的历史留着 —— 它们不再是"证据",这一点要在界面上说清楚。
- 不搬,把旧库整个冻结成只读归档,新链从创世行重新开始。
- 搬并重签。**这一条等于把证据重新签一遍**,只有在能接受"这段历史此后只证明它没被改过
  *自搬迁那天起*"的前提下才成立,而且必须写下来。

## 这个校验能证明什么,不能证明什么

能:任何一行被**改过**内容,或者被从链中间**抽掉**,都会让重算的哈希对不上,而且指得出
是哪一行。

不能:从**末尾**整段截掉。剩下的链自己仍然自洽。要查出这种,得把链尾定期锚到网关之外
(打时间戳、外发、写只读介质)。这件事没有做,所以 `ChainReport.Note` 里明说了它覆盖不到
—— 一句没有边界的"链完好"会变成假的安全感。

## 附带的一条约束

写侧的 `auditPayload` 和读侧的 `auditPayloadFor` 共用同一段构造,**一处说了算**。
这两段一旦分开写,分叉的表现是校验器报出**成片的假警报**,而那比不校验更糟:没人会信一个
天天喊狼来了的警报,最后的结果是校验被关掉。
