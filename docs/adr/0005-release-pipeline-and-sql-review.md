# ADR-0005:数据库变更发布流水线(CI/CD)与规范审查规则库

- 状态:已接受(2026-08-24)
- 相关:ADR-0001(三层判定)、ADR-0004(按引擎判定方言)、迁移 `0019_pipeline_sqlreview.sql`

## 背景

此前一次数据库变更要落到生产,靠的是人在终端里按顺序做对若干件事:先自己看一眼 SQL
写得规不规范,再发起审批,批完了回到终端执行,执行完再手工查一下结果。每一步都有,但
**顺序、是否做过、做的结果**只存在于做事人的记忆里;审计链能证明"某条语句被谁执行了",
证明不了"它执行前有没有被审查过"。

同时,"写得规不规范"这件事在系统里根本没有位置。高危命令字典管的是**危险**
(`DROP` 在 prod 拦截),它无法表达"建表必须有主键"——后者一点都不危险,只是错的,而且
只在上线后才付出代价。

## 决策

### 一、规范审查(`internal/review`)与风险引擎分开

新增 `review` 包,纯函数:规则 + 语句进,findings 出,不读库、不认识用户。

两者回答的是不同问题,合并会同时毁掉两边:

- 把规范规则塞进高危字典,字典的 high/mid/off 就不再表示危险等级;
- 让审查去拒绝命令,它就不再是开发者能对自己代码随手跑的工具,而变成又一道拦路的闸门。

所以**审查不参与执行判定**。它的结论只有一个消费者:发布流水线的审查阶段——由流水线
决定 error 级命中是否中止本次发布。

规则库(`tbl_sql_review_rule`)的取舍:

- **`code` 即身份**。内置规则的 code 绑定 `registry` 里的实现,因此不允许改名;
  `TestBuiltinRegistryComplete` 双向校验目录与实现,杜绝"列在控制台里、看着是启用的、
  实际什么都不检查"的规则。
- **级别按规则而不是按命中定**。"缺表注释是否卡发布"是组织决定一次的事,不该由检查器
  每次现场判断。
- **方言作用域**(`mysql,tidb` / `all`)。TiDB 与 MySQL 在这里是**两个方言**,尽管在
  `gateway.engineFamily` 里它们同属一个协议族(那边选的是驱动)。TiDB 拒收部分 MySQL
  DDL、有自己的写热点规则;把它当 MySQL 审,会放过目标库根本不接受的语句。
- **升级只增不改**。`SeedSQLReviewRules` 只写缺失的 code:运维把某条规则降级或停用是
  一次策略决定,不能被下一次发版重置。

### 二、发布流水线不是执行旁路

流水线的执行阶段**再判一次**三层闸门(能力矩阵 · 高危字典 · 严格模式),而不是凭"提交时
判过了"直接下发。理由有二:

1. 本仓库每一条新执行通道都栽在同一个地方(第五轮 ER6:异步通道让终端里被拦下的人把
   同一条语句改成后台任务就跑了)。流水线是其中最有吸引力的一条——它异步、以服务身份
   运行、目的就是改生产。
2. 发布单可能在审批里停留数小时。这期间字典可以改、实例可以换环境、发起人的角色可以
   变。真正管用的判定是**语句下发那一刻**的判定。

提交时也判一次,但目的不同:让"你的角色根本碰不了这个实例"立刻得到答复,而不是排队三个
阶段后再失败。同理,提交时就检查"需要审批的变更所选流程里有没有审批阶段"——否则用户会
拿到一个"已受理"的发布单,几分钟后死在执行阶段。

### 三、审批通过不执行:`tbl_approval.release_id`

流水线的审批阶段复用既有审批单与审批链(不另开一套决策入口),但审批单带上 `release_id`,
`finalizeApproval` 见到它就**只记录决策、不执行命令**。

否则同一次变更会被应用两次:一次由审批通过时的执行器,一次由流水线的执行阶段——而后者
此时仍认为自己还没跑过。审计行因此停在 `pending`(已批准、尚未执行),真正的执行由执行
阶段逐条记账。

### 四、用巡检而不是回调恢复被审批阻塞的流水线

审批结论可以从四个门进来:控制台、飞书卡片、审批魔方回调、超时失效。挂在其中任何一个上
的回调,都会让从另外三个门进来的决策把发布单永远晾在那儿。`ResumeReleaseApprovals`
每 15 秒读一次已经记录了结论的行,谁写的都一样管用。

### 五、重启后的回收方向

- `running` → `failed`,并说明"执行阶段结果未知,请人工确认后重新发起"。它的执行阶段
  可能已经打到目标库了,**重跑是比报错更坏的结果**。
- `waiting` 原样保留:它卡在人身上,状态完整存在库里。
- `pending` 重新入队:它一步都没走。

### 六、发布是能力矩阵里的一个维度(`release`),不是只靠菜单

补充于 2026-08-24:第一版只用菜单键 `pipeline` 控制"谁能进发布页",执行阶段再按语句自身的
`write` / `ddl` 判。这留下一件**说不出口的事**:"这个角色可以自助发布到开发,预发布必须走审批,
生产一律不许发起"。要表达它,只能把 `DDL` 在生产整个关掉 —— 那会连带堵死终端和审批通道,而那
正是生产 DBA 干活的地方。

所以新增能力维度 `release`,与其它维度一样按分层判,三态在这里读作:

- `allow` — 可以在该分层发起发布单
- `approve` — 可以发起,但只能选**含审批阶段**的流程,哪怕这条语句本身放行
- `deny` — 不允许在该分层发起发布

它与执行阶段的复判**不重复**:`write`/`ddl` 回答"这个角色能不能在这里改数据/改结构",执行阶段
照问不误;`release` 回答的是"能不能起一张发布单",提交时就判,失败在第一步而不是第三个阶段。

升级回填**按各角色同分层的 `write` 等级推导**,不是一律 allow:不能写的角色本来也不该发起发布,
写要审批的发起也该审批。推导让升级不引入任何新策略,而且和内置角色的种子矩阵是同一张表
(`TestReleaseCapabilityMirrorsWrite` 盯住两者不许漂移)。每个 role × tier 都实际写行,理由与
`explain` 维度当初一样:没有行读作放行,管理员在页面上就分不清"没人做过决定"和"有人选了放行"。

## 影响

- 新菜单键 `pipeline`,从 `terminal` 继承(能在实例上执行的人,才是该发起发布的人);
  规范审查页挂在 `terminal` 上——上线前自查必须是写变更的人自己能跑的。
- 新表:`tbl_sql_review_rule` / `tbl_pipeline` / `tbl_pipeline_stage` / `tbl_release` /
  `tbl_release_stage`;`tbl_approval` 增加 `release_id`。
- 发布单快照 `pipeline_name` / `env` / `tier_code` / `engine`,与审批单同理(ADR 0013
  迁移的双快照):模板改了、环境换了分层,都不能改写这次发布**当时**做了什么。

## 未采纳

- **让审查参与终端执行判定**:审查会开始拒绝命令,而它的规则是风格与规范,拒绝的理由
  经不起在事故现场被追问。
- **物理备份阶段**:网关没有备份通道,做一个"备份完成"的绿灯而底下什么都没发生,是整条
  流水线里最危险的一行。备份阶段只执行运维显式配置的备份语句,未配置就 `skipped` 并
  如实说明。
- **执行阶段失败后继续**:`on_failure` 对执行阶段强制 `abort`——继续下去,后面的校验与
  通知会宣告一次并未发生的变更成功。
