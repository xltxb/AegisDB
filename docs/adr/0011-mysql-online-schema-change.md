# ADR 0011:MySQL 在线加索引走 gh-ost 那套(自研)

- 状态:进行中(阶段一、二已落地)
- 日期:2026-09-01
- 相关:`backend/internal/osc/`

## 先说一件容易被跳过的事

**MySQL 5.6+ 加二级索引本来就是 `ALGORITHM=INPLACE, LOCK=NONE`,不阻塞读写。**
所以这套东西的价值不在"在线"两个字上 —— 原生 DDL 已经在线了。它换来的是原生
DDL 给不了的三件事:

| | 原生 INPLACE | 影子表方案 |
|---|---|---|
| 中途限流 / 暂停 / 中止 | 做不到,下去就只能等 | 可以,拷贝是我们自己在推 |
| 从库延迟 | DDL 串行重放,主库跑 3 小时从库就延迟 3 小时 | 拷贝是普通 DML,从库跟得上 |
| MDL 排队雪崩 | 结束时要拿元数据锁,一个长事务就能让它卡住,后面所有访问该表的请求排在它身后 | cut-over 那一下才需要锁,且可重试 |

第三条是最容易被低估的:表面上是"加个索引",实际后果是全站访问该表的请求排队 ——
"加索引把库搞挂了"绝大多数是这么来的。

**如果你的表不大、从库延迟无所谓,原生 DDL 是更好的选择。** 这套东西是给大表和
有从库的场景准备的,不是给所有 ALTER 准备的。

## 为什么是自研,以及自研到哪一层

调用 gh-ost 二进制的方案被否掉了(需要网关起外部进程 —— 那个进程握着所有库的凭据)。
所以实现的是 **gh-ost 的算法**,不是它的二进制:

- **binlog 线协议用库**(`go-mysql/replication`)。gh-ost 自己也是这么做的 —— 它实现
  的是算法,不是协议解析。手写一个 binlog parser 要处理几十种事件类型和 JSON /
  DECIMAL 的列编码,没有任何收益,只有出错的机会。
- **算法自己写**:影子表、分块拷贝、binlog 追平、cut-over、限流。

## 算法与那条不变式

```
① 建影子表 _t_gho,把 ALTER 应用在它上面
② 从当前 binlog 位点开始订阅,把 t 上的行事件重放到 _t_gho
③ 同时按主键分块,把 t 的存量行拷进 _t_gho
④ 追平后 cut-over:t → _t_del,_t_gho → t(原子)
```

②③ 是**同时**在跑的,它们会交错。收敛靠的是这一组写法:

| 来源 | 写法 | 为什么 |
|---|---|---|
| 存量拷贝 | `INSERT IGNORE` | 这一行若已被 binlog 重放写成新值,拷贝不能把它盖回旧值 |
| binlog INSERT/UPDATE | `REPLACE INTO` | binlog 拿到的永远是"这一行现在的样子",可以无条件盖过拷贝写的旧值 |
| binlog DELETE | `DELETE` | 删掉的行,拷贝即便随后写进来也会被下一次重放删掉 |

**这组不变式是整件事的正确性所在:拷贝永不覆盖,重放永远覆盖。** 任何改动都必须先
回到这张表。这也是为什么 `binlog_row_image` 必须是 `FULL` —— MINIMAL 下 UPDATE 只
带被改的列,`REPLACE INTO` 会把没带的列写成默认值,悄悄毁掉数据。

## 拒绝优先

本包的第一道关不是拷贝,是**拒绝**。宁可拒绝一个本可以做的,不可放过一个做不干净
的 —— 前者是麻烦,后者是数据不一致。

阶段一已落地的 14 条阻塞项:

| 类别 | 拒绝原因 |
|---|---|
| 适用范围 | 非 MySQL;非索引变更;MySQL < 5.6 |
| 目标表 | 表不存在;无主键且无唯一非空索引;有外键(任一方向);有触发器 |
| 实例参数 | `log_bin=OFF`;`binlog_format≠ROW`;`binlog_row_image≠FULL`;缺 REPLICATION SLAVE / CLIENT |
| 残留 | 上次未清理的 `_gho` / `_del` 表 |
| 容量 | 磁盘余量 < 表大小 × 1.2 |

几条值得单独说的判断:

- **无主键但有唯一非空索引 → 放行。** 分块要的是"稳定、唯一、非空",主键只是最常见
  的那一种。一并拒掉会挡住一批本可以做的表。
- **拿不到磁盘余量 → 不拦。** 把未知当成 0 会拒掉全部变更。
- **外键两个方向都拒。** 指向影子表的约束会跟着 rename 走,指向原表的会在 cut-over
  后指向被弃置的旧表 —— 两个方向都把约束悄悄挪到了错误的对象上。
- **一次报全部问题,不是第一个。** 让人改一条、重试、再发现第二条,在生产上就是三个
  变更窗口。
- **引擎不对就停止后续检查。** 对着一个 PostgreSQL 实例抱怨 binlog 参数毫无意义。

范围刻意窄:**只做加索引 / 删索引**。ADD COLUMN / MODIFY COLUMN 会引入类型转换与
默认值回填的语义问题,不在同一次里搭进来。范围窄不是偷懒,是让"能做的都做对"可验证。

- **测试用的 MySQL 一度没有了。** `5a329a3` 在把网关自身存储收敛到 PostgreSQL
  (ADR 0018)时,顺手把 compose 里的 `mysql:8.0` 换成了 `postgres:16`。那对存储是
  对的,但 OSC 要的 MySQL 是**被管理的目标库**,是另一个角色。现在以 `mysql-target`
  的名字加回来了,并按重放的需要配了 ROW + FULL,而不是用默认值。

分块拷贝只支持**单列**唯一非空键。多列键的游标是一个元组,`> ?` 要改写成字典序比较;
加索引这个场景里单列主键覆盖了绝大多数表,先把能做对的做对。

**整个特性默认关闭,直到全部阶段落地。** 半成品绝不能从界面上点得到 —— 一个跑到
一半的迁移留下的是影子表和一段没追平的 binlog,而人以为自己"加了个索引"。

## 测试

前置检查是纯函数,不依赖 MySQL,已测透。

**阶段二起必须对着真 MySQL 测** —— 拷贝与重放的交错、cut-over 的锁竞争,拿 sqlite
或 mock 测出来的绿色是假的。两种起法都行:

```bash
# 本机装(macOS)。新版 MySQL 默认就是 log_bin=ON / ROW / FULL,不必改配置。
brew install mysql && brew services start mysql
mysql -u root -e "CREATE DATABASE osc_test;
  CREATE USER 'vela'@'127.0.0.1' IDENTIFIED BY 'velapass';
  GRANT ALL ON osc_test.* TO 'vela'@'127.0.0.1';
  GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'vela'@'127.0.0.1';"

# 或用仓库根的 mysql-target 容器(端口 3307,避开本机的 3306)
docker compose up -d mysql-target
export VELA_OSC_MYSQL_DSN="vela:velapass@tcp(127.0.0.1:3307)/osc_test"
```

**连不上是失败,不是 skip。** 和后端其余测试对 `vela_test` 的规矩一致:静默跳过会让
一个谁也没跑过的 `osc` 包看起来是绿的,而它是会在生产库上改表的东西。

那条不变式(拷贝 `INSERT IGNORE` 永不覆盖)有一条测试单独钉住,并做过变异验证:把它
改成 `REPLACE`,测试立刻报「id=5 的值被拷贝盖回成了旧值」。能通过不等于能失败,这种
承重的断言值得确认它真的会红。

这一条不是流程要求,是这个特性的前提:一个自己会动数据的工具,没有对着真数据库跑过
的代码路径,等于没写。
