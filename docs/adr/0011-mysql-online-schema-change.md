## 先说一件容易被跳过的事

**MySQL 5.6+ 加二级索引本来就是 `ALGORITHM=INPLACE, LOCK=NONE`,不阻塞读写。**
所以这套东西的价值不在"在线"两个字上 —— 原生 DDL 已经在线了。它换来的是原生
DDL 给不了的三件事:

| | 原生 INPLACE | 影子表方案 |
|---|---|---|
| 中途限流 / 暂停 / 中止 | 做不到,下去就只能等 | 可以,拷贝是我们自己在推 |
| 从库延迟 | DDL 串行重放,主库跑 3 小时从库就延迟 3 小时 | 拷贝是普通 DML,从库跟得上 |
| MDL 排队雪崩 | 结束时要拿元数据锁,一个长事务就能让它卡住,后面所有访问该表的请求排在它身后 | cut-over 那一下才需要锁,且可重试 |

第三条是最容易被低估的:表面上是"加个索引",实际后果是全站访问该表的请求排队 ——
"加索引把库搞挂了"绝大多数是这么来的。

**如果你的表不大、从库延迟无所谓,原生 DDL 是更好的选择。** 这套东西是给大表和
有从库的场景准备的,不是给所有 ALTER 准备的。

## 为什么是自研,以及自研到哪一层

调用 gh-ost 二进制的方案被否掉了(需要网关起外部进程 —— 那个进程握着所有库的凭据)。
所以实现的是 **gh-ost 的算法**,不是它的二进制:

- **binlog 线协议用库**(`go-mysql/replication`)。gh-ost 自己也是这么做的 —— 它实现
  的是算法,不是协议解析。手写一个 binlog parser 要处理几十种事件类型和 JSON /
  DECIMAL 的列编码,没有任何收益,只有出错的机会。
- **算法自己写**:影子表、分块拷贝、binlog 追平、cut-over、限流。

## 算法与那条不变式

```
① 建影子表 _t_gho,把 ALTER 应用在它上面
② 从当前 binlog 位点开始订阅,把 t 上的行事件重放到 _t_gho
③ 同时按主键分块,把 t 的存量行拷进 _t_gho
④ 追平后 cut-over:t → _t_del,_t_gho → t(原子)
```

②③ 是**同时**在跑的,它们会交错。收敛靠的是这一组写法:

| 来源 | 写法 | 为什么 |
|---|---|---|
| 存量拷贝 | `INSERT IGNORE` | 这一行若已被 binlog 重放写成新值,拷贝不能把它盖回旧值 |
| binlog INSERT/UPDATE | `REPLACE INTO` | binlog 拿到的永远是"这一行现在的样子",可以无条件盖过拷贝写的旧值 |
| binlog DELETE | `DELETE` | 删掉的行,拷贝即便随后写进来也会被下一次重放删掉 |

**这组不变式是整件事的正确性所在:拷贝永不覆盖,重放永远覆盖。** 任何改动都必须先
回到这张表。这也是为什么 `binlog_row_image` 必须是 `FULL` —— MINIMAL 下 UPDATE 只
带被改的列,`REPLACE INTO` 会把没带的列写成默认值,悄悄毁掉数据。

## 拒绝优先

本包的第一道关不是拷贝,是**拒绝**。宁可拒绝一个本可以做的,不可放过一个做不干净
的 —— 前者是麻烦,后者是数据不一致。

阶段一已落地的 14 条阻塞项:

| 类别 | 拒绝原因 |
|---|---|
| 适用范围 | 非 MySQL;非索引变更;MySQL < 5.6 |
| 目标表 | 表不存在;无主键且无唯一非空索引;有外键(任一方向);有触发器 |
| 实例参数 | `log_bin=OFF`;`binlog_format≠ROW`;`binlog_row_image≠FULL`;缺 REPLICATION SLAVE / CLIENT |
| 残留 | 上次未清理的 `_gho` / `_del` 表 |
| 容量 | 磁盘余量 < 表大小 × 1.2 |

几条值得单独说的判断:

- **无主键但有唯一非空索引 → 放行。** 分块要的是"稳定、唯一、非空",主键只是最常见
  的那一种。一并拒掉会挡住一批本可以做的表。
- **拿不到磁盘余量 → 不拦。** 把未知当成 0 会拒掉全部变更。
- **外键两个方向都拒。** 指向影子表的约束会跟着 rename 走,指向原表的会在 cut-over
  后指向被弃置的旧表 —— 两个方向都把约束悄悄挪到了错误的对象上。
- **一次报全部问题,不是第一个。** 让人改一条、重试、再发现第二条,在生产上就是三个
  变更窗口。
- **引擎不对就停止后续检查。** 对着一个 PostgreSQL 实例抱怨 binlog 参数毫无意义。

范围刻意窄:**只做加索引 / 删索引**。ADD COLUMN / MODIFY COLUMN 会引入类型转换与
默认值回填的语义问题,不在同一次里搭进来。范围窄不是偷懒,是让"能做的都做对"可验证。

### 阶段四:为什么是一条 RENAME

原计划写的是"两步锁重命名"。落地时收敛成**单条原子 `RENAME TABLE t TO _t_del,
_t_gho TO t`** —— MySQL 保证这一条是原子的,没有任何一刻 `t` 这个名字是空的。
它仍然要等元数据锁,但等待期间读写是**排队而不是失败**:排队可以忍,表消失不能。

朴素的 `DROP` + `RENAME` 在两条语句之间留下一个窗口,那一瞬间访问这张表的每个请求
都拿到 `1146 table doesn't exist`。这个窗口**极窄**,窄到只断言最终状态永远发现不了
它 —— 所以有一条用例开并发读循环一直查这张表,断言它一次都没读到表不存在。变异验证
过:把那一条 RENAME 拆成两条,**1142 次读里有 1 次**撞上,测试立刻报出来。

`_t_del` **留着不删**。出了事要能换回去,那是唯一的退路;磁盘可以事后清,数据不行。

追平判定由调用方给(`ReplayCaughtUp`),CutOver 自己不等 —— 等待属于阶段五,一个动作
既管切换又管等待,失败时说不清是没追上还是换不过去。

### 阶段五:中止的一半是续跑

这一段买的是开篇列的第一件事 ——「可限流、可暂停、可中止」。其中**中止最要紧,而
"能停"只是一半:停完要能接着跑**。做不到的话中止等于前功尽弃,那个中止键没人敢按,
于是它等于不存在。

所以 `CopyAll` 返回 `CopyResult{Copied, Cursor, Interrupted}`:

- `Cursor` 是停在哪,`CopyOptions.Resume` 拿它接着跑。游标本来就是按键范围推进的,
  续跑天然可重入。
- `Interrupted` 让调用方分得清「跑完了」和「被停了」。少了它,一次被中断的迁移会被
  当成完成的,而它的影子表里少着一截数据 —— 随后的 cut-over 就把那个缺口换上了生产。

两条都做过变异验证:去掉 `Cursor` 或去掉取消检查,对应的断言立刻变红。

**限流拆成两半。** `shouldPause(lag, max)` 是纯判断,逐格测透;延迟从哪来做成可注入的
`ReplicaLag` 函数。这样"限流真的让拷贝慢下来"可以用假延迟源测,不必搭一套主从复制 ——
那测的是 MySQL 的复制,不是我们的逻辑。

阈值为 0 表示没开限流。把它当成「一有延迟就停」会让拷贝永远动不了。正好等于阈值不算
超,否则一个恰好卡在线上的稳定延迟会让它一直等下去。

限流的等待本身可被中止 —— 否则一个被限住的迁移对中止信号无动于衷,而"能中止"正是
这套东西相对原生 DDL 的卖点之一。

### 端到端:交错必须真的发生

`TestMigrate_EndToEndWithConcurrentWrites` 走完整条链路,并在**拷贝进行中**持续写入。
不制造交错的话,拷贝与重放各跑各的,那条不变式根本不会被触发 —— 跑出来的绿是假的。

这一点比看上去难。第一版一次就绿,查下来是**拷贝比写入快得多**:2000 行在写入循环还
没铺开时就拷完了,交错压根没落在同一批行上。所以用例里现在有一条硬断言:统计「重放先
碰过、拷贝随后才走到」的键,为 0 就直接判失败,并写明「绿是假的」。调整节奏后这个数
稳定在 1100 以上。

中途还犯过一个判据错误,值得记下来:曾在拷贝刚结束时断言「影子表里还是旧值 = 拷贝覆盖
了重放」。那是错的 —— 那一刻本来就有一批事件还在 binlog 队列里没重放到,而「重放尚未
追平」与「拷贝盖回旧值」**在数据上长得一模一样**。真正能区分二者的只有收敛。

四向变异验证的结果如实记在用例注释里:重放漏发 DELETE、重放用 INSERT IGNORE、UPDATE
用改前镜像都被抓住;**拷贝用 REPLACE 抓不住** —— 停写后的收尾重放会把每行再 REPLACE
一遍,悄悄修正了拷贝中途的覆盖。生产里写入不会停,没有这段安静的收尾期,所以那条路径
靠的是 `TestCopy_NeverOverwritesWhatReplayAlreadyWrote` 这条不依赖时序运气的单点用例。

半成品绝不能从界面上点得到 —— 一个跑到一半的迁移留下的是影子表和一段没追平的
binlog,而人以为自己"加了个索引"。

## 限流的另一半:延迟从哪来

阶段五留下的缺口是「`ReplicaLag` 有注入点,但没有数据源」。补它的时候有三个决定,
每一个都有一条被否掉的、看起来更省事的路。

### 不读 `Seconds_Behind_Source`,自己写心跳

主库上 `SHOW REPLICA STATUS` **返回空** —— 那条语句问的是"我落后我的上游多少",
而主库没有上游。延迟只能从从库那一侧读,这一点先把"在目标连接上读一下就完了"排除掉。

即便连到从库上,`Seconds_Behind_Source` 也不该信:它在从库空闲时报 0,在一个大事务
重放到一半时**也报 0**(那个事务还没开始应用)。而恰恰是大事务期间最需要限流。

所以走 gh-ost 那条路:主库上一张单行心跳表 `_<table>_ghc`,每 500ms 写一个时间戳,
从库上把它读回来,差多少就是**数据晚到了多久** —— 与从库忙不忙无关。

**时间戳由网关进程写,不是 `NOW(6)`。** 用服务器时间的话,比较的是 MySQL 的钟与
网关的钟,两台机器差几秒是常事,而那几秒会被整个算成从库延迟:要么凭空限流,要么
把真延迟抵消掉。心跳由网关写、由网关读,全程只有一个钟。

心跳存 `BIGINT` 里的 Unix 微秒,不是 `DATETIME`:后者要连接带 `parseTime=true`、
两端 `loc` 一致才读得回 `time.Time`,而读它的是**从库**那条连接,参数是从主库 DSN
借过去的 —— 不该在那里赌它带对了参数。

### 从库的地址问主库要,凭据借主库的

网关的连接表里没有从库。三条路:让人在发起时选一条已登记的从库连接、在配置文件里
按实例写 DSN、或者问主库自己(`SHOW REPLICAS`,8.0.22 以下是 `SHOW SLAVE HOSTS`)。

选了问主库:前两条都要求人**维护一份与真实拓扑同步的名单**,而拓扑会变 —— 名单过期
的后果不是报错,是限流悄悄护着一台已经下线的从库。主库报出来的永远是此刻真连着的。

代价写在这里:**从库必须配 `report_host`**,否则主库报出的那一行 `Host` 是空的。
空地址被直接丢掉(拿它去连会连回网关自己),于是那台从库在限流眼里不存在。

凭据借主库的那一套。复制拓扑里两端账号通用是常态,而让人在网关里单独登记一遍从库
密码,等于多一份会过期的秘密。拼从库 DSN 走驱动的 `ParseDSN`/`FormatDSN`,不做字符串
拼接:密码里带 `@` 或 `:` 的账号真实存在,手写的切分会把密码切断 —— 而切断的后果
不是一个显眼的报错,是**限流静默失效**。

### 装不起来就退化,而且必须说出口

限流有四种装不起来的方式:阈值配成了 0、主库报不出从库(单机、没配 `report_host`)、
从库连不上、心跳到不了从库(复制断着,或者复制过滤器把这个库排除了)。

最后一种最阴:发现得到、也连得上,只是那一行永远读不回来。不管它的话,算出的延迟
会一路变大,把拷贝**永久按死**在限流里,而界面上写着"限流已启用"。所以装限流的最后
一步是探一次:5 秒之内至少有一个从库读得到心跳,否则退化成不限流。

四种都不是错误,迁移照跑 —— 单机实例上"没有从库"是事实,把它当故障会让一个本来最
安全的迁移反而做不成(与前置检查对"拿不到磁盘余量"的立场一致)。

心跳表本身走正常退出路径清掉(成功、失败、中止都一样)。进程被 kill 掉时它会残留,
而残留的后果是**下一次同表迁移的限流装不起来**:心跳表已存在时拒绝复用(两个心跳
互相覆盖,两边算出的延迟都是错的),退化成不限流,留痕里点名"心跳表建不出来(已存在)"。
链条是闭合的 —— 人看得到原因,删掉那张表就恢复。残局列表里只列影子表,不列它:
心跳表不装数据,删错了也只是少一次限流,而影子表删错了是数据。

但**照跑不等于不说**。每一次迁移都落两列:`throttle` 是一句人话(开着:几个从库、
什么阈值;没开:上面四种里的哪一种),`throttled` 是同一件事的布尔面。分成两列是因为
界面要按它上色,而**按中文前缀去判断"未启用"的话,后端改一次文案,那条警示就悄悄
没了** —— 它恰恰是最不该丢的那一条。

阈值来自配置 `osc.max_lag_seconds`,不写 = 30 秒。要关限流得**写一个负数**:0 不行,
因为 0 同时也是"这一段根本没写",而把没写解释成不限流,会让升级上来的部署在打开
开关之后悄悄跑在没有限流的状态下。

### 这一段怎么验的

限流的每一环都能在单机上"绿"得毫无破绽:心跳写得动、延迟算得出、`shouldPause`
判得对。但**拷贝真的会因为从库落后而停下来**,只有让一个真从库落后才验得到。

所以有 `replica_replication_test.go`:它要一套真主从,把从库的 SQL 线程停掉制造延迟,
断言拷贝在那段时间里**一行都没搬**(限流检查在每块之前,第一块也算一块),然后恢复
复制,断言它自己接着跑完 —— 「停得住」只是一半,停完不能自己恢复的话,这个限流等于
把迁移永久卡死,那比不限流更糟,因为人会把它关掉。

做过变异验证:把 `waitForReplica` 改成直接返回,这条用例当场报「从库落后 1s 以上时
仍然拷了 3000 行」。

没有从库时这几条用例跳过,并在 skip 文案里写明怎么搭一套。**跑演练或 CI 时设
`VELA_OSC_EXPECT_REPLICA=1`** —— 那之后跳过变成失败,省得一次本该验证主从的运行
悄悄什么都没验。这条开关本身也验过:让 `SHOW REPLICAS` 返回空,严格模式立刻报错。

## 界面:一个默认关着的开关

上面那句「半成品绝不能从界面上点得到」仍然成立,而这一节记的是它怎么被**有条件地**
放开了 —— 需求方明确要求"能点'开始迁移'",并且要求残局落库、重启后看得见。

直接照做会正面撞上那句话。所以放开的不是"能点",而是三道写进代码里的闸:

1. **配置开关 `osc.enabled` 默认 `false`**,两份 `configs/*.yaml` 里都写着关闭的
   理由。关着的时候 `POST /api/v1/osc/jobs` 返回 `42700`(`CodeOscDisabled`)——
   单独一个业务码,不是 404,也不是 500:前者看起来像路由写错了,后者看起来像坏了,
   而真实原因是"它还没做完,被有意关着",界面要能原样说出这句话。
2. **发起前必过 `Preflight`,而且是同步做的**。被拒绝的变更连一条任务记录都不留,
   更不会建出影子表;阻塞项一次全列出来 —— 一条条试出来,在生产上就是一个个变更窗口。
3. **做不到的事写在按钮旁边**,不在这份文档里。`GET /api/v1/osc/status` 回一个
   `caveats` 数组,页面原样渲染在发起按钮上方。要按下那颗按钮的人不会来读 ADR;
   后端补齐一件就删一条,两边不会各说各话。「没有从库延迟限流」那一条已经删掉了,
   换上的是它的下半句:**限流装不装得起来要看目标实例当时的样子**,装不起来时
   迁移照跑,只是不限流。这一条删不掉 —— 它不是没做完,是这件事本身就有前提。

读接口(状态、列表、单条)**不受开关影响**。一次半途失败留下的影子表和一段没追平的
binlog,恰恰是在人关掉开关之后最需要被看见的东西 —— 把列表一起锁上等于把残局藏起来。
页面因此把"残局"单独拎到历史列表**前面**:状态停在中间态的(进程没了,没有人再推进
它),以及已失败/中止但影子表名还在的(自动清理没做成,库里躺着一张表)。已完成的任务
一律不算残局,哪怕它记着影子表名 —— 切换成功之后那个名字指的是已经上位的新表,列成
待清理会诱导人去删掉刚换上去的表。

写接口(发起、中止)限平台管理员。这条守卫的测试一开始是**假绿**的:只读账号确实被
挡下了,但挡它的是"实例凭据不完整"(40001),跟权限毫无关系 —— 去掉 `admin` 中间件
它照样通过。变异验证当场抓到,断言改成点名 `40300` 之后才真的守住。

还没做的:**残留的一键清理**(现在只把残局列出来,删表由人手工做 —— 一个会自动删表
的按钮,在这套东西的成熟度上还不该存在)。

从库延迟采集已经补上,而它给界面添了新的一条:限流**可能装不起来**,而那时迁移照跑。
所以任务行上多了一句留痕(`throttle` / `throttled` 两列),记的是**这一次**的事实,
不是发起页面上那段"这套东西能做什么"。两者会不一致,而不一致的那一刻正是要看的那次。

## 第二个入口:发布流水线

上面那一节记的是**人**在控制台按下"开始迁移"。这一节记的是另一条路:发布单执行到一条
索引变更时,**它自己改走 OSC**。

判定顺序在 `internal/oscroute`,一个不碰数据库的纯函数层:

```
skip 覆盖      → 不走(发起人对这一单说了不,不再问别的)
force 覆盖     → 走,跳过行数判断,但仍然要通过语句识别
急停或未启用   → 不走
autoRoute 关   → 不走
非 MySQL       → 不走
不是索引 DDL   → 不走
行数 ≤ 阈值    → 不走(正好等于阈值不算超)
否则           → 走
```

顺序本身就是决定。覆盖排在策略前面 —— 策略是对一类情况的默认,覆盖是人对这一次的明确
指令。而**引擎与语句识别排在 force 前面**:`force` 跳过的是行数判断,不是"把任何语句都
塞给 OSC"。一条改列语句、一个 PostgreSQL 目标,强制模式也进不去 —— 进去了要到 Preflight
才失败,而人看到的是一张失败的发布单,不是"这条语句不该走这条路"。

行数取 `information_schema.TABLES.TABLE_ROWS` 的估算值,**不做 `COUNT(*)`**:八百万行上
要跑几十秒,而边界上误判的后果是"走了/没走 OSC",两边都不危险。它是懒查的 —— 只有认出
这是索引 DDL 之后才去查,一张单里十条 UPDATE 不该换来十次往返。

### 走不了就直发,并且说出来

阈值命中了、OSC 却用不上(急停关着、目标不是 MySQL、发起被 Preflight 拒),**迁移照跑,
只是不限流**。原生加二级索引本来就是 `ALGORITHM=INPLACE, LOCK=NONE` —— "没走 OSC"是失去
了限流、从库跟得上、MDL 可重试这三件事,不是干了一件危险的事。让一个本来能跑的发布单
卡死,理由却是"我们本想用个更温和的办法",不成立。

但**照跑不等于不说**:阶段日志逐条记下走的哪条路。只有索引 DDL 才记 —— 一条 UPDATE 旁边
写"不是索引变更"没有信息量,而阶段日志落库前会被截断到 20000 字,一次跨几小时、分几段
恢复的执行,那点额度要留给真正说明了什么的行。

### 急停开关管住两条路,而且是同一个闭包

`osc.enabled` 有两层:配置文件里的那个是**前提**(打开它的条件是一次对着有从库的实例的
演练),`tbl_setting` 里的那个是**急停**(一次迁移正在把从库拖垮时,人要立刻挡住后续发起,
而不是先去重启网关)。两者相与,方向不对称 —— 后台那个只关得掉、打不开。

**流水线这条路必须走同一道闸。** 它接上之前,那道闸只拦 HTTP 接口;接上之后,`svc.AttachOSC`
让流水线直接调 `Runner.Start`,绕过了它。运维扳下急停以为挡住了所有发起,而发布单还在
一个个地起新任务 —— 而设置页上写着"关掉它立刻挡住后续发起"。

所以 `router.go` 里那个 `enabled` 闭包**提出来给两处共用**,不是各写一份判断:各写一份
迟早会再次分叉,而分叉的那一刻没有人会发现。

### 执行阶段怎么挂在一个几小时的任务上

阶段记两个值:`exec_cursor`(**已经执行完**的语句条数)和 `osc_job_id`(此刻挂着哪个任务)。

```
stageExecute:
  拆句,从 exec_cursor 开始逐条
    ├ 不走 OSC → 直发 → 审计 → cursor++
    └ 走 OSC   → Runner.Start → 记 job_id 与 cursor(**不 +1**) → 返回 waiting
任务走到终态 → Runner.OnFinish → 找到等它的阶段:
    ├ done            → cursor++、job_id 清零 → 异步 driveRelease 续跑
    └ failed/aborted  → 阶段判失败,按 OnFailure 决定整单的去向
```

几条踩过的坑,都在代码里留了注释:

- **游标停在"已完成"而不是"正在做"。** 走 OSC 的那条要等任务结束才算完成。差一格的后果
  是恢复时跳过一条没执行的、或重跑一条执行过的 —— 而一条 `UPDATE` 重跑不会报任何错。
- **游标边走边记。** 跑完一起记的话,进程在中途崩溃时库里写的是 0,恢复从头再来。
- **日志要接上。** `driveRelease` 每次都用 `out.log` 覆盖阶段的日志列,恢复时从空开始的话,
  这个阶段在暂停之前记下的每一条都会消失。
- **失败不能无条件交回 `driveRelease`。** 它的循环把已经是 failed 的阶段当成"处理过了"跳过
  (那是为 `onFailure=continue` 准备的),循环走完就落到 `finishRelease(success)` ——
  迁移失败的发布单最后会显示**成功**,而那条索引根本没加上。比"永远等下去"更糟:等着的
  单子看得见,说成功的单子没人再去看。
- **续跑要异步。** `OnFinish` 挂在迁移的退出路径上,而 `driveRelease` 会把剩下的阶段全跑
  一遍(一条没到阈值的语句走 `Executor.Run`,超时默认 5400 秒)。同步跑的话,它阻塞多久,
  `IsRunning`/`Abort` 就对一个已经写成 done 的任务说多久的谎。
- **中止发布单要连带中止迁移**,而且遍历**全部**挂着任务的阶段 —— 命中第一个就返回的话,
  一个过期的 job id 排在前面会让终止原因写着"已连带叫停 #错的那个",真正在跑的那个只字
  未提。`Abort` 只叫得停本进程手上的任务,停不掉时照常中止发布单,但要告诉人去哪儿收拾。

### 界面:两种 waiting 长得一模一样

`waiting` 现在有两种意思 —— "等人点确认执行"和"等一个迁移跑完",而它们的 `status` 完全
相同。判据是 `osc_job_id > 0`。给后者画上「确认执行」按钮,按下去只会让人以为自己推进了
什么。这与本文档前面"中止按钮跟着 `running` 走而不是跟着 `status` 走"是同一类问题。

第三种情况是网关重启之后:阶段还挂着任务,而那个任务已经没有进程在推进了。判据是
`oscRunning`(不落库,由接口层从 `Runner.IsRunning` 现填,与 `osc.Job.Running` 同一个做法)。
它与"正在等"**互斥展示** —— 同一张卡片上先写"点此查看进度"、再写"它不会自己走完",
只扫一眼顶部的人会走开。

## 授权:这条路放宽了一道边界

OSC 的 HTTP 发起接口限平台管理员,而**发布单的执行闸不限**。自动路由接上之后,一个非
管理员点「确认执行」就会发起一次 OSC 迁移 —— 在生产库上建影子表、拷全表、改表名。

这是有意的:**发布单的审批链就是授权**,OSC 只是执行手段,不是一道独立的权限。变更本身
已经过了 review 与 approve。

但有一个边界要说清楚:**并非每张单都有审批阶段。** 低风险变更走的流程可能根本没有
`approve` 这一步。那种单子上,"审批链就是授权"实际等于"执行闸那个人就是授权"。这是这条
决定的真实含义,不是它的例外 —— 接受它,或者把大表索引变更所在的流程配上审批阶段,
而后者是流程配置的事,不是代码的事。

## 测试

前置检查是纯函数,不依赖 MySQL,已测透。

**阶段二起必须对着真 MySQL 测** —— 拷贝与重放的交错、cut-over 的锁竞争,拿 sqlite
或 mock 测出来的绿色是假的。两种起法都行:

```bash
# 本机装(macOS)。新版 MySQL 默认就是 log_bin=ON / ROW / FULL,不必改配置。
brew install mysql && brew services start mysql
mysql -u root -e "CREATE DATABASE osc_test;
  CREATE USER 'vela'@'127.0.0.1' IDENTIFIED BY 'velapass';
  GRANT ALL ON osc_test.* TO 'vela'@'127.0.0.1';
  GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'vela'@'127.0.0.1';"

# 或用仓库根的 mysql-target 容器(端口 3307,避开本机的 3306)
docker compose up -d mysql-target
export VELA_OSC_MYSQL_DSN="vela:velapass@tcp(127.0.0.1:3307)/osc_test"
```

**连不上是失败,不是 skip。** 和后端其余测试对 `vela_test` 的规矩一致:静默跳过会让
一个谁也没跑过的 `osc` 包看起来是绿的,而它是会在生产库上改表的东西。

**限流那几条要一套主从**,单机上会跳过。仓库根的 `docker-compose.yml` 里有一对
(`mysql-target` + `mysql-replica`,复制由 `mysql-replica-setup` 一次性接好);
本机起第二个实例也行:

```bash
mysqld --initialize-insecure --datadir=/tmp/osc-replica
mysqld --datadir=/tmp/osc-replica --port=3308 --socket=/tmp/osc-replica.sock \
  --server-id=2 --report-host=127.0.0.1 --report-port=3308 \
  --log-bin --binlog-format=ROW --binlog-row-image=FULL \
  --gtid-mode=ON --enforce-gtid-consistency=ON --mysqlx=OFF &
# 主库:CREATE USER 'repl'@'%' IDENTIFIED BY 'replpass'; GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
# 从库:CHANGE REPLICATION SOURCE TO SOURCE_HOST='127.0.0.1', SOURCE_PORT=3306,
#        SOURCE_USER='repl', SOURCE_PASSWORD='replpass', SOURCE_AUTO_POSITION=1,
#        GET_SOURCE_PUBLIC_KEY=1; START REPLICA;
VELA_OSC_EXPECT_REPLICA=1 go test ./internal/osc/ -run TestReplication -v
```

`report-host` 报的是 **127.0.0.1:3308**,不是容器名或主机名:主库报出的那个地址是
**网关要去连的**,不是主库自己要连的。写成容器名的话,容器网络之外(比如在宿主机上
跑测试)会连不上,而连不上在这套东西里表现为"限流退化成不限流",不是一个显眼的报错。

那条不变式(拷贝 `INSERT IGNORE` 永不覆盖)有一条测试单独钉住,并做过变异验证:把它
改成 `REPLACE`,测试立刻报「id=5 的值被拷贝盖回成了旧值」。能通过不等于能失败,这种
承重的断言值得确认它真的会红。

这一条不是流程要求,是这个特性的前提:一个自己会动数据的工具,没有对着真数据库跑过
的代码路径,等于没写。
