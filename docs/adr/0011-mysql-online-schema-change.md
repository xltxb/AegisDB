# ADR 0011:MySQL 在线加索引走 gh-ost 那套(自研)

- 状态:已接入产品(2026-10-01):引擎阶段一至五完成;终端与发布流水线入口、任务持久化、界面见 `.scratch/osc-product`
- 日期:2026-09-01
- 相关:`backend/internal/osc/`

## 先说一件容易被跳过的事

**MySQL 5.6+ 加二级索引本来就是 `ALGORITHM=INPLACE, LOCK=NONE`,不阻塞读写。**
所以这套东西的价值不在"在线"两个字上 —— 原生 DDL 已经在线了。它换来的是原生
DDL 给不了的三件事:

| | 原生 INPLACE | 影子表方案 |
|---|---|---|
| 中途限流 / 暂停 / 中止 | 做不到,下去就只能等 | 可以,拷贝是我们自己在推 |
| 从库延迟 | DDL 串行重放,主库跑 3 小时从库就延迟 3 小时 | 拷贝是普通 DML,从库跟得上 |
| MDL 排队雪崩 | 结束时要拿元数据锁,一个长事务就能让它卡住,后面所有访问该表的请求排在它身后 | cut-over 那一下才需要锁,且可重试 |

第三条是最容易被低估的:表面上是"加个索引",实际后果是全站访问该表的请求排队 ——
"加索引把库搞挂了"绝大多数是这么来的。

**如果你的表不大、从库延迟无所谓,原生 DDL 是更好的选择。** 这套东西是给大表和
有从库的场景准备的,不是给所有 ALTER 准备的。

## 为什么是自研,以及自研到哪一层

调用 gh-ost 二进制的方案被否掉了(需要网关起外部进程 —— 那个进程握着所有库的凭据)。
所以实现的是 **gh-ost 的算法**,不是它的二进制:

- **binlog 线协议用库**(`go-mysql/replication`)。gh-ost 自己也是这么做的 —— 它实现
  的是算法,不是协议解析。手写一个 binlog parser 要处理几十种事件类型和 JSON /
  DECIMAL 的列编码,没有任何收益,只有出错的机会。
- **算法自己写**:影子表、分块拷贝、binlog 追平、cut-over、限流。

## 算法与那条不变式

```
① 建影子表 _t_gho,把 ALTER 应用在它上面
② 从当前 binlog 位点开始订阅,把 t 上的行事件重放到 _t_gho
③ 同时按主键分块,把 t 的存量行拷进 _t_gho
④ 追平后 cut-over:t → _t_del,_t_gho → t(原子)
```

②③ 是**同时**在跑的,它们会交错。收敛靠的是这一组写法:

| 来源 | 写法 | 为什么 |
|---|---|---|
| 存量拷贝 | `INSERT IGNORE` | 这一行若已被 binlog 重放写成新值,拷贝不能把它盖回旧值 |
| binlog INSERT/UPDATE | `REPLACE INTO` | binlog 拿到的永远是"这一行现在的样子",可以无条件盖过拷贝写的旧值 |
| binlog DELETE | `DELETE` | 删掉的行,拷贝即便随后写进来也会被下一次重放删掉 |

**这组不变式是整件事的正确性所在:拷贝永不覆盖,重放永远覆盖。** 任何改动都必须先
回到这张表。这也是为什么 `binlog_row_image` 必须是 `FULL` —— MINIMAL 下 UPDATE 只
带被改的列,`REPLACE INTO` 会把没带的列写成默认值,悄悄毁掉数据。

## 拒绝优先

本包的第一道关不是拷贝,是**拒绝**。宁可拒绝一个本可以做的,不可放过一个做不干净
的 —— 前者是麻烦,后者是数据不一致。

阶段一落地时的 14 条阻塞项(阶段二起又加了几条,见下一节):

| 类别 | 拒绝原因 |
|---|---|
| 适用范围 | 非 MySQL;非索引变更;MySQL < 8.0.13 |
| 目标表 | 表不存在;无主键且无唯一非空索引;有外键(任一方向);有触发器 |
| 实例参数 | `log_bin=OFF`;`binlog_format≠ROW`;`binlog_row_image≠FULL`;缺 REPLICATION SLAVE / CLIENT |
| 残留 | 上次未清理的 `_gho` / `_del` 表 |
| 容量 | 磁盘余量 < 表大小 × 1.2 |

几条值得单独说的判断:

- **无主键但有唯一非空索引 → 放行。** 分块要的是"稳定、唯一、非空",主键只是最常见
  的那一种。一并拒掉会挡住一批本可以做的表。
- **拿不到磁盘余量 → 不拦。** 把未知当成 0 会拒掉全部变更。
- **外键两个方向都拒。** 指向影子表的约束会跟着 rename 走,指向原表的会在 cut-over
  后指向被弃置的旧表 —— 两个方向都把约束悄悄挪到了错误的对象上。
- **一次报全部问题,不是第一个。** 让人改一条、重试、再发现第二条,在生产上就是三个
  变更窗口。
- **引擎不对就停止后续检查。** 对着一个 PostgreSQL 实例抱怨 binlog 参数毫无意义。

范围刻意窄:**只做加索引 / 删索引**。ADD COLUMN / MODIFY COLUMN 会引入类型转换与
默认值回填的语义问题,不在同一次里搭进来。范围窄不是偷懒,是让"能做的都做对"可验证。

## 阶段二至五落地时定下的几件事

**cut-over 用 8.0.13+ 的"LOCK TABLES 之下 RENAME TABLE",版本下限因此从 5.6 提到 8.0.13。**

```
LOCK TABLES t WRITE, _t_gho WRITE      从这一刻起原表不再有写入
读 binlog head                          锁之前提交的写入都在它之前
在持锁连接上把流重放到 head              影子表被本连接锁着,只有它能写
RENAME TABLE t TO _t_del, _t_gho TO t   原子
UNLOCK TABLES
```

任何一步失败都只需 UNLOCK,改名之前什么都没变;锁连接断开同样等于 UNLOCK。gh-ost
那套哨兵表的五步舞是为了在 5.x 上模拟同样的原子性,多出来的每一步都是一个可能卡在
半路的地方 —— 5.7 已经 EOL,不值得。拿锁超时(默认 3s,它同时是业务写入被挡住的
上限)、持锁后追不平(默认 5s)都放锁重试,默认 10 次。

**拒绝在线加唯一索引。** 看上去只多一个关键字,实际两条写入路径都会静默丢行:
`INSERT IGNORE` 丢掉重复的那一行,`REPLACE INTO` 删掉与之冲突的另一行,都不报错。

**新增的阻塞项:** 非 InnoDB(拷贝靠 `FOR SHARE` 行锁防幽灵行);分块键列类型不适合范围
切分(浮点、ENUM/SET、JSON 等 —— "排序顺序"与"比较顺序"不一致会漏行);有重放无法
原样写回的列类型(空间类型等,白名单之外一律拒);表名超过 59 字符(影子表名超 64);
加索引的索引名已存在 / 列不存在;删的索引不存在、是主键、或是唯一可用的分块键。

**拷贝要加 `FOR SHARE`。** 没有它:拷贝读到一行 → 这一行被删、删除被重放 → 拷贝把读到
的旧值写进影子表,留下一行原表里已不存在的幽灵数据。加了共享锁,删除要么先提交(拷贝
读不到),要么等拷贝提交之后(随后被重放删掉)。

**所有 SQL 走 `SET NAMES binary` + `time_zone='+00:00'` 的专用会话。** 字符串以列自身
字符集的原始字节往返,写回时用 `CONVERT(? USING <列字符集>)` 贴标签,比较键时再加
`COLLATE <列排序规则>` 以走上索引。否则 latin1 列里的 `0xE9` 会被当作 utf8mb4 解释。
这些会话用完**丢弃,不还回连接池** —— 测试里真实踩到过:还回去的连接带着 binary 字符
集,下一个借到它的普通查询读出了一堆原始字节。

**整数键按整数传回。** 以字符串与 BIGINT 比较会被 MySQL 转成 double,超过 2^53 的键
就比不准了。

**Run 自己再跑一遍前置检查,不信任调用方。** 它是唯一的安全阀,不能是可跳过的步骤。

**失败或中止时删掉本次建的影子表;成功后默认保留 `_t_del`。** 前者是半成品,留着只会
让下一次因残留被拒;后者是唯一的回退手段,且大表 DROP 本身有 IO 抖动,由人挑时候删。

**binlog 里出现本表的 DDL 就中止。** 重放按下标对列,结构一变就会错位。行镜像列数与
表列数不符同样中止。

**限流:** `Threads_running` 超阈值时拷贝与重放都停(探测结果缓存一个间隔);人工暂停
同理。复制延迟限流需要连从库,当前没有,留待接入。

## 阶段

| 阶段 | 内容 | 状态 |
|---|---|---|
| 一 | 纯逻辑前置检查 + 事实采集 | **已完成**(`preflight.go` / `gather.go`) |
| 二 | 影子表创建、ALTER 应用、分块拷贝 | **已完成**(`copy.go`) |
| 三 | binlog 订阅与重放 | **已完成**(`apply.go` / `binlog_mysql.go`,go-mysql v1.13.0) |
| 四 | cut-over(持锁改名) | **已完成**(`migrate.go`) |
| 五 | 限流 / 暂停 / 中止 / 进度 | **已完成**(`migrate.go`) |

阶段三(`binlog_mysql.go`)用 `go-mysql/replication` 实现 `Binlog` / `Stream`。定下来的几件事:

- **版本 v1.13.0**:它是最后一个要求 Go 1.23 的版本;更新的版本要求 Go 1.25,会连带抬高整个项目的版本线。
- 解码库的 TIMESTAMP 文本按 **UTC** 格式化(与迁移会话的 time_zone 一致)—— 不设就按网关进程的
  本地时区,测试里实测差出 17 行;DECIMAL 保持解码库默认的文本(`UseDecimal` 关),不经过浮点。
- 涉及本表的**任何**非事务控制语句都置 `Event.DDL`(迁移中止):不只 ALTER,TRUNCATE、按语句格式
  记的 DML 也改了表却没有行镜像。宁可误报(一次中止重来),不可漏报(按错位的列写数据)。
- **读位点用自己的连接**,不与迁移、业务共用池子:cut-over 持着原表的锁读位点,被锁挡住的写入
  占满池子时会互相等死(测试里池子 4 条时真实撞上)。
- 断线不自动续传(`DisableRetrySync`):续上的位点由解码库自己记,无从核对是否漏了事件;断了就
  让迁移失败(它会清理影子表)。
- 以随机的大 server_id 连接,避免与真从库撞号(同号会被库端踢掉)。

产品接入(`.scratch/osc-product`,2026-10-01):生产实例(分层要求 MFA)上、估算 ≥ `osc.minRows`
(默认 100 万)行或 ≥ `osc.minBytes`(默认 1 GB)的表,单个加 / 删索引自动改走在线变更 —— 终端里变成
一张必须审批的「在线变更」工单(通过后执行 = 再查一遍 + 启动迁移),发布流水线里在执行阶段就地迁移
(须有已通过的审批)。任务落 `tbl_osc_job`(迁移 0049),网关重启时进行中的判失败并清理影子表,不续跑。
大表上做不了的 DDL 照原路径并醒目提示;切换后保留的旧表由 DBA 手动删。

## 测试

前置检查是纯函数,不依赖 MySQL,已测透。

**阶段二起必须对着真 MySQL 测** —— 拷贝与重放的交错、cut-over 的锁竞争,拿 sqlite
或 mock 测出来的绿色是假的。`mysql_test.go` 在设置了 `AEGISDB_OSC_TEST_DSN` 时运行
(需要 8.0.13+、ROW binlog、建库与复制权限的账号),每个测试建自己的库:

```
docker run -d --name aegisdb-mysql-osc -e MYSQL_ROOT_PASSWORD=aegisdbosc -p 127.0.0.1:13307:3306 mysql:8.0
AEGISDB_OSC_TEST_DSN='root:aegisdbosc@tcp(127.0.0.1:13307)/' go test ./internal/osc/
```

这些测试里 binlog 流是一个假的解码器(写入方提交后记下解码库会给出的行镜像),其余
—— 拷贝、重放的 SQL、表锁、改名 —— 全部是真的。核心用例在 2 万行上边拷贝边做插入 /
改值 / 改键 / 删除,穿过 cut-over 之后逐行比对,覆盖 utf8mb4、latin1、超 int32 的无符号
整数、DECIMAL、毫秒 DATETIME 与虚拟生成列。

`binlog_mysql_test.go` 是同一组场景换成**真实 binlog**:写入方只执行 SQL,迁移从 binlog 读。
另有一张几乎覆盖全部列类型的表(无符号超 2^63、DECIMAL(30,10)、DATETIME(6)、TIMESTAMP(3)
且全局时区不是 UTC、TIME 负值、YEAR、latin1、emoji、二进制、BLOB、ENUM、SET、BIT、JSON、
虚拟生成列),迁移期间并发改写,同样的写入落一张不迁移的对照表,最后逐列按原始字节比对;
以及迁移期间 TRUNCATE 必须中止并清理。

这一条不是流程要求,是这个特性的前提:一个自己会动数据的工具,没有对着真数据库跑过
的代码路径,等于没写。
