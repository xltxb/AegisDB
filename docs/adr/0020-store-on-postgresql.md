# ADR 0020:网关存储库支持 PostgreSQL,并提供从 MySQL 的停机搬迁

- 状态:已采纳
- 日期:2026-11-17
- 相关:`backend/migrations/pg/`、`backend/internal/storemigrate/`、`backend/internal/bootstrap/pgschema_test.go`、
  `docs/上线部署SOP-存储库搬迁到PG.md`

## 背景

网关自己的存储库(账号、工单、审计、元数据)一直是 MySQL,表结构由 `migrations/*.sql` 手写迁移决定;
dev 与测试跑 SQLite + GORM AutoMigrate,生产迁移从没被测试执行过。用户决定生产存储库换成自建
PostgreSQL 16+,停机一次性搬迁,MySQL 原样保留作回退。审计哈希链能否原样搬过去,2026-11-16 先做了实验
(可以,条件见下)。

## 决定

### 一、PG 表结构是第二套手写迁移,和 MySQL 逐列对齐

- `migrations/pg/0064_baseline.sql` 等价于 MySQL 0001-0064 跑完后的表结构,由 `TestGenPGBaseline`
  从真实 MySQL 生成,不手改。之后每次改表结构,MySQL 与 PG 各写一份、**编号相同**。
- `TestPGSchemaMatchesMySQL` 两边都跑一遍,逐表逐列比类型、可空、默认值、长度、索引。漏写一边会红。
- 不用 GORM AutoMigrate 建 PG 表:模型里有 MySQL 专属类型标签,而且生产表结构不该由模型推断(B6/H13)。

### 二、类型映射保住 MySQL 上的现有行为

| MySQL | PG | 为什么 |
|---|---|---|
| VARCHAR/CHAR/TEXT(全是 `*_ci`) | `citext` + 长度 CHECK | 现有行为不分大小写:邮箱登录、搜索的 LIKE、唯一索引都依赖它。超长在 MySQL 严格模式下是报错,CHECK 保持报错 |
| TINYINT(1) | boolean | GORM 的 bool |
| DATETIME(p) | timestamptz(p) | 审计哈希里的时间带时区偏移;不带时区的 timestamp 读回来偏移变了,审计链第 1 行就断 |
| 自增 id | `GENERATED BY DEFAULT AS IDENTITY` | 搬迁要原样带 id 写入,写完把序列推到 max(id) |

不用 `CHAR(n)` 存哈希:PG 的 CHAR 读回补空格,链头的空前驱会变成 64 个空格。citext 没有这个问题。
需要 PG 13+(citext 是受信扩展,库属主即可创建)。

### 三、运行时代码不分方言

存储库访问几乎全是 GORM。全量回归在 PG 上跑出的不兼容只有三处:两处 MySQL 反引号
(改用 `clause.Eq` / `clause.OrderBy` 让 GORM 按方言引用),一处测试直接调 AutoMigrate。
迁移锁:MySQL 用 `GET_LOCK`,PG 用会话级咨询锁,同样钉在一条专用连接上。

测试:`VELA_TEST_STORE_PG` 设了,整个 bootstrap 套件改跑真 PG(每个测试从迁移+播种好的模板库
`CREATE DATABASE … TEMPLATE` 复制一份)。

### 四、搬迁是网关二进制的子命令 `migrate-store`,停机进行

只读源库,写空的目标库;每张表一条 SELECT 流式 COPY 进 PG;核对行数、与行序无关的逐值内容摘要、
审计链在两边结论一致、源库行数在搬迁期间没变。任何一项不过就不算搬完,退出码 1。

- **时区**:MySQL 的 DATETIME 不带时区,`--tz` 必填。填错时内容摘要两边照样相等(按同一个错时区换算),
  能拦住它的只有审计链,所以源库审计链验不过默认拒绝搬(`--accept-broken-chain` 例外)。
- **防分叉**:搬完在源 MySQL 里建标记表 `vela_store_moved`。网关在 MySQL 上启动(serve / init / migrate)
  见到它就拒绝。起因是升级包会覆盖 `configs/config.yaml`,如果把切换写在那里,下一次升级会悄悄连回旧
  MySQL 继续接写入。所以切换写在 `vela.env`(`VELA_DB_DRIVER=postgres`),标记是第二道保险。
  回退到 MySQL = 有意地删掉这张表。

### 五、不做的

- 不停机的增量同步:用户选了停机一次性拷贝。
- PG → MySQL 的反向搬迁:回退就是切回原样保留的 MySQL,切换后在 PG 上产生的数据需人工补。
- SQLite 仍是 dev 的默认存储库,不变。

## 后果

- 之后每个改表结构的迁移要写两份(MySQL + PG),漂移测试兜底。
- 测试多一种跑法:`VELA_TEST_STORE_MYSQL` + `VELA_TEST_STORE_PG` 设了才跑的那些用例(表结构比对、
  搬迁端到端)平时会跳过,发版前要带上这两个变量跑一遍。
