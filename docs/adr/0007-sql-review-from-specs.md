# ADR 0007:规则库按公司规范重写

- 状态:已采纳
- 日期:2026-08-27
- 相关:`backend/internal/review/`、`docs/MySQL規範.md`、`docs/TIDB規範.md`、
  `docs/Oracle規範.md`、`docs/DWS对象设计和业务开发规范-ABLE.md`

## 背景

规则库原本是 31 条平台自拟的检查项。公司随后把四份数据库规范落到 `docs/` 下,
其中 DWS 那份把条目编成了 `RULE 1..62`,每条标注【Must】/【Should】。

于是规则库和规范成了两套各说各话的东西:一个开发被平台拦下来,看到的是
"禁止 NOT IN (子查询)",无从知道这是公司规定还是平台的个人偏好;而规范里写了
的条目,平台可能根本不查。

## 决定

### 1. 每条规则记下它的**出处**,与它的**强度**分开存

新增两列:

- `spec` —— 规范怎么定性这条要求:`critical`(高危)/ `mandatory`(强制)/
  `recommended`(建议),空 = 规范未覆盖,平台内置。
- `spec_ref` —— 出自哪一条,如 `DWS对象设计和业务开发规范 RULE 13`。

它和已有的 `level`(error 拦发布 / warn 记录放行 / info 提示)**刻意分成两列**:

> level 是这条发现在本平台值多少钱,spec 是规范怎么定性这条要求。
> 运维把某条降成告警是运营决定,不等于改了公司规范;合成一列会让这两件事
> 看起来是一回事。

空出处同样是有意义的信息:库里有 25 条规则是规范没写、平台自带的防护
(MySQL 上的 `SELECT *`、索引数量上限、明文口令等)。标出来,免得有人拿平台的
默认值当规范原文去引用。

### 2. 种子强度照规范定,例外必须写明原因

`高危 / 强制 → error`(规范原文都是"DBA 强制退回 / 需修改后方可上线"),
`建议 → info`。

三条查得出但查不准的刻意压低一档,并在 `builtin.go` 对应条目上写明原因;
`TestSeededLevelsFollowTheStandard` 把这三条登记为白名单,**新增的偏离会当场
失败** —— 免得"压低一档"变成一种随手可用的逃生门:

| 规则 | 规范 | 种子 | 为什么 |
|---|---|---|---|
| `dws.require.col.not.null` | Must (RULE 24) | warn | "明确不存在 NULL 值"是业务判断,语句里读不出来 |
| `dws.replication.confirm` | Must (RULE 12) | warn | 行数与表的角色都不在语句里,只能要求确认 |
| `dws.partition.ttl` | Must (RULE 21) | warn | 有没有 drop partition 的调度不在建表语句里 |

### 3. 存量规则一条不删

规范没覆盖到的现有规则保留,只把出处标空。删掉一道在跑的防护,不该由一份文档的
沉默来决定;而且运维此前对这些规则做过的调整(改级别、改参数、停用)会一并丢失。

### 4. 查得准才查

规范里有相当一部分要求不是单条语句里能读出来的。它们**不做成规则**,也不硬凑
正则 —— 一条老是误报的拦截规则,最后换来的是所有人学会无视整个审查:

| 规范条目 | 为什么没落地 |
|---|---|
| DWS RULE 6 禁用集群默认库 | 哪个是默认库不在语句里 |
| DWS RULE 28 同一含义字段跨表类型一致 | 需要跨语句、跨表的上下文 |
| DWS RULE 32 物化视图刷新频率 ≥3min | 调度配置,不在 SQL 里 |
| DWS RULE 35-37 经 ELB 连接 / 时区一致 / 及时关连接 | 连接层,不在 SQL 里 |
| DWS RULE 40 冲突操作错峰执行 | 时间安排,不在 SQL 里 |
| DWS RULE 41 大批量变更后收集统计信息 | 需要知道实际影响行数 |
| DWS RULE 48 JOIN 字段类型一致 | 需要表结构,单条语句读不出 |
| DWS RULE 57/59 DDL 走审批 / 先测试环境验证 | **这是本平台的发布流水线在做的事**,不是 SQL 检查 |
| DWS RULE 60-62 低谷执行 / 巡检 / 数据倾斜 | 运维动作,不在 SQL 里 |
| MySQL 大表用 gh-ost、TiDB 超百万行表定义归档周期 | 需要知道表的实际大小 |
| 三份规范的"定期备份并验证可用性""所有表设计须经 DBA 审核" | 流程要求,不是语句属性 |

### 5. Oracle 规范目前近乎空文

`docs/Oracle規範.md` 只有章节标题,除 §十 的几段 Online DDL 示例外没有任何
`[強制]`/`[建議]` 条目。因此 Oracle 只派生出一条 `oracle.index.require.online`
(建议级),原有两条 Oracle 规则保持"平台内置"。**这不是遗漏,是原文如此。**

## 结果

规则库 87 条:

| 维度 | 分布 |
|---|---|
| 规范分级 | 高危 4 · 强制 47 · 建议 11 · 平台内置 25 |
| 平台强度 | error 55 · warn 16 · info 16 |
| 方言归属 | 通用 28 · DWS 46 · TiDB 7 · MySQL 3 · Oracle 3 |

**这会明显增加发布单被拦的比例**(error 从 9 条涨到 55 条)。这是照搬规范的
直接后果:规范说【高危】【强制】两级"DBA 强制退回"。每条规则都能在规则库页面
上改级别、改参数或停用,且改过的不会被后续升级覆盖(`SeedSQLReviewRules` 只补
新码,不动已有行)。

## DWS 规范改版的处理

新版 `DWS对象设计和业务开发规范-ABLE.md` 取代了旧的
`Huawei DWS 規範_Data Warehouse Guidelines.md`。规则库跟着改版走:

- **降级**:`dws.require.schema.qualified`、`dws.require.sql.tag` 由【強制】
  变成【Should】(RULE 51 / RULE 56),强度从 error 降为 info。
- **收紧**:JOIN 表数上限 16 → **8**(RULE 52);列存 hstore_opt 由"建议"
  变成**一律强制**且要求 `colversion=3.0`(RULE 11)。
- **下线**:旧版才有的 COUNT(1)、sequence cache >1000、分区名 `p_YYYYMM`、
  行存禁压缩、业务账户权限白名单、时间字段统一命名,随旧版一起删除 ——
  它们不是"存量规则",是上一版规范的派生物,规范改了就不该留着。
- **保留但改标**:"禁止存储敏感字段"在新版里没有了。规则留着(它是一道在跑的
  防护),但出处退回"平台内置"。
