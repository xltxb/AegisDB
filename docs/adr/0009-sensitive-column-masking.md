# ADR 0009:敏感字段脱敏在服务端做

- 状态:已采纳
- 日期:2026-08-28
- 相关:`backend/internal/gateway/sensitive.go`、`internal/service/sensitive.go`、
  `migrations/0027_sensitive_column.sql`

## 为什么必须在服务端

一个"前端负责打码"的设计,等于把敏感数据**完整地发到了浏览器**,再请浏览器不要
显示。抓个包、开个 DevTools 就绕过了,而且在那之前它已经躺在:

- 浏览器缓存与内存
- 沿途任何反向代理 / WAF 的访问日志
- 前端的错误上报(把整个响应体发给第三方是常见做法)

所以脱敏的落点是**结果离开网关之前**:回给浏览器的那个 JSON 里,身份证号已经不在
了。这不是实现偏好,它是这个功能全部的意义 —— 端到端测试因此直接断言**原始响应体
里明文一个字节都不能出现**,而不是断言界面上显示成了星号。

## 落在哪两处

整个网关只有两处把行读出来:

| 出口 | 谁在用 |
|---|---|
| `RealRun` | 终端、异步执行、发布单代执行 |
| `RealQueryEach` | 数据导出(流式) |

脱敏就放在这两处。放在这里而不是让上层各自处理,是为了**新加的调用路径天然被覆盖**
—— 不会有人"忘了加脱敏"。导出那条尤其不能漏:一份 CSV 落到磁盘、发进聊天工具,
比在终端上看一眼跑得远得多。

规则通过 `gateway.SensitiveRulesProvider` 注入(启动时挂一次),而不是一路当参数传:
两个出口有半打调用方,传参意味着每个新调用方都可能忘。

## 怎么判断哪一列该打码

难点只有一个:**结果集只带回列名,不带回它来自哪张表**。而且

```sql
SELECT id_card FROM t_user            -- 列名 id_card,认得出
SELECT id_card AS x FROM t_user       -- 列名 x,按列名匹配就漏了
SELECT SUBSTR(id_card,1,6) AS x       -- 同上
```

所以分两步:

1. **按列名**匹配。`SELECT *` 落在这一步 —— 而且它恰恰是最安全的形态,驱动回传的
   就是真实列名。
2. **按算法**匹配:选择列表第 k 项的表达式里提到了敏感字段,第 k 列就打码。别名与
   函数包装都在这一步兜住。

只看**选择列表**,不看整条语句:`SELECT count(1) FROM t WHERE id_card = ?` 的输出是
个计数,不是敏感数据,把它打码只会让人觉得这道闸没道理。

方向上宁可多打:**多打一列是看不到本可以看的数据,漏打一列是敏感数据直接回传。**

## 它的上限 —— 这一节比上面都重要

**这道闸防的是"顺手看到",不是防外泄。**

一个铁了心要拿数据的人总能构造出映射不回去的表达式,最简单的一种是经子查询再套一层
别名:

```sql
SELECT x FROM (SELECT id_card AS x FROM t_user) s   -- 外层选择列表里没有 id_card
```

要堵死它,就得做完整的 SQL 语义分析并跟踪列的血缘 —— 那是一个真正的 SQL 解析器的
工作量,而且每个方言都要单独做对,做错的方向是"以为打了码其实没打",比现在更危险。

**真正的边界是不给这张表的访问权限。** 标签(tags)与角色才是那道墙,这里只是让日常
查询不至于把身份证号刷在屏幕上、写进导出文件里。把它当成外泄防线来依赖,是这套机制
唯一的误用方式。

## 几个具体决定

| 决定 | 为什么 |
|---|---|
| 空值保持空,不打成 `***` | 把 NULL 打成星号会让人以为那里本来有数据 |
| 短值(≤8 字符)整体抹掉 | 一个 4 位数留头留尾等于没打 |
| `hash` 模式同值同码 | 能核对"是不是同一个人",看不出是谁 —— 对账场景需要它 |
| 表名留空存成 `*` | 让"所有表"在列表里显式可见,而不是一个看不出含义的空格 |
| 规则缓存 5 秒,且挂在 Services 实例上 | 短到"加完规则去试一下"就已经生效;挂实例而非包级变量,否则多个 Services 之间会串味,而"有时候用的是别人的规则"的脱敏比没有还危险 |
| 读库失败时沿用上一次的规则,不返回空 | 空意味着"什么都不脱敏",一次数据库抖动就会让敏感数据明文回传 |
| 停用/删除都写审计 | 这两个动作会让某字段**从此明文回传**,是需要事后能追的 |
| 读接口不限管理员 | 被脱敏的列是一串星号,"为什么这列看不到"必须有个自己查得到的答案 |

## 没有做的:按角色豁免

DBA 有时确实需要看到原值。当前实现**对所有人一视同仁**,包括管理员 —— 要看原值,
只能先停用规则(会写审计)。

没做豁免是因为它需要先回答一个更难的问题:豁免记不记审计、豁免是按角色还是按人、
临时豁免要不要审批。在那之前,一个"管理员自动看到明文"的口子会让这道闸在最需要它的
场景下形同虚设 —— 而多数泄露正是发生在有权限的人手上。

## 补充(2026-09-02):导出要原值,得有人签字

上面「没有做的:按角色豁免」那一节说过,当时对所有人一视同仁,要看原值只能停用规则
(会写审计)。现在多了一条**按次授权**的路,专门给导出。

导出确实存在需要原值的场景 —— 对账、迁移、监管调取。但它也是这套机制里最要紧的
一路:一份带身份证号的 CSV 落到磁盘、发进聊天工具,比在终端上看一眼跑得远得多。所以
放开它既不能靠"停用规则"(那是全局的、影响所有人所有查询),也不能靠自己勾一个开关。

**做法:勾了「包含敏感字段」的导出任务不进队列,停在 `awaiting` 等审批,批准之后才由
worker 后台执行。**

| 关节 | 怎么守 |
|---|---|
| 默认脱敏 | 不变。`RealQueryEach` 照旧逐行打码 |
| 唯一旁路 | `RealQueryEachRaw` —— 名字刻意刺眼。不在 `RealQueryEach` 上加一个默认 false 的参数,那会让"这一次到底脱没脱敏"藏在一个布尔值里 |
| 不进队列 | 任务建成 `awaiting`;而 `ClaimExportJob` 只认 `pending`,所以即便有人把这个 id 塞进队列,worker 也拿不到它 |
| 不能手动执行 | 审批单带 `ExportJobID`,与 `ReleaseID` 一样把它挡在发起人手动执行那条路之外 —— 导出单的 command 是一句描述,放它过去网关会把描述当命令发给数据库 |
| 放行前复核 | worker 在**放行原值的那一刻**再核一次审批状态 |
| 不会放行两次 | `SetExportStatus` 的条件里带当前状态,同一张单被处理两次只有一次能改动那一行 —— 否则会产出两份带原值的归档,而人只知道有一份 |

最后那道复核是重复的,**故意的**。这类旁路最常见的失效方式不是逻辑写错,是后来有人
加了一条新路径、忘了先检查。把检查放在放行的那一刻,新路径就绕不过去。

审批单按**高危**记。它不改任何数据,但风险等级衡量的是后果,而这一条的后果是明文 PII
落到一个网关再也管不到的地方。

界面上那句提示要把"勾了就不会马上跑"说在前面 —— 否则人以为点了导出就在跑,而任务
停在待审批,他等在下载那一栏。
