# ADR 0017:收单检查 —— 语法交给数据库,对象缓存优先

- 状态:已采纳
- 日期:2026-09-11
- 相关:`backend/internal/gateway/precheck.go`、`backend/internal/service/precheck.go`、
  `backend/internal/gateway/probe.go`、`backend/pkg/sqlutil/refs.go`、
  `backend/pkg/sqlutil/alter.go`、`migrations/0036_release_precheck.sql`、
  ADR 0005(发布流水线与规范审查)、ADR 0006(开放接口)、ADR 0008(引擎语法边界)

## 背景

发布单收进来的是一段 SQL,而在此之前,网关对它只做两件事:**判定**(危不危险、要不要
审批)和**规范审查**(有没有主键、有没有注释)。两件都不回答最朴素的那个问题:

> 这段 SQL 在目标库上跑得起来吗?

跑不起来的变更会一路走到执行阶段才失败 —— 那时它可能已经过了一次人工审批,而提单的
CI 早在几小时前就拿着一个 200 走了。

## 决定

### 一、语法由**目标库**判,平台不解析

ADR 0008 的立场不变:网关不做完整 SQL 解析,也不该做。而"这条语句语法对不对"恰恰是
最不需要平台判断的问题 —— `EXPLAIN`(不带 ANALYZE)只生成计划、不执行语句,而生成计划
就必须把表和列解析出来。所以它同时校验了语法**和**引用的对象,给出的还是**那台库、
那个版本**的真实答案。

动词限定在 `SELECT / INSERT / UPDATE / DELETE`。这个集合窄是有意的:它们在
MySQL 5.6+ / PostgreSQL / SQLite 上都支持 EXPLAIN。再宽一点就会遇到"这个引擎的
EXPLAIN 不支持这种语句"的报错,而那句报错和"你的语句语法错了"在文本上分不开 ——
把前者报成后者,就是拿一个假的语法错误去拦一条正确的变更。

### 二、DDL 不做语法检查,并且**明确说没做**

| 引擎 | 能不能"只解析不执行" | 为什么 |
|---|---|---|
| MySQL / Oracle | **不能** | DDL 隐式提交,任何"试一下"都等于真的执行 |
| PostgreSQL / DWS | 技术上能(事务里回滚) | 但会对目标表加 ACCESS EXCLUSIVE 锁,繁忙的生产表上哪怕最后回滚也可能短暂阻塞线上查询 |

所以一律不做。**把没做的检查报成通过,比不检查糟得多** —— 它让人以为这条 DDL 已经被
验过了。结果里 `skipped` 是一等结论,和 `error` 一样要显示出来;`syntaxChecked` 与
`syntaxSkipped` 必须同时给,只给"0 个语法错"会被读成"每条都验过了"。

### 三、对象检查缓存优先,但每条结论都带来源

取数顺序是:这台实例有元数据缓存就用缓存,一条都没有才当场查目标库。这是明确的产品
选择(少打扰生产),代价是**同一个检查有两种准确度**。

代价不能靠沉默消化。所以:

- 整份结果有 `objectSource`(`cache` / `live` / `none`);
- 缓存时附 `cacheSyncedAt`,界面直说"缓存之后建的对象会被报成不存在";
- 每一条对象结论自带 `source`。

`none` 是独立的一档:**"没能核对"和"核对过、都在"是两回事**,页面上必须分开说。

这件事与"缓存是只读副本、不用于判定"的既有立场并不冲突 —— 前提是**检查不拦发布**
(见第五条)。一旦它开始拦,这份可能过期的数据就变成了判定依据。

### 四、引用提取是关键字锚定,认不出就说认不出

`pkg/sqlutil/refs.go` 只认几个关键字后面跟着的那个名字,不是解析器。子查询、CTE、
表值函数一律标成"未识别"而不是猜一个名字。

理由是**认错的方向**:一句"表 t_order 不存在"会让人去建表、或者以为发布环境配错了;
一句"这条语句的引用对象没能识别"只是让人自己看一眼。前者在认错时会让人做出错误的
动作,后者不会。漏认一条语句只是少一次检查,没有人会因此做错事。

同一批脚本里 `CREATE TABLE t` 之后的语句引用 `t` 不算缺失 —— 不区分"要求存在"和
"本次创建",每一份建表脚本都会挂一串假红。

### 四之二、字段与约束:字段一律实时查,数据探测带护栏

表一级的检查可以用缓存,字段一级不行 —— **字段比建表变得频繁得多**,一份昨天的缓存会把
昨天刚加的列报成"不存在",而那句话会让人去改一个本来正确的脚本。所以 `ALTER TABLE` 的
目标表,列信息一律当场查(一次取回这批脚本涉及的所有表,不是一条语句问一次)。

「数据违反约束」则连结构都不够,它要读**数据**:

| 形状 | 探测 | 不探会怎样 |
|---|---|---|
| `ADD COLUMN c T NOT NULL`(无默认值) | 表里有没有行 | 表非空时必然失败 |
| `MODIFY/ALTER … SET NOT NULL` | 该列有没有 NULL | 有一个就失败 |
| `ADD UNIQUE (c…)` | 这几列有没有重复值 | 有一组就失败 |

这三条跑在生产库上,所以每条都受护栏约束:

- **只对有风险的形状跑。** 普通索引、放松约束、改类型宽窄一律不跑 —— 最后一个不是
  懒,是"会不会超长"没法用一条便宜的探测回答。
- **用 EXISTS 不用 COUNT。** 要回答的是"会不会",不是"有多少";命中一行就停。
- **10 秒超时,每单最多 20 次探测。** 超时如实报「未能核对」,不报通过。
- **标识符白名单。** 表名列名来自用户提交的 SQL,拼进探测语句就是一条注入面。这里不做
  "转义得足够好",而是**不合规就不探**:名字里只允许字母数字下划线 `$` 和点。中文表名
  因此探不了 —— 那是有意放弃的一点覆盖率,换来"拼不出注入"不依赖任何转义逻辑。

`ALTER` 的形状识别同样保守(`pkg/sqlutil/alter.go`):外键、CHECK、分区、`IF NOT EXISTS`
的幂等写法一律不认,而且**一条 ALTER 里只要有一个子句认不出就整条不认** —— 子句是一起
成败的,报一半结论会让人以为另一半没问题。

### 五、检查**不拦发布**

结果随响应返回、并落在发布单上;卡不卡由发布流程的阶段决定。

理由就是上面三条的总和:语法检查覆盖不到 DDL,对象检查可能基于过期的缓存,引用提取
会有认不出的形状。**拿一个覆盖不全、可能过期的结论去拦正常变更,比不检查更糟。**

`errors > 0` 的单子照样是 `pending`。调用方要不要据此让流水线变红,是调用方的决定。

### 六、结果存在单子上

提单的是 CI,后面看这张单的是审批的人、执行的人、出事回头查的人 —— 只在响应里,这几个
人一个都看不到。也不能等发布跑到某个阶段再算一遍:检查说的是"收单那一刻目标库长什么
样",而发布可能几小时后才执行。

对外(开放接口)是一份独立的结构 `dto.OpenPrecheck`,不是内部那串 JSON:对接方的契约
不该跟着内部存储变(与 `OpenReleaseResp` 同一个理由)。

## 代价与欠账

- **收单会连一次目标库。** DML 的每条 EXPLAIN 都是一次往返(上限 50 条),对象检查在
  没有缓存时也要查一次字典。收单是同步的,这些时间都加在提单方的等待上。
- **只有 SQLite 上真跑过。** 测试用真实 SQLite 库验证了整条路径 —— 而且那三种约束失败
  在 SQLite 上是**真会发生**的(加非空列、唯一约束撞重复、删不存在的列),所以验的不是
  "判断逻辑自洽",是"这条语句真的会失败,而我们在收单时就说出来了"。MySQL / PostgreSQL /
  Oracle 上的行为仍然没有在真机验证过 —— 与 issue 24 同一笔欠账。
- **结论文案是服务端拼的中文。** 与终端那一批(`outText.*`)是同一类问题:英文界面上
  这些句子仍然是中文。数据库原话本来就是英文,不受影响;对象与约束那几句需要按
  `RuleRef` / `OutputRef` 的做法改成 code + args 由前端渲染。尚未做。
- **Oracle 完全没有语法检查。** 不是漏了,是 `EXPLAIN PLAN` 要写 `PLAN_TABLE`,而
  `DBMS_SQL.PARSE` 在 Oracle 上对 DDL 就是执行。结果里会如实说明。
