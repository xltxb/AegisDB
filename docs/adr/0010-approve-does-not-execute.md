# ADR 0010:审批通过不再代执行,由发起人自己执行

- 状态:已采纳
- 日期:2026-09-01
- 相关:`backend/internal/service/approval_execute.go`、`internal/service/gateway.go`
  (`finalizeApproval`)、`migrations/0028_approval_executed_at.sql`

## 变更

终端里被拦下来的命令,原先是**审批人一点通过,网关就代替发起人把它跑了**。现在拆成
两步:

```
通过  →  通知发起人  →  发起人自己执行(POST /approvals/{id}/execute)
```

升级单不受影响 —— 它早就不是"批了就跑":流水线的执行阶段拥有执行,审批只是授权。
这次是把终端工单也对齐到同一个模型上。

## 为什么

两条,第二条更根本。

**执行时机不是审批人的信息。** 业务低峰、应用是否已停、备份是否就绪、灰度批次跑到
哪 —— 这些只有发起人知道。审批人按下的是"我同意",把它当成"现在就跑",等于让一个
不掌握这些信息的人替另一个人选了时机。

**没有人在看着它。** 一条 DROP 在半夜被批准并执行,发起人不在现场。出了事,发现得
比谁都晚 —— 而 DDL 恰恰是最需要有人盯着回滚窗口的那一类。

## 四条边界

| 边界 | 为什么 |
|---|---|
| 执行的人必须**自己就能在那台实例上跑这条命令** | 见文末修订:这一格原先写的是「只有发起人能执行」 |
| 一张工单只能执行**一次** | 批准是对**一次**执行的授权,不是一张可反复使用的通行证 |
| 发布单的工单走不了这条路 | 它的执行归流水线;插队执行会把同一变更应用两次 —— 一次在这里,一次在还以为自己没跑过的流水线里 |
| 下发前**再判一次**规则 | 工单可能在待执行状态里放了很久,期间字典、实例归属、发起人的角色都可能变。只在结论变成"拒绝"时拦下:命中"需审批"是正常的,这张工单正是那次审批的结果 |

"只执行一次"靠一行 SQL 顶住:`UPDATE … WHERE id=? AND status='approved' AND
executed_at IS NULL`。并发的两个请求只有一个能改动那一行,另一个拿到 0 行受影响,
于是知道自己来晚了。

占位在执行**之前**,而且失败也不退回。执行失败时命令到底跑没跑是不确定的(连接在
语句中途断开是最常见的一种),退回让人重试就可能把变更应用两次 —— 这与发布流水线在
网关重启时把 `running` 判失败、不重跑,是同一条理由。

## 界面上必须说清"还没跑"

改完之后最大的风险不是技术上的,是**话说得不清楚**:一句"审批已通过"会让人以为事情
办完了,然后那条命令一直挂在那里,直到有人发现变更根本没生效。

所以通知的正文是"请到「审批」页找到这张工单并执行",详情页的落款是"已通过 · 等待
发起人执行",而提交时的说明也改了口径 —— 原先它承诺"通过后由网关代执行"。

按钮亮不亮由服务端的 `canExecute` 决定(`CanExecuteApproved`),前端不自己去拼
`status` / `executedAt` / 是不是发起人这三件事:两份判断迟早会不一致,而不一致的
样子就是一个亮着却点不动的按钮 —— 这个坑在 `canDecide` 上已经踩过一次。

## 已知的口子:批准后的窗口没有到期

一张已批准、未执行的工单**目前永不过期**。这是这次拆分引入的:原先"批了就跑",
批准与执行之间没有窗口;现在有了,而且没有上界。

一条上周批准的 DDL,今天执行时环境可能已经完全不同。下发前的重判挡住了"规则变严"
这一路(现在被禁止就拒绝执行),但挡不住"当时的判断依据已经不成立"——比如表结构
变了、数据量涨了一个量级。

没有现在就做,是因为到期时长该是多久、到期后是作废还是要求重新审批、快到期要不要
提醒,这几个问题的答案取决于实际用起来之后的节奏。**在那之前,这一条是明知的欠账,
不是被忽略的疏漏。**

## 修订(2026-09-09):执行权从「只有发起人」放开到「能在这台实例执行的人」

原来的规则是**只有发起人能按下那一下**,理由写在上面:执行时机(业务低峰、应用是否
已停、备份是否就绪)只有他知道。

现实推翻了它的一半。变更常常在凌晨批下来,而发起人已经下班;值班的同事接不了手,
于是这张单要么干等到第二天,要么**有人拿发起人的账号去跑** —— 后者比放开更糟:审计
里记下的是一个并没有真的按下按钮的人。

所以改成:**谁本来就能在这台实例上跑这条命令,谁就能执行它。**

要紧的是这句话没有放松任何一道闸。执行路径上的每一道**在放开之前就已经**按实际按下
按钮的人(actor)算,而不是按发起人 —— 所以这次放开的确实只有「必须是发起人」这一条:

| 闸 | 按谁算 |
|---|---|
| 标签授权 `canAccessConn` | actor。够不到那台实例的人执行不了,**列表里也看不到那张单**(工单带着完整 SQL,只挡执行同样是泄露) |
| 生产步进验证 `checkMFA` | actor 自己的 TOTP |
| 能力矩阵复判 `EvaluateFor` | actor 的角色。只读角色不会因为单子批过就能删生产表 |
| 一次性闸 `ClaimApprovalExecution` | 与谁无关:一张单仍然只跑一次 |

列表可见性跟着放开了一类:**已批准、尚未执行、且落在你够得到的实例上**的工单。
它在 SQL 里按 `connection_id` 收口,而不是取回来再在应用层筛 —— 后者会让分页的总数
和实际行数对不上,而那种列表会对着躺在第三页的工单说「没有」。

别人替你跑了,发起人会收到站内通知。审计里一直记着实际执行人,但没有人会天天去翻
审计,而「我的变更什么时候生效的」是他一定会问的问题。

**一个被这次放开牺牲掉的性质**:审批人现在也可以执行他自己批过的单 —— 他确实是「能
在这台实例上执行的人」之一。于是「批的人」和「跑的人」不再必然是两个人。要保留那条
两人控制,只需在 `canExecuteApproved` 里再加一条「决定过这张单的人不能执行」;这里
没有加,是因为需求要的是「值班的人能接手」,而值班的人常常正是审批人。
