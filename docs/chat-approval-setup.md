# 聊天审批卡片接入（Lark / 飞书、Telegram）

审批人在 Lark（飞书）或 Telegram 里私聊收到审批卡片，直接点通过或拒绝。两个渠道各自开关，可以只开一个，也可以都开
（两边都绑定的人两边都收到）。规则与站内审批完全一致，走同一个决定核心；
**通过不等于执行**（ADR 0010），卡片上不能执行命令。设计与取舍见
`docs/adr/0021-chat-approval-cards.md`。

> **还没有用真实的 Lark 应用、真实的 Telegram 机器人验证过。** 本文的平台侧步骤来自官方文档与代码，标「未验证」的
> 尤其要先用测试应用 / 测试机器人走一遍。Lark 国际版（larksuite.com）整体未验证。

## 一、前提

- 网关主动连出去，不需要公网入口、域名、证书，但要能访问外网：
  - Lark 国内版：`https://open.feishu.cn`，以及长连接 `wss://*.feishu.cn`；
  - Lark 国际版：`https://open.larksuite.com`，以及 `wss://*.larksuite.com`（这个域名是假设，未验证）；
  - Telegram：只有 `https://api.telegram.org`（443），可以经代理（第五节）。
- 两个渠道都**不看** `HTTP_PROXY` / `HTTPS_PROXY`。只能经代理出网的部署用不了 Lark；Telegram 在设置里单独填代理。
- Lark 只支持**企业自建应用**（飞书的长连接不支持商店应用）。
- **每个环境一个应用 / 一个机器人**，不能共用。同一个环境也只能跑一个网关实例。
  - Lark：飞书的长连接是集群模式、不广播：同一个应用有两处连着时，每条消息只随机送给其中一处 —— 绑定码会报
    无效，卡片上的点击会回「这个聊天账号没有绑定网关账号」（在另一处也绑过的人则是「卡片已失效」）。两处都显示
    「已连接」，**不会报冲突**（见第七节）。
  - Telegram：同一个机器人有两处在收，平台会让其中一处出错（409），那一处的状态显示**冲突**。网关退避重试，
    不抢也不放弃，所以两处会轮流收到消息，现象同上，状态可能在「已连接」与「冲突」之间来回变。

## 二、Lark：建应用

1. 在飞书开放平台（国际版是 Lark Developer）新建**企业自建应用**，记下 App ID 与 App Secret。
2. 【应用能力】里添加**机器人**能力。
3. 【权限管理】里开通：

   | 用途 | 权限 | 说明 |
   |---|---|---|
   | 发卡片、回复绑定结果 | `im:message:send_as_bot` | 官方文档：`im:message`、`im:message:send_as_bot`、`im:message:send` 任一即可 |
   | 更新已发出的卡片 | 同上 | 官方文档：`im:message`、`im:message:send_as_bot`、`im:message:update` 任一即可 |
   | 收用户私聊发来的绑定码 | `im:message.p2p_msg:readonly` | 不要开群消息的权限，网关不处理群消息 |
   | 收卡片点击 | 无需权限 | 官方文档：订阅 `card.action.trigger` 不要权限 |

   网关不读通讯录，不需要 `contact:*`。这一组权限在真实应用上是否够用：未验证。
4. 【版本管理与发布】里把**可用范围**设为包含全部审批人，否则给范围外的人发消息会报 `230013`。

先不要配事件订阅：开放平台要求**长连接已经连上**才能把订阅方式存成「长连接」，所以先做第三节。

## 三、Lark：在网关里配置

【管理后台 · 系统设置 · 审批】的「审批机器人」：

1. 打开「Lark（飞书）审批机器人」，选区域，填 App ID 与 App Secret，点页面底部的**保存设置**。
   缺任何一项，整次保存会被拒绝。
2. 数秒内「连接状态」应变成**已连接**，不用重启。状态与测试卡片用的是已保存的配置。
3. 【系统设置 · 通知】里的「控制台地址」决定卡片上有没有「查看详情」按钮（两个渠道都是）。
4. 「卡片语言」对两个渠道、所有人生效，默认中文。

| 设置键 | 默认 | 说明 |
|---|---|---|
| `chat.cardLang` | `zh` | `zh` / `en`，两个渠道共用 |
| `chat.lark.enabled` | `false` | |
| `chat.lark.region` | `feishu` | `feishu` 国内版 / `lark` 国际版（未验证） |
| `chat.lark.appId` | 空 | 换了应用，所有旧绑定失效，要重新绑定 |
| `chat.lark.appSecret` | 空 | 加密存；不回显，留空 = 不改，「清除」= 删掉。开着时不能清除 |

## 四、Lark：订阅事件与回调，发布

状态「已连接」之后，回到开放平台的【事件与回调】：

1. **事件配置**：订阅方式选「使用长连接接收事件」，添加 `im.message.receive_v1`（接收消息）。
2. **回调配置**：订阅方式选「使用长连接接收回调」，添加 `card.action.trigger`（卡片回传交互）。
3. 只订阅这两个。多订的事件网关不认，平台会当失败反复重推。
4. 【版本管理与发布】创建版本并发布，管理员审核通过后权限与订阅才生效。之后改权限、订阅、可用范围都要
   再发一版。

## 五、Telegram：建机器人与配置

1. 在 Telegram 里找 [@BotFather](https://t.me/BotFather)（认准蓝色认证标记），发 `/newbot`，按提示起显示名与用户名
   （以 `bot` 结尾），拿到**令牌**，形如 `123456789:AA…`。令牌等于机器人本身：不要发进群、工单、截图；泄露了用
   `/revoke` 换一个，重新填进设置。同一个机器人换令牌，绑定不受影响。
2. 用 `/setjoingroups` 关掉进群。网关不处理群里的消息与点击。群隐私模式（`/setprivacy`）保持默认即可。
3. 不要给这个机器人设 webhook，也不要在别处用同一个令牌跑 `getUpdates`。设过 webhook 的要**由管理员自己**在原来用它的地方
   删掉（Bot API 的 `deleteWebhook`）；网关只报错，不替人删 —— 删了会弄断别人的服务。
4. 【管理后台 · 系统设置 · 审批】的「审批机器人」：打开「Telegram 审批机器人」，填 Bot Token，需要时填代理地址，点页面
   底部的**保存设置**。缺令牌或格式不对，整次保存会被拒绝。
5. 数秒内「连接状态」应变成**已连接**，不用重启。

| 设置键 | 默认 | 说明 |
|---|---|---|
| `chat.telegram.enabled` | `false` | |
| `chat.telegram.botToken` | 空 | 加密存；不回显，留空 = 不改，「清除」= 删掉，开着时不能清除。换成**另一个**机器人，旧绑定全部失效，要重新绑定 |
| `chat.telegram.includeSql` | `false` | 卡片带 SQL。见下 |
| `chat.telegram.proxyToken` | 空 | 代理地址，可能带口令，所以按密钥处理：加密存、不回显、留空 = 不改、「清除」= 改成直连 |

**带 SQL。** 默认关着：卡片上只有单号、类型、实例、环境、风险、发起人（在线变更单另有执行方式，执行窗口单另有窗口名与
时间段，敏感导出单另有「原值 / 按脱敏导出」），没有语句、原因、库名、判定分层、系统提示、发布单的标题与正文，并写明
「卡片未显示全文」，但仍能直接通过。打开之后这些都会带上，**语句会发到 Telegram 的服务器并留在那里**（口令先打码）。
这个开关只影响之后发的卡片，已发出的不会补上、也不会抹掉语句。

**代理。** 只收 `http://`、`https://`、`socks5://`（不收 `socks5h`：域名本来就交给代理解析），可以写成
`socks5://用户:口令@主机:端口`，可以在内网。代理要允许连到 `api.telegram.org:443`。配了代理时网关只拨代理。真实的代理只用
本地的 HTTP CONNECT 与 SOCKS5 桩验证过，`https://` 代理与 SOCKS5 口令未验证。

**连通性。** 先在网关那台机器上试（地址里不要带令牌）：

```
curl -sS -o /dev/null -w '%{http_code}\n' https://api.telegram.org/
curl -sS -o /dev/null -w '%{http_code}\n' -x socks5h://10.0.0.9:1080 https://api.telegram.org/   # 经代理
```

回出任何一个 HTTP 状态码（不是 `000`）就算通。

## 六、绑定与验证

没绑定的人收不到卡片，照常在站内审批。网关不按邮箱自动匹配聊天账号。两个渠道各绑各的。

1. 每个审批人点头像打开用户菜单 →「审批机器人」（没有任何渠道开着时不显示）→「生成绑定码」。启用了 MFA
   的账号先要输入 MFA 验证码。
2. 把码交给机器人：
   - Lark：找到这个应用的机器人，**私聊**把码发过去。
   - Telegram：打开弹窗里的 `https://t.me/<机器人>?start=<码>` 链接，点「开始」(Start)；或者找到机器人，私聊把码发过去
     （弹窗里没有链接时也是这样）。

   码 10 分钟内有效、只能用一次，重新生成则旧码作废。发到群里不处理。同一个聊天账号 15 分钟内输错 10 次，锁 15 分钟；
   每人 15 分钟内最多生成 10 次码。
3. 机器人回「已绑定」，弹窗自动变成「已绑定」，本人收到一条站内通知，审计里记一条 `chat.bind`。机器人的回话是尽力而为，
   以弹窗为准。
4. 管理员在设置页点「发测试卡片给我」（自己要先绑定），到聊天里点卡片上的按钮，应提示「测试成功」。
   测试卡片不碰任何审批单。
5. 用一张不要紧的单子走一遍真的：
   - Lark：**通过**（有确认框）与**拒绝**（填一个原因）都要点到。拒绝按钮是表单提交，表单回调的确切内容没有在真实客户端
     上验证过，请确认审批页上看得到「拒绝原因」和「经 Lark 审批」。
   - Telegram：**通过**点两步，先「通过」，按钮换成「确认通过 / 返回」，点「确认通过」才算数。**拒绝点一下就决定**，没有
     二次确认，也填不了原因。审批页上应看到「经 Telegram 审批」。

解绑：

- 本人在同一个弹窗里点「解绑」；管理员在【权限 · 用户】的用户弹窗里点「解除聊天绑定」。
- 停用账号、改 / 重置口令、管理员重置或代绑 MFA 会**自动解绑**。本人自己开关 MFA 不会。
- **只用 SSO 登录的人**在公司侧被停用后，网关里不停用，他的聊天绑定仍然有效。离职要在网关里停用账号。

卡片规则：

- 发给审批链上每个已绑定的人；发起人自己在链上、而没开自审批时不发给他。四类单子都发：高危命令、发布、
  执行窗口、敏感导出。绑定之前、渠道开启之前建的单不补发。
- 卡片放不下全文、或单子本身只存了节选时，卡片正文和通过的确认框里都会写「未显示全文」，但仍能直接通过。
- 任何一个人处理之后，别人手里的卡片在数秒内更新成结论、按钮消失。Telegram 上刚点过「通过」或「返回」的那张，要等那次
  应答落定，最多晚约 20 秒；这期间再点也只会提示已处理并当场更新。
- Telegram 的卡片不许转发、不许保存。
- 群机器人 Webhook 通知（【系统设置 · 通知】）是另一回事，照旧。

## 七、排查

先看【系统设置 · 审批】里的连接状态。Lark 的「已连接」只说明长连接是通的，不代表权限与订阅都配好了。

| 状态 | 原因与处理 |
|---|---|
| 未开启 | 开关没开，或没保存 |
| 连接中 | 正在连。后面若带着一句原因，是上一次断开的原因，连上就消失 |
| 出错（任何原因） | 断开之后等着重连的时候也显示它（等待逐次加长，上限 60 秒；Telegram 要求放慢时按它说的等，最多 5 分钟），会自己恢复；一直不恢复才是故障，原因见下面几行 |
| 出错：没有填写 App ID 或 App Secret | 有人直接改了库。补上并保存 |
| 出错：没有填写 Bot Token；Bot Token 或代理地址的格式不对 | 有人直接改了库。重新填写并保存 |
| 出错：密钥无法解密 | `AEGISDB_SECRET_KEY` 变了。重新填 App Secret / Bot Token / 代理地址并保存 |
| 出错：`lark: connection: …` | 平台的原话。App ID / App Secret 不对、区域选错、应用不是企业自建应用、网络不通（不走代理）都在这里 |
| 出错：`websocket endpoint … is not allowed` | 平台给的长连接域名不在预期之内，最可能出现在国际版。把报的域名反馈给开发 |
| 出错：机器人令牌无效或已被撤销 | 令牌填错，或在 BotFather 里 `/revoke`、删了机器人。重新填令牌并保存 |
| 出错：这个机器人设置了 webhook | 网关收不到消息。管理员在原来用它的地方删掉 webhook（第五节），之后最多一分钟自动连上 |
| 出错：`telegram: getMe: …` / `telegram: getUpdates: …` | 平台或网络的原话：连不上 `api.telegram.org`、被防火墙拦了、平台限流（`code 429`） |
| 出错：`telegram: … via proxy: …` | 经代理没通。只说是哪一种（`connection refused`、`timed out`、`proxy host lookup failed`、`the proxy answered HTTP 407` 等），不带代理地址，也不带代理的原话 |
| 冲突（Lark） | 这个应用的长连接数超限（飞书每个应用最多 50 条），多半有别处也在用同一个应用。**只有两三处共用时不会显示冲突** |
| 冲突（Telegram） | 别处也在用同一个机器人收消息（另一个环境、另一个网关实例、别的程序）。停掉那一处，之后最多一分钟自动恢复；停不掉、或不知道是谁在用（当令牌泄露处理）就 `/revoke` 换令牌 |

| 现象 | 原因与处理 |
|---|---|
| 已连接，机器人不回绑定码（Telegram） | 先看弹窗：已变成「已绑定」就是绑上了，只是那句话没送到（第八节）。没变：发到了群里，或同一个机器人在别处也有人在收 |
| 已连接，机器人不回绑定码（Lark） | 没订阅 `im.message.receive_v1`、没开 `im:message.p2p_msg:readonly`、改完没发版本、发到了群里，或同一个应用在别处也连着 |
| 绑定码总说无效 | 过了 10 分钟、重新生成过，或消息被另一处网关收走了。网关刚重启过、弹窗已是「已绑定」的，是同一条消息被处理了第二遍 |
| 生成绑定码报「审批机器人还没连上」 | 机器人还没认出自己：刚保存、令牌被撤销、挂着 webhook、连不上平台。看连接状态 |
| 绑过的人忽然都显示「未绑定」 | 换了应用 / 机器人；或 Telegram 的令牌失效、挂着 webhook —— 恢复之后绑定还在 |
| 点按钮没反应或报错（Telegram） | 渠道关了或正断着（这期间的点击恢复后会补处理，平台最多存 24 小时）；这张卡片是换机器人之前的旧机器人发的 |
| 点按钮没反应或报错（Lark） | 没订阅 `card.action.trigger`，或订阅方式不是长连接；渠道关了或正断着；这张卡片是换应用之前的旧应用发的 |
| 点按钮提示「这个聊天账号没有绑定网关账号」 | 已经解绑（本人、管理员，或停用账号、改口令等自动解绑），或点击被另一处用同一个应用的网关收走了 |
| 点按钮提示「卡片已失效」 | 点的人不是这张卡片的收件人；发送超时重试之前的那一张（见第八节）；或点击被另一处网关收走，而他在那边也绑过 |
| 点按钮提示「正在处理」 | 网关 2.5 秒内没处理完。稍后看卡片上的结论，或到站内看；没办成的，机器人会另发一句说原因 —— 这句尽力而为，只发一次，平台限流、正忙或发送失败就没有。以卡片上的结论和站内为准 |
| 测试卡片报 `code 230006` | 没开机器人能力，或开了没发版本 |
| 测试卡片报 `code 230013` | 这个人不在应用的可用范围内 |
| 测试卡片报 `code 230027` | 缺权限，或开了没发版本 |
| 测试卡片报 `code 403` | 这个人在 Telegram 里屏蔽了机器人，或删了账号。解除屏蔽后再试 |
| Telegram 卡片上没有「查看详情」 | 没配控制台地址；或平台不认这个地址（内网主机名这类），网关去掉它照发 |
| 审批人没收到卡片 | 没绑定；绑定之后换过应用 / 机器人；在 Telegram 里屏蔽了机器人；账号停用；本人是发起人。仍不明的看库里 `tbl_chat_card` 那一行的 `state` 与 `last_error` |
| 菜单里没有「审批机器人」 | 没有开着的渠道；渠道开着但配置有问题（缺 App ID / App Secret / Bot Token、密钥无法解密）；或这一次读绑定状态失败，关掉菜单再打开 |

日志里不会有 App Secret、机器人令牌、代理地址、卡片令牌、长连接票据。每个发送 / 更新最多试 5 次（间隔 5、15、45、135 秒），
之后记 `failed`；平台要求放慢的不算一次，等它说的时间再来（最多 10 分钟）。渠道不可用不影响建单、站内审批与超时处理。

## 八、已知限制

两个渠道都有：

- 卡片语言选英文时，仍有少数内容是中文：大表直接执行的原因、带 SQL 时执行窗口的描述、敏感导出单的前缀与理由。
- 发送超时但平台其实收到了，重试会再发一张：会看到两张卡片，先到的那张点了提示「卡片已失效」。
- 不支持群内审批、多个网关实例共用一个机器人、在卡片上执行或撤回。

Lark：

- 飞书只允许更新 14 天内的消息。更早的卡片不再更新，上面的按钮还在，点了提示已处理。
- 不支持代理出网。
- 国际版未验证：官方文档没有明说国际版支持长连接。
- 断线期间收不到点击；没收到应答的文字消息，平台会在约 15 秒、5 分钟、1 小时、6 小时后重推，点击要人再点一次。
- 表单（拒绝原因）回调在真实客户端上未验证；卡片的显示效果也未验证。
- 官方 SDK 每次「连上又断开」会留下一个很小的协程，长期频繁断线时内存会缓慢增长。

Telegram：

- **真实的 Telegram 整体未验证**：报错的原话、点击应答的时限、卡片的显示效果、屏蔽与删号的处理。
- 断线期间（包括在设置里关掉渠道、网关停机）的消息与点击，平台最多替人存 24 小时，恢复之后**照样处理**：那时点的「确认通过」
  只要单子还在等、绑定还有效就算数。超过 24 小时的丢弃，卡片还在，可以再点。
- 点击处理到一半进程被强制结束，重启后平台会再给一遍。决定是幂等的，不会决定两次；重复的绑定码会回「无效」，而绑定其实已
  经成了。一次处理超过 30 秒的不再等它，这时进程崩掉，那次点击就丢了，要再点一次。
- 拒绝没有二次确认，也不能填原因。
- 机器人的文字回话（绑定结果、处理慢了之后补的提示）有限额：同一个人每分钟最多 12 句没绑上的回话，全体同时最多 8 句，多出来的
  不回；平台限流期间也不回。卡片不受这个限制。
- 有人大量给机器人发消息时，多出来的文字会丢掉（别人这时发的绑定码也可能丢，再发一次即可），不影响点击。
- 卡片全文最多 4096 个字符单位，放不下就截短并写明未显示全文。

## 九、已接受的风险

- 审批人可能没看完整语句就在卡片上通过（卡片上有「未显示全文」的提示）。
- 离职的人在管理员停用其网关账号之前，仍可用已绑定的聊天账号审批。
- **用户 IP 白名单管不到卡片上的点击**：聊天客户端在哪里，网关看不到。
- 卡片内容会经过并留在平台的服务器上：Lark 的含打码后的语句；Telegram 的默认不含，打开「带 SQL」之后才含。
- 任何人都能给 Telegram 机器人发消息。没绑定的账号只会得到用法说明或「绑定码无效」这类回话，看不到任何单子。

## 十、升级与回滚

- 升级：迁移 `0065_chat_cards`（MySQL 与 PostgreSQL 各一份，编号相同），只增不删：新表
  `tbl_chat_binding`、`tbl_chat_bind_code`、`tbl_chat_card`，`tbl_approval` 加 `decided_via`、`reject_reason`
  两列（有默认值）。渠道默认关闭，升级本身不改变任何行为。Telegram 不需要另外的迁移。
- 只想停用：在设置页关掉开关并保存，立即生效。连接断开后，已发出的卡片点了没有反应（客户端提示出错或一直转圈），也不再更新，单子在站内批；重新打开后接着
  更新，Telegram 上关着时的点击还会补处理（最多存 24 小时，第八节）。不想让它们生效，重新打开之前先在站内处理掉那些单子。
- 回滚二进制：0065 只增不删，新表与新列闲置无害，旧版本照常读写 `tbl_approval`（未实测；常规流程仍以
  `docs/上线部署SOP.md` §7 为准）。回滚期间卡片上的按钮点了没有反应，单子在站内批。
- **回滚之后再升级要注意**：旧版本不认识绑定，回滚期间停用账号、重置口令、重置 MFA **不会**解绑；渠道设置
  也还在，升级后会自动连上。期间动过这些账号的，升级后由管理员逐个「解除聊天绑定」；拿不准就在启动新版本
  之前清空 `tbl_chat_binding` 与 `tbl_chat_bind_code`，让大家重新绑定。
