# 模拟实现清单

这份清单存在的理由，是一次线上误判：

> 「批量巡检」把 88 台实例全报成「可连」，而其中有的连 dial 都超时。

原因是 `Executor.Test` 从仓库第一笔提交（`7c0bc72`，2026-07-17）起就是一个
`sleep(120ms); return true, "已接入网关"` 的桩——**从不拨号**，并且**没有记在任何
待办里**。它躺了将近两个月，直到有人拿它去判断一台生产实例能不能连。

一个永远说好话的巡检比没有巡检更糟：没有巡检时人会自己去试，有一个说「可连」的巡检
时人不会。

## 规矩

### 一、模拟只在开发环境生效

**生产模式下，任何已实现的功能都必须是真实现。**

总开关是 `gateway.AllowSimulation`，**默认 `false`**——漏设的后果必须是"拒绝"，不是
"造假"。将来某个新入口（新的 `cmd/`、新的测试夹具、某个工具）忘了设它，得到的是明确
的错误，而不是一堆悄悄编出来的数据。设置它的地方只有两处，都是显式的：

| 位置 | 值 |
|---|---|
| `cmd/server/main.go` | `cfg.Env != "prod"`，并把结论打进启动日志 |
| `bootstrap` 测试夹具 | `true`（它模拟的就是开发环境） |

生产下所有模拟路径给的是同一句话：

> 该实例未配置真实执行凭据；生产环境不返回模拟数据

这句话故意说全两件事：**问题在网关这边、不在远端**，以及**为什么开发环境上同一台
实例看起来是好的**。少说后半句，人会以为是网关坏了。

### 二、加了模拟实现，必须登记

凡是产出「合成数据」而不是去问目标库的代码路径，必须同时做两件事：

1. 在代码里带上标记 `SIMULATED-PATH: <id>`；
2. 在下面的表里有一行。

### 三、模拟执行不记成「已执行」

审计链要回答的是"谁在什么时候对哪台库执行了什么"。一条**从未接触任何数据库**的命令
如果记成 `executed`，就是在这条链上写下一句假话——而这条链的全部价值就在于它不说假话。
它也不是 `warn`：没有任何东西出错。

所以有单独的一个值 `model.ResultSimulated`（审计页显示为「模拟(未执行)」，中性色）。
生产环境不会出现它。

## 三道闸

| 闸 | 挡什么 |
|---|---|
| `TestProductionServesNoSimulatedData` | 关掉模拟之后，每条路径必须**拒绝**而不是给数据 |
| `TestSimulationDefaultsToOff` | 源码里的默认值必须是 `false` |
| `TestSimulatedPathsAreDocumented` | 加了模拟实现却不登记 / 清单里留着已删的条目 |
| `TestAudit_SimulatedRunIsNotRecordedAsExecuted` | 模拟执行不得记成「已执行」 |

前三条**接在 `build.sh` 里**，在编译之前跑：

```
==> Verify no simulated data in prod
```

跑不过就不出包。实测过两个方向：正常时正常出包；把默认值改成 `true` 之后，
`build.sh` 退出码 1、停在这一步、`dist/` 里没有二进制。

每一条都验过"会咬人"：临时塞一个未登记的标记进去、临时把默认改成 `true`，测试都
带着可照做的提示失败；撤掉后恢复通过。

## 新代码的标准做法：**拒绝，并说清为什么**

较新的几处从一开始就没有模拟分支，那才是标准：

| 位置 | 没有凭据时 |
|---|---|
| `gateway.RealMetadata` | 报错「实例未配置真实执行凭据，无法探查元数据」 |
| `service.CompileObject` | 报错「该实例未配置真实执行凭据，无法编译」 |
| `service.oracleObjectConn` | 报错「该实例未配置真实执行凭据，无法清点无效对象」 |
| `gateway.RealPing` | 报**不可连**，并说明是凭据没配 |

理由：一份空清单读起来是「这台库很干净」，一句「已接入网关」读起来是「那台库是好的」。
**把「我们没配凭据」说成「远端的状况」，是这里最坏的一种谎。**

## 现存的模拟路径

全部由 `!gateway.RealExecSupported(conn)` 触发——也就是**没有填连接凭据的实例**——
并且**只在 `AllowSimulation` 为真时**才走到。生产模式下它们一律拒绝。

| id | 位置 | 假的是什么 | 开发环境下用户能分辨吗 |
|---|---|---|---|
| `exec-run` | `gateway.Executor.Run` | 随机的行数 / 影响行数 | 终端上**不能**；但审计记的是 `simulated` |
| `exec-result-grid` | `frontend/src/lib/sqlResult.ts` `synthTable` | 由行数合成的结果表格 | 不能（服务端一拒绝就走不到它） |
| `objects-list` | `service.simulatedObjects` | 一组演示用的函数/过程/包 | 不能 |
| `object-source` | `service.simulatedObjectSource` | 一段像模像样的对象源码 | 不能 |
| `schema-tree` | `service.ConnectionSchema` 的兜底 | 种子表 `tbl_schema_object` 里的库表树 | 不能 |

## 仍然可以做，但当前不必

上表五项在**开发环境**里仍然分辨不出（除了审计那一栏）。这不再是生产问题，所以不急：

1. 终端在模拟结果上打一行「· 模拟结果（该实例未配置凭据）」；
2. 给连接加一个显式的「演示实例」标记，让模拟成为一次**写下来的决定**，而不是
   "凭据为空"这个巧合的副作用——今天这几处假实现之所以能躺两个月，正是因为触发
   条件是一个巧合；
3. 演示数据集整个改用真实的 SQLite 文件（`demo-sqlite` 已经是这么做的），模拟分支
   删干净。

在做出决定之前，这份清单就是那个「记下来让后面补充」的地方。
