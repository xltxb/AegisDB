03 核心架构：网关代执行

Gateway Proxy

所有命令不直连数据库，统一经网关：鉴权 → 实例可达性 → MFA → 风险判定 → 放行执行 / 转审批 / 拒绝 → 审计 → Webhook。终端、脚本、后台执行、发布与导出用同一个风险引擎（RiskEngine.EvaluateFor）。

// service/gateway.go Exec（节选，省略在线变更分支）
conn, err := s.Repo.GetConnection(connID)
applyTargetDatabase(conn, database)
if !s.canAccessConn(u, conn) { return nil, ErrForbidden }        // 标签授权
if conn.Status == model.ConnStatusMaint { return maint, nil }    // 维护态
if err := s.checkMFA(u, conn, mfaCode); err != nil { return nil, err }
stmts := gateway.SplitForJudge(conn.Engine, sql)                 // 逐条判定
v, win := s.judge(u, conn, stmts)                                // 取最严；执行窗口可放宽
return s.applyVerdict(ctx, u, conn, sql, v, reason, win)
  • deny：拒绝并审计。approve：建审批单、审计记 pending。allow：执行并审计。
  • 多条语句拆开逐条判、逐条下发，MySQL 的 multiStatements 有意关闭。
  • 对不能直接改数据的人，纯读命令在数据库层面以只读方式执行。
  • 没有凭据的实例：本地开发可返回模拟数据，其他环境一律报错（见 docs/simulated-paths.md）。

04 风险判定引擎（三层）

Risk Engine

菜单权限由中间件把关，引擎判三层，取最严：① 能力矩阵（角色 × 能力 × 分层）→ ② 高危字典（命令 × 分层）→ ③ 无 WHERE 拦截（按分层开关）。规则按分层（tier）而不是环境取：环境挂在分层下面。

档位能力矩阵高危字典
allow / off放行放行
approve / mid转审批转审批，中风险
deny / high拒绝转审批，高风险
  • 能力共 8 项：select、write、ddl、grant、conn、approve、explain、release。多角色取并集（最宽的一档）；没有规则行视为 allow，读不到规则则拒绝（ED3）。
  • 动词与能力由引擎方言决定（ADR 0004）；MySQL 系的 # 注释等歧义按多种读法各判一遍取最严。
  • 服务器端写文件（INTO OUTFILE 等）直接拒绝；调用即生效的函数按 write 判。
  • 只取计划的 EXPLAIN、SHOW / DESC、会话级 SET 不过字典：前者看 select 与 explain 两格，后两者看 select。
  • 执行窗口（ADR 0015）是唯一的放宽：在指定时间、指定库内把 approve 变成 allow；deny 不动，风险等级不降，越库不放。

05 鉴权与中间件

Auth & Middleware
中间件作用
JWTAuthAuthorization: Bearer 优先（脚本、Swagger）；否则读控制台的 HttpOnly Cookie，写操作另校验 X-CSRF-Token。校验会话代次与账号状态。
IPAllowlist控制台来源 IP 白名单；回环地址始终放行。登录与终端 WS 也过它。
MenuGuard角色菜单权限，无则 40300。
AdminOnly · AdminPortalGate管理接口只给平台管理员；管理后台另有 IP 白名单（40303）与独立空闲超时（40304）。
AuditSupervisor · AuditListGate审计的导出、校验只给管理员 / 审计员 / DBA 负责人；列表人人可读，范围由服务层收窄。
APIClientAuth · RequireScope开放接口：key.secret 凭据，绑服务账号、自带 IP 白名单与 scope，不走控制台白名单。
全局访问日志、Recovery、安全响应头、CORS、延迟统计、请求体上限；/api/v1 一律 no-store。

MFA 是按分层要求的步进验证：需要的分层上执行前要 TOTP，通过后对本会话、本实例有一段宽限；连错会锁定。来源 IP 只采信显式配置的代理转发的头。

07 审批、Lark 集成与告警

Approval & Lark
  • 建单生成 ap_no 与审批步骤：发布阶段可指定审批角色，否则用默认链（DBA 负责人；没人则平台管理员）。链上没有可审批的人就不建单。
  • 链上任意一人的决定即生效；同一张单只认第一个决定。能否自审由设置决定。
  • 通过不等于执行（ADR 0010）：普通单停在「待执行」，由够得到该实例、自己有权执行的人点执行，届时按执行人重新过标签、MFA 与判定；一张单只执行一次。
  • 发布单的审批只授权流水线，执行归执行阶段；执行窗口批准即生效；敏感导出批准即入队。
  • 新单推送飞书群机器人通知；审批只在站内决策。
  • 超时策略：保持等待 / 自动作废 / 自动升级（站内通知默认审批人 + 飞书卡片，每张单一次，单子仍待审批）；初始化写入自动升级、720 分钟，库里没有这项设置时按保持等待。每 60 秒扫描 tbl_approval。
  • 发布单失败或终止时，它名下待审批的单在同一事务里作废。

后台定时任务（cmd/server/main.go）：

周期任务
15 秒推进审批已有结论的发布单
60 秒审批超时、查询授权到期、终端会话与结果缓存清理
1 小时导出文件保留期清理
按设置连通性巡检、元数据同步

08 审计与 Webhook 外推

Audit & Webhook

审计 append-only、同步写入：hash = SHA256(prev_hash + payload) 形成哈希链；进程内加锁，prev_hash 唯一索引兜住并发分叉，冲突则重读链尾重试。命令里的口令先脱敏再入库。写入失败计数在 /healthz 的 auditWriteFailures。

  • 载荷按代演进：新字段只进新一代，老行按写入时那一代重算。
  • 校验：aegisdb verify-audit 或管理后台，链断了命令退出码 2。服务器时区不能变，否则整链重算不过。

Webhook 按审计事件的增删改查（data_action）与环境订阅，后台投递。鉴权是 Authorization: Bearer <secret>，不是签名；secret 加密存储。目标地址过 SSRF 检查。

// service/webhook.go Dispatch（节选）
req.Header.Set("Authorization", "Bearer "+secret)
req.Header.Set("X-AegisDB-Event", eventType)
req.Header.Set("X-AegisDB-Pushed-At", pushedAt)
// 失败按 1、2、4 … 秒退避，单次最多 30 秒；总时长不超过 2 分钟，次数由 retry_max 限制

请求体是事件中心格式（source_system / occurred_at / action / resource / operator / summary / raw_payload），见《事件中心平台接入文档》。每次投递记入 tbl_webhook_delivery。

10 非功能与错误码

NFR & Error Codes
  • 规则：判定时直接读存储库，改完立即生效；没有缓存层。
  • 凭据：连接口令、TOTP 种子、Webhook secret 用 AES-256-GCM 加密，密钥由 scrypt 派生自 AEGISDB_SECRET_KEY；用户口令与开放接口 secret 用 bcrypt。密钥一经使用不可更改。
  • 单进程部署：终端会话、限流计数、在线用户、管理后台空闲、任务队列都在内存里，重启即清空；重启时把中断的任务收尾（失败、不重跑）。
  • 并发：状态流转用条件更新认领（claim），发布单终态、阶段与审批单在一个事务里收尾。
  • 迁移：生产用 migrate 子命令，幂等；迁移后不要单独回滚二进制。
code含义
0成功
40001参数错误

40300无权限
