# 控制台接口说明

面向**接控制台这一面**的人：写第二个前端、做自动化脚本、把网关的数据接进内部看板。

这不是契约文件。逐字段的请求/响应形状看 `backend/docs/openapi.yaml`（运行时
`GET /openapi.yaml`；本地开发可开 Swagger UI `GET /docs`，带 Authorize 与 Try it out）。
本文回答契约表达不了的三件事：

1. **这一组接口是干什么的**，以及它们之间的顺序关系；
2. **调它要付什么代价** —— 每条路由的守卫；
3. **哪些地方的语义和直觉不一样** —— 那些看契约看不出来、踩过才知道的。

> 要从**外部系统**提交变更单，别用这一面。那是另一套鉴权与另一份文档：
> `docs/开放接口对接文档.md`。

## 一、公共约定

### 两套鉴权面，别混用

| 面 | 前缀 | 鉴权 | 谁在调 |
|---|---|---|---|
| **控制台**（本文） | `/api/v1` | `Authorization: Bearer <JWT>` | 登录的人 |
| 开放接口 | `/api/v1/open` | `Authorization: Bearer <key>.<secret>` | 外部系统 |

### 信封

**所有响应都是 HTTP 200**，业务结果在包体里：

```json
{ "code": 0, "msg": "ok", "data": { } }
```

判断成功看 `code === 0`，不要看 HTTP 状态码。常用码：

| code | 含义 |
|---|---|
| `0` | 成功 |
| `40001` | 参数问题（`msg` 指名道姓） |
| `40100` | 未登录 / token 失效 / 会话代次已被作废 |
| `40300` | 无权（菜单、角色或数据范围） |
| `40301` | 来源 IP 不在白名单 |
| `42200` | **命令被拦截，已开审批单**（`data` 带 `approvalNo`）—— 这是正常结局，不是错误 |
| `42600` / `42601` | 网关未配置脚本 / 导出保存路径 |
| `42800` | 需要 MFA 二次验证，带上 `mfaCode` 重发 |
| `42900` | 请求过多：登录尝试过多（按源 IP 限流）；业务查询的并发配额已满（每人 / 每实例）或当天次数已到每日上限 |
| `50000` | 服务端错误 |

`42200` 值得单独说：终端执行、脚本执行、异步执行都可能以它结束，而那**不代表调用失败** ——
网关判定这条命令要人批，已经替你建了单。把它当错误弹红框，是最常见的一种接错。

### 两层守卫

每条路由的代价由两样东西决定，本文的表格里直接标出来：

- **菜单键**（`menu(...)`）：调用者的角色集合要持有这个菜单。权限取**所有角色的并集**。
- **`admin`**：只有平台管理员角色。角色/权限配置与账号管理限于此 —— 否则 DBA 负责人可以
  给自己加权限，那就不叫权限了。

表格里守卫栏为空 = 只要登录就能调。另有少数几条的真正门槛在 service 层（因为路由只认得
菜单键、认不出角色或行归属），这类会在各节里写明。

### 会话

JWT 里带**会话代次**（`TokenVersion`）。登出、停用账号、重置密码都会把它加一，于是所有
旧 token 当场失效 —— 这就是为什么 `40100` 的含义里有"会话代次已被作废"这一条。

## 二、身份与会话

| 方法 | 路径 | 守卫 |
|---|---|---|
| `POST` | `/auth/login` | 公开（按源 IP 限流 + IP 白名单）。启用 SSO 时，**已绑定 SSO 的非管理员**口令正确也回 `40300` 并提示改走 SSO |
| `GET` | `/auth/sso/config` | 公开。登录页据此决定是否露出「使用 SRD 授权登录」；`loginUrl` 为 `{SRD}/auth/login`；`forcedOff` 为 true 表示部署配置（`sso.disabled` / `AEGISDB_SSO_DISABLED`）强制关闭了 SSO |
| `POST` | `/auth/sso` | 公开（按源 IP 限流 + IP 白名单）。从父域 Cookie `CS-Token` 解出 JWT，以 Bearer 调 SRD 的 `userinfo` 换邮箱，再换网关会话；存量账号首次经 SRD 登录时自动绑定。`40101` 表示没有 SRD 登录态（不是错误） |
| `POST` | `/auth/logout` | 登录 |
| `GET` | `/auth/me` | 登录 |
| `POST` | `/auth/mfa/setup` `/auth/mfa/enable` `/auth/mfa/disable` | 登录 |
| `GET` | `/auth/chat-bindings` | 登录。本人在各审批机器人渠道上的绑定状态；一个渠道都没开是空数组。`botName` 只有 Telegram 有（机器人的用户名） |
| `POST` | `/auth/chat-bindings/:channel/code` | 登录。生成一次性绑定码（10 分钟有效）；启用了 MFA 的账号要带 `mfaCode`，没带回 `42800` |
| `DELETE` | `/auth/chat-bindings/:channel` | 登录。本人解绑 |
| `GET` | `/gateway/stats` | 登录 |
| `GET` | `/notifications` · `POST /notifications/read` | 登录 |
| `GET` | `/approval-chain` | 登录 |

**先调 `/auth/me`**，再决定界面画什么。它回的 `menus` 与 `capabilities` 就是上面那两层守卫
的同一份数据 —— 照着它收敛入口，可以避免"按钮亮着、点下去 403"。但**不要拿它当安全边界**：
服务端每条路由都自己判，前端的收敛只是为了不让人对着一个必然失败的按钮。

登录可能以 `42800` 结束（该账号已绑 TOTP）：这不是失败，带上 `mfaCode` 重发即可。密码正确
但没带码，也算 `42800` 而不是 `40100` —— 两者要人做的事不同。

## 三、终端：判定与执行

这一面是整个网关的核心，顺序是**先判后跑**：

| 方法 | 路径 | 守卫 | 干什么 |
|---|---|---|---|
| `POST` | `/risk/check` | `menu(terminal)` + 实例访问权 | 只判不跑：这条语句会被放行、拦截还是拒绝。够不到这台实例的人调不动它 —— 预检的结论本身就是情报（实例存不存在、挂在哪个分层、哪些命令要审批），否则可以靠枚举 `connectionId` 问出来 |
| `POST` | `/terminal/exec` | `menu(terminal)` | 同步执行。Oracle 上带 `serverOutput: true`（终端开了 `SET SERVEROUTPUT ON`）时，同一会话读回 `DBMS_OUTPUT`，随结果以 `serverOutput[]` 返回（至多 2000 行）；SQL*Plus 的 `SET` 不下发，回一句"已忽略" |
| `POST` | `/terminal/exec-async` | `menu(terminal)` | 转后台执行（长语句） |
| `GET` | `/async-jobs` · `/async-jobs/:id` | `menu(terminal)` | 后台任务与进度日志 |
| `GET` | `/terminal/ws` | **自带鉴权**（token 走 `Sec-WebSocket-Protocol`） | 流式终端 |
| `POST` | `/terminal/transcript-export` | `menu(terminal)` | 记录"会话日志被导出"这一事实 |

几件要紧的：

- **`database` 要传。** 执行窗口（班车）按库开，预检不带库名就判不出窗口，会比真实执行更严：
  终端先弹一个多余的审批理由框，提交后才发现根本不用审批。
- **`/risk/check` 与 `/terminal/exec` 用的是同一条判定链**，但预检的结论**不构成承诺**：
  执行时会重新判一次。中间可能过了几秒，也可能过了几小时（审批单的执行路径），而规则、
  实例归属、你的角色都可能变。
- **多语句按最严格的一条判**。`SELECT 1; DROP TABLE x;` 整批拦截，工单上会列出全部命中。
- **`/terminal/ws` 不在 JWT 中间件后面**（WebSocket 握手带不了 `Authorization`），它自己在
  handler 里校验 token、菜单与活跃会话，并且照样过 IP 白名单。
- `transcript-export` 送的是一份**描述**（文件名、行数、丢弃行数），不是会话内容本身 ——
  把已经显示过的文本再传回服务端存一份，等于凭空造出第二份要保护的数据。

## 四、脚本与快捷片段

| 方法 | 路径 | 守卫 |
|---|---|---|
| `GET` | `/scripts/config` | `menu(terminal)` |
| `POST` | `/scripts/scan` | `menu(terminal)` |
| `POST` | `/scripts/execute` | `menu(terminal)` |
| `GET/POST/DELETE` | `/scripts/uploads`（含 `/:id/download`、`/:id/content`） | `menu(terminal)` |
| `GET/POST/PUT/DELETE` | `/snippets`（含 `/limits`、`/:id`） | `menu(terminal)` |

- **先 `scan` 后 `execute`。** 扫描逐语句判级；检出高危则整脚本转审批，审批单引用的是**已上传
  的那个文件**（记了哈希）。执行时重新读文件、校验哈希、逐语句重判再逐条下发 —— 审查过的
  字节和执行的字节是同一份。
- 上传文件是**按人隔离**的：你只看得见自己传的。
- `scan` / `execute` 比别的接口慢得多（6MB 的迁移脚本服务端要跑十几秒）。客户端超时按
  **两分钟**设，别用默认的十几秒 —— 那会在工单已经建好之后给你一个网络错误。

## 五、数据导出

| 方法 | 路径 | 守卫 |
|---|---|---|
| `GET` | `/export/config` | `menu(terminal)` |
| `POST` | `/export` | `menu(terminal)` |
| `GET` | `/export/jobs` | `menu(terminal)` |
| `POST` | `/export/jobs/:id/cancel`（终止排队中 / 待审批 / 执行中的导出；执行中的同时终止目标库上的查询，待审批的一并撤回审批单；仅提交人或平台管理员） | `menu(terminal)` |
| `GET` | `/export/download` | `menu(terminal)` |

只接受**单条只读查询**（写操作、写文件子句一律拒绝）。任务异步跑，结果是 AES-256 加密的
分卷 zip，口令按任务发放。行数 / 字节 / 超时上限都是运行时设置，管理员在【设置 · 网关】改。

**要敏感字段原值**（`includeSensitive`）的任务不会直接进队列，先去等审批。脱敏发生在结果
离开网关**之前**，不是前端打码。

## 六、实例、元数据与数据库对象

| 方法 | 路径 | 守卫 |
|---|---|---|
| `GET` | `/connections` | 登录（按你的角色标签过滤） |
| `GET` | `/tags` | 登录 |
| `POST/PUT/PATCH` | `/connections`、`/connections/:id`、`/connections/:id/test` | `menu(db)` + `admin` |
| `PATCH` | `/connections/:id` 带 `bizQuery`（业务查询源标记：只有它能被查询授权引用；写审计） | `menu(db)` + `admin` |
| `PUT` | `/connections/:id` 带 `replicaHost` / `replicaUsername` / `replicaPassword`（从库：业务方数据查询都由从库提供，连不上回落主库；`replicaHost` 空串 = 去掉从库，不传 = 不动；密码留空保持不变） | `menu(db)` + `admin` |
| `GET` | `/bizquery/grants`（我的查询授权：生效中与未到开始时间的） | `menu(query)` |
| `GET` | `/bizquery/tables?sourceId=&database=`（授权库里的表与视图，给数据查询页的「表」下拉：判定同 `/bizquery/exec` 前半段，无授权回 `40300`；读不到目录回 `0` + `data.error`；不写审计） | `menu(query)` + 该库的生效授权 |
| `POST` | `/bizquery/export`（结果下载为 CSV：需全局导出开关与授权的「允许导出」，至多授权行数上限，永远脱敏，写导出审计；失败时是 JSON 信封，错误码同 `/bizquery/exec`） | `menu(query)` + 该库的生效授权 |
| `GET` | `/query-grants`（查询授权总表，可按邮箱 / 部门 / 实例 / 库 / 状态筛选） | `menu(perms)` |
| `POST` | `/query-grants/:id/revoke`（管理员撤销，立即生效，原因写审计） | `menu(perms)` + `admin` |
| `POST` | `/bizquery/exec`（业务方执行一条查询：单条只读、按库收窄、行数上限、库端时限、只读事务；判定拒绝回 `40300`，并发配额已满或当天次数已到上限回 `42900`（均带 `data.reasonRef`），执行失败回 `0` + `data.error`；最外层 LIMIT 大于上限会被改小，写的不是数字则拒绝；结果按敏感字段规则脱敏，经子查询 / UNION / WITH 给敏感字段改名的拒绝，原因码 `bizSensitiveEvasion`） | `menu(query)` + 该库的生效授权 |
| `GET` | `/schema-diff/connections`（可参与表结构对比的实例，带引擎族，只有同一族能互比） | `menu(schemadiff)` |
| `GET` | `/schema-diff/connections/:id/databases`（实例上可以比的库，给库名下拉：实时读、不列系统库，Oracle 为用户且总含登录账号；读不到回 `0` + `data.error`，页面退回手填；不写审计） | `menu(schemadiff)` + 该实例的访问权限 |
| `GET` | `/schema-diff/connections/:id/schemas?database=`（PG / DWS 一个库里可以比的 schema，给 schema 下拉：口径与对比时读目录相同；非 PG 系回空列表；读不到回 `0` + `data.error`；不写审计） | `menu(schemadiff)` + 该实例的访问权限 |
| `POST` | `/schema-diff`（比较两个库的表结构：左右实例都要能访问，可以是同一实例的两个库 / PG 同库的两个 `schema`；实时读目录；无权访问一边回 `40300`，实例不存在 / 没配凭据 / 引擎不同回 `40001`，均带 `data.reasonRef`；读失败回 `0` + `data.error` / `errorRef` / `errorSide`；一边空库照常出报告并标 `data.emptySide`；审计记"读"，左右两个实例各记一条） | `menu(schemadiff)` + 两边实例的访问权限 |
| `PUT` | `/connections/:id/database-project` | `menu(db)` + `admin` |
| `GET` | `/connections/:id/schema` · `/objects` · `/object-source` · `/objects/invalid` | `menu(terminal)` |
| `GET` | `/connections/:id/columns?database=&table=`（一张表的列名，终端 Tab 补全用：实时查、按建表顺序、保留原始大小写；table 可带限定名） | `menu(terminal)` + 可访问该实例 |
| `POST` | `/connections/:id/objects/compile` · `/objects/recompile` | `menu(terminal)` + 实例访问权 + 生产 MFA |
| `POST` | `/connections/:id/packages/download`（Oracle 程序包导出为 .pck，多选打成 zip；记导出审计） | `menu(terminal)` + 实例访问权 |
| `GET` | `/connections/:id/metadata` · `/metadata/search` | `menu(terminal)` |
| `POST` | `/connections/:id/metadata/sync` | `menu(db)` + `admin` |
| `GET/POST/PATCH/DELETE` | `/projects`（读为登录） | `menu(project)` + `admin` |
| `GET/POST/PUT/DELETE` | `/sensitive-columns`（读为 `menu(terminal)`，见下） | `menu(perms)` + `admin` |

- **`/connections` 已经按角色的标签范围过滤过。** 你看得见的就是你够得到的，不必自己再筛。
- **库表不随连接列表下发。** 每台实例要单独连过去 introspect 一次（`/schema`），所以
  "搜索覆盖库表"只覆盖**探查过的**那些。要全量，得逐台触发 —— 并发受限、代价真实。
- **Oracle 的第二层是 OWNER（schema），不是服务名。** 切了 schema 之后建的工单、审计行、
  后台任务记的都是那个 schema，批准后执行会切回同一个地方。
- 实例口令 AES-GCM 静态加密，任何读接口都不回明文。

## 七、分层与环境

| 方法 | 路径 | 守卫 |
|---|---|---|
| `GET` | `/env-tiers` · `/environments` | 登录 |
| `GET` | `/environments/usage` | `menu(envtier)` |
| `POST/PUT/DELETE` | `/env-tiers/...` · `/environments/...` | `menu(envtier)` + `admin` |

读对所有登录者开放：终端的实例树、实例标签、连接表单都要渲染它们。写限管理员 —— **分层决定
它底下的实例被管得多严**，这是整套管控的根。

**分层（tier）承载规则，环境（environment）归属实例。** 规则行全部按分层存；新建一个环境挂到
现成分层上，它立刻受完整管控，不复制任何规则行，不存在空规则窗口期。

## 八、执行窗口（「班车」）

| 方法 | 路径 | 守卫 |
|---|---|---|
| `GET` | `/exec-windows` | 登录 |
| `GET` | `/exec-windows/:id/statements` | **service 层**：班车菜单 **或** 监督角色 |
| `POST/PUT/DELETE` | `/exec-windows`、`/exec-windows/:id` | `menu(execwindow)` |

- 申请窗口**不要求管理员** —— 这个功能的整个要点就是"开门的人和签字的人不是同一个"。
  改和撤只有申请人本人或管理员能做（判断在 service 层，路由认不出行归属）。
- 窗口**批准后才生效**：`status=approved` + `enabled` + 此刻落在时间表内，三者都成立才是开着的。
  响应里的 `active` / `expired` 由服务端用与判定完全相同的逻辑算好 —— 别在客户端自己算
  跨午夜与时区，两份实现迟早分叉，而分叉的表现是"界面说开着、网关说没开"。
- **回看**（`/statements`）列出这扇门开着的那几个小时里跑过的语句，被它放行的那几条单独标出。
  内容**不按人收窄**：打得开这一页的人看得见所有人跑的原文。这与审计页的规则刻意分道 ——
  免审批的门免掉了签字的人，一份只剩自己那两条的回看读起来和"没出什么事"一样。
  门槛因此挪到"谁打得开"：班车菜单持有者，或监督角色（管理员/负责人/审计员）。

## 九、审批

| 方法 | 路径 | 守卫 |
|---|---|---|
| `GET` | `/approvals` | `menu(approve)` |
| `GET` | `/approvals/todo` | 登录 |
| `POST` | `/approvals/:id/approve` · `/reject` | `menu(approve)` |
| `POST` | `/approvals/:id/execute` | `menu(terminal)` |
| `POST` | `/approvals/:id/cancel` | `menu(terminal)` |

**注意最后两条挂的是 `terminal` 而不是 `approve`** —— 这不是笔误：执行与撤回是**执行侧**的动作，
审批人手里的动作是通过与驳回。两者要的菜单因此不同。

- **通过不执行任何命令。** 通过后由人回来点执行，一张单只能执行一次，执行前会再判一次规则。
- **执行权不限发起人本人**（ADR 0010 的 2026-09-09 修订）：够得到那台实例（标签授权）、能力
  矩阵也放行的人都可以接手 —— 需求要的是"值班的人能接手"，而值班的常常正是审批人。门都按
  **执行者**算（标签、MFA、能力矩阵复判），别人替你跑了发起人会收到通知。
  **撤回**仍然只限发起人本人与管理员：审批人能撤回的话，他可以用撤回把一张本该驳回的单悄悄
  抹掉，而记录上看不出有人拒绝过什么。
- **三类工单走不了 `/execute`**：发布单归流水线，执行窗口单批准即生效，导出单由后台任务跑 ——
  后两类的 `command` 是一句描述而不是可执行语句。
- 列表行上带着服务端算好的 `canDecide` / `canExecute` / `canCancel` 与 `blockReason`。
  **照着它们画按钮，不要自己推**：服务端的规则比"是不是审批链成员"多好几条（比如不能审自己
  发起的），两份判断不一致的结果就是一个亮着却点不动的按钮。
- `GET /approvals` 的每张单带 `decidedVia`（决定渠道：`console` / `api` / `lark` / `telegram`，空 = 没有人做过决定或
  早于这一列的老单；通过之后又撤回的留着当初的渠道）与 `rejectReason`（拒绝原因，只有聊天卡片上能填）。
  后者是人写的原文，当纯文本显示。
- `/approvals/todo` 是"**此刻在等我动手的**"，与"状态是 pending"不是一回事 —— 后者把我自己
  发起、等别人审的那些也算进去了。
- 一张单的**最终状态以数据库上那次执行的结果为准**：目标库拒绝了这条语句，单子显示失败，
  而不是"已通过"。执行结果单独存（`execStatus`：`running` 执行中 / `success` / `failed`；空 = 未执行
  或早于这一列的历史单），不与审批状态合并。点下执行即写 `running`，命令在库上跑完才落结论；网关在
  执行途中重启的，启动时判 `failed` 并写明结果未知，不重跑。

## 十、发布与流程

| 方法 | 路径 | 守卫 |
|---|---|---|
| `GET` | `/pipelines` · `/pipelines/:id` | `menu(pipeline)` |
| `POST/PUT/DELETE` | `/pipelines`、`/pipelines/:id` | `menu(pipeline)` + `admin` |
| `GET` | `/releases` · `/releases/:id` | `menu(pipeline)` |
| `POST` | `/releases` | `menu(pipeline)` |
| `POST` | `/releases/:id/abort` | `menu(pipeline)` |
| `POST` | `/releases/:id/stages/:stageId/continue` | `menu(pipeline)` |

一条流程 = 有序阶段列表（`review` / `approve` / `backup` / `execute` / `verify` / `manual` /
`notify`）。发布单按阶段展示状态、耗时、日志与审查结果。

- **能不能发起发布**是能力矩阵里单独的一维（`release`），与"这条语句能不能跑"是两个问题。
  可以做到"开发自助发布、预发布必须走审批、生产一律不许外部发起"，而不必把 `DDL` 在生产整个
  关掉（那会连带堵死终端和审批通道）。
- `stages/:stageId/continue` 只对**人工确认**阶段有意义。
- 网关重启后：`running` 判失败（执行结果未知，不重跑）、`waiting` 原样保留、`pending` 重新入队。

## 十一、规则：高危字典与规范审查

| 方法 | 路径 | 守卫 |
|---|---|---|
| `GET` | `/risk-commands` | `menu(terminal)` |
| `POST/PATCH/DELETE` | `/risk-commands`、`/risk-commands/:name` | `menu(rules)` + `admin` |
| `GET` | `/sql-review/rules` · `/sql-review/catalog` | `menu(terminal)` |
| `POST` | `/sql-review/check` | `menu(terminal)` |
| `POST/PUT/DELETE` | `/sql-review/rules`、`/sql-review/rules/:id` | `menu(rules)` + `admin` |

两套规则回答的是**不同的问题**，别混：

- **高危命令字典**判"危不危险"，影响执行链路（放行 / 转审批 / 拒绝），按分层存。
- **规范审查**判"写得对不对"，结论只被发布流水线的审查阶段消费；终端执行链路不受影响。
  87 条内置规则各自标着公司规范的出处，级别与开关在库里、控制台即改即生效。

读接口挂 `menu(terminal)` 而不是 `menu(rules)`：上线前自查是写变更的一部分，不该是另一项特权。
改规则才要 `rules` + 管理员。

## 十二、审计

| 方法 | 路径 | 守卫 |
|---|---|---|
| `GET` | `/audit` | `menu(audit)` |
| `GET` | `/audit/instances` | `menu(audit)` |
| `GET` | `/audit/approval/:apNo`（一张审批单的全部操作记录，按时间先后；可见范围同列表，不受列表筛选限制） | `menu(audit)` |
| `GET` | `/audit/export` | `menu(audit)` |
| `GET` | `/audit/verify` | `menu(audit)` + **service 层**：监督角色 |

**可见性**：有监督角色（`admin` / `owner` / `audit`）的人看得见所有人的行，其余人只看得见
自己的。这条在 service 层统一加，列表、导出、计数都绕不过去 —— 一份导出里多出他在列表上
看不见的行，是这一页最不该出的错。

**筛选参数**（`/audit` 与 `/audit/export` 共用同一段解析）：

| 参数 | 说明 |
|---|---|
| `risk` | `all` / `high` / `mid` / `low` |
| `event` | **多选**，逗号分隔：`intercept,approve,exec,login` |
| `action` | **多选**，逗号分隔：`create,delete,update,read,other` |
| `instance` | 精确匹配；可选值来自 `/audit/instances` |
| `q` | 模糊匹配**操作人姓名、邮箱或来源 IP**（`%`、`_` 按字面量处理，上限 128 字符） |
| `range` | `1h` / `24h` / `7d` / `30d` |
| `from` / `to` | 绝对区间，**优先于 `range`** |
| `page` / `pageSize` | 分页（`pageSize` 上限 500） |
| `group` | 仅 `/audit`：`approval` = 同一张审批单的行合成一个条目（显示最新一行），响应多带 `groups`（审批单号 → 条数）；分页与 `total` 按条目算。导出不合并 |

多选里任何一个取值认不出，**整条请求报错**，不是把认得出的那半拿去筛 —— 半懂半不懂地筛，
给出的结果比报错更难发现是错的。

**两列时间语义不同**：`occurredAt` 是这一行写下的时刻。审批单上的"执行时间"是另一回事，
在审批那一面。

**`/audit/verify`** 重算哈希链，验最近 5000 行（整表校验走命令行 `aegisdb verify-audit`）。
它只报**第一处**对不上的行，`badReason` 三种：`content`（内容被改过）/ `link`（前驱哈希接不上，
中间有行被删或插）/ `gen`（按更老的键集才算得过）。响应里另附一句人话 `reasonText`。
门槛是监督角色而不只是 `audit` 菜单 —— 它扫的是全表，天然越过了"只看得见自己"那条线。

| 方法 | 路径 | 守卫 |
|---|---|---|
| `GET` | `/roles` · `/roles/:id` · `/users` · `/users/:id/tags` | `menu(perms)` |
| `PATCH` | `/roles/:id` | `menu(perms)` + `admin` |

| `POST` | `/users/:id/sso-unbind` | `menu(perms)` + `admin`。解除 SSO 绑定，恢复口令登录；下次经 SRD 登录会重新绑定 |
| `PATCH` | `/users/:id` | `menu(perms)` + `admin` |
| `POST` | `/users/:id/password` · `/mfa/reset` · `/mfa/bind` | `menu(perms)` + `admin` |
| `DELETE` | `/users/:id/chat-bindings` | `menu(perms)` + `admin`。解除该用户的全部审批机器人绑定 |
| `PUT` | `/users/:id/tags` | `menu(perms)` + `admin` |

**读写分离得很清楚**：看得见权限配置（`perms` 菜单）和改得动它（`admin`）是两件事。角色配置
与账号凭据只有平台管理员能动 —— 否则 DBA 负责人可以给自己加权限。

- 一个用户可挂多个角色，**权限取并集**；主角色只决定显示的角色名与层级。
- `POST /users` 由管理员设初始密码，建出来就是 `active`；`invite` 建的是待激活。
- 停用账号会作废它的所有会话（会话代次 +1）。列表行上带着服务端算好的 `canDisable` /
  `disableBlock`，同样照着画就行。

- 签发凭据要绑一个**服务账号**（`kind=service`）：它登录不了控制台，唯一的门就是那把凭据。

## 十五、几条通用的踩坑提示

1. **`42200` 不是错误。** 它说的是"这条命令要人批，单子已经建好了"，`data.approvalNo` 拿去展示。
2. **别缓存 `/auth/me` 太久。** 管理员改了你的角色之后，旧的菜单集合会让界面画出点不动的东西。
3. **列表接口几乎都分页且在服务端筛。** 自己在客户端过滤"当前页"，会对一条躺在第三页的记录
   回答"没有" —— 而人会据此认为它不存在。
4. **服务端算好的布尔位要直接用**（`canDecide` / `canExecute` / `canCancel` / `canDisable` /
   `active` / `expired`）。它们存在的唯一理由就是不让第二份判断在客户端长出来。
5. **时间一律按服务器本地时区**返回。执行窗口的时间表另带自己的 `timezone` 字段。
6. **所有写操作都进审计链**，包括被拒绝的那些，而且带上来源 IP。
