## 一、项目概况

### 1.1 建设背景

数据库是业务数据的最终落点，而日常运维中对生产库的访问长期依赖"客户端工具 + 口头审批 +
事后追问"的模式。这一模式存在三个结构性缺陷：

1. **权限颗粒度过粗**。数据库账号一旦下发，权限便是静态的：能连上就能执行，无法区分
   "查询生产"与"删除生产"，也无法区分工作时间与维护窗口。
2. **高危操作缺少前置闸门**。`DROP`、不带 `WHERE` 的 `DELETE` 一旦执行即不可逆；事前审批
   靠人自觉发起，事后补救靠备份。
3. **操作轨迹不完整、不可信**。谁、在什么时候、从哪台机器、对哪个库做了什么，分散在数据库
   日志、跳板机记录与聊天记录中，且均可被有权限者修改。

本项目的目标，是把上述三件事收敛到一个**统一入口**上：所有对受管数据库的访问都经过网关，
由网关按可配置的规则做实时判定，并留下不可否认的操作轨迹。

### 1.2 建设目标

| 目标 | 落地形态 |
|---|---|
| 统一访问入口 | Web 终端、脚本执行、异步任务、数据导出、变更发布、开放接口，六条通道共用同一判定链 |
| 风险前置拦截 | 四层判定（菜单权限 → 能力矩阵 → 高危命令字典 → 无 WHERE 拦截），规则全部按环境分层存储、在线可改 |
| 变更流程闭环 | 多步审批链 + 发布流水线 + 执行窗口；审批通过不等于执行，执行由人显式触发并二次判定 |
| 操作可追溯 | 全量审计 + SHA-256 哈希链 + 可离线重算的校验工具 |
| 数据不外泄 | 敏感字段在结果离开网关之前脱敏；导出加密分卷；口令语法全引擎脱敏后入库 |
| 规范前移 | 87 条数据库设计规范规则，可在 CI 合并前作为门禁调用 |

## 二、技术方案

### 2.1 技术选型

| 层次 | 选型 | 选择理由 |
|---|---|---|
| 后端 | Go 1.23 · Gin · GORM | 单二进制交付，无运行时依赖；契合"内网、断网、无容器编排"的实际部署环境 |
| 数据库 | MySQL 8（生产）/ SQLite（开发） | 生产沿用现有 MySQL 运维体系；开发态零依赖，克隆仓库后可直接启动 |
| 前端 | Vue 3 · TypeScript · Vite · Pinia | 组合式 API 与类型检查覆盖到构建期；国际化文案在构建期预编译，非法文案直接构建失败 |
| 终端 | xterm.js + WebSocket | 真实终端交互体验，流式返回；WebSocket 不可用时自动回退 REST |
| 交付 | 单文件 + systemd + Nginx 反代 | 前端资源、迁移脚本、接口文档全部内嵌进二进制，部署即一次解包 |

### 2.2 总体架构

```
外部系统 ──┐
          ├─→ 开放接口 (/api/v1/open, Key+Secret)  ─┐
浏览器 ────┼─→ 控制台   (/api/v1, JWT)              ─┼─→ 统一判定链 → 执行器 → 受管数据库
审批服务 ──┘   回调 (共享密钥 + 签名 + IP 白名单)    ─┘         │
                                                              └─→ 审计（哈希链）→ Webhook → SIEM
```

设计上的一条硬约束：**开放接口只是一扇门，不是第二条执行通道**。外部系统提单走的是同一套
流程模板、同一份规则库、同一条审批链、同一次执行前复判、同一条审计链。

### 2.3 关键设计决策

项目形成 **14 篇架构决策记录（ADR）**，记录每项决策的背景、备选方案与取舍。其中影响面
最大的五条：

| ADR | 决策 | 要解决的问题 |
|---|---|---|
| 0009 | 敏感字段脱敏在**服务端**做 | 前端打码等于把明文完整发到浏览器再请它不要显示——数据在"被隐藏"之前已经躺在浏览器缓存、反代日志与前端错误上报里 |
| 0010 | **审批通过不执行任何命令** | 批准与执行分离，避免同一变更被应用两次；2026-09-09 修订将执行权由"仅发起人"放开至"够得到该实例的同事"，因为值班的人常常正是审批人 |
| 0013 | 无 WHERE 拦截**按分层**生效 | 原为全局开关，导致无法只对开发环境关闭，实际使用中被整体关掉，防护归零 |
| 0015 | **执行窗口（班车）** | 把"提前把规则改松、事后忘了改回去"的口头约定，变成系统内可查、可审计、到点自动关闭的对象；且只把"需审批"降为"放行"，"拒绝"仍然拒绝 |
| 0017 | 收单**预检**结论标注来源 | 没做的检查照样列出来，而不是从结果里消失——留白会被读成通过 |

### 2.4 一条贯穿全局的工程原则：失败朝"关"的方向

判定链上所有异常路径均为 fail-closed：读不到规则表、时区解析失败、库名为空、数据库瞬时
故障，一律不生效或当场拒绝，而非放行。

此原则在代码评审与安全审计中被反复检验。2026-09 审计发现的 M-4（数据库查询失败被当作
"无规则配置"从而放行）即是对该原则的一次违反，已修复，并在注释中标明"查询失败不等于规则
缺失"——这类缺陷的危险之处在于它只在数据库瞬时故障时显形，平时无任何征兆。

## 三、建设内容

控制台共 **17 个菜单页**，按角色收敛显示。核心模块如下。

### 3.1 风险判定与环境分层

- **四层判定链**：菜单权限 → 能力矩阵（角色 × 能力 × 分层，三态：放行 / 审批 / 拒绝）→
  高危命令字典（命令 × 分层）→ 无 WHERE 拦截（分层）。四层规则**全部按分层存储**，
  在线可改、即改即生效。
- **分层承载规则，环境归属实例**：内置 `prod` 生产 / `gli` 法务 / `staging` 预发布 /
  `uat` 演练 / `dev` 开发五个分层；可自建环境挂到任一分层，新分层自动克隆规则。
  同一条 `DROP` 在生产分层拦截转审批，在开发分层直接放行。
- **多语句整批判定**：批量粘贴的语句逐条判级、取最严格结论；预检 / 同步执行 / 异步执行
  三条路径结论一致，工单聚合展示全部命中规则。
- **按引擎方言判定**：MySQL / PostgreSQL / Oracle / MongoDB 语法差异独立处理，注释剥离
  防绕过。`EXPLAIN` 按只读判，但 `EXPLAIN ANALYZE`、`EXPLAIN PERFORMANCE` 等**会真实执行**
  被包住语句的形式按真实执行判。
- **能力维度 8 项**：`SELECT`、`INSERT·UPDATE`、`DDL`、`GRANT`、管理连接、审批、`EXPLAIN`、
  发起发布单。

### 3.2 Web 终端

基于 xterm.js 的真实终端：WebSocket 流式执行、psql/mysql 风格元命令、实例树三级组织
（环境 → 类型 → 实例）、搜索覆盖实例/库/表、结果网格与垂直显示、会话日志一键导出
（含审计标注、口令全引擎脱敏）、快捷脚本 `Alt+1…9` 一键执行。

Oracle 的对象树第二层为 **OWNER（schema）** 而非服务名；终端内切换 schema 后触发的工单、
审计与后台任务记录的均为该 schema，批准后执行会切回同一位置。

### 3.3 审批与流程

- 多步审批链、超时策略（自动拒绝 / 自动升级 / 继续等待）、自审开关、服务端分页搜索。
- **通过不执行**：通过后通知发起人，由人回到页面点「执行」；一张单只能执行一次
  （`WHERE executed_at IS NULL` 数据库层兜底），执行前再判一次规则。
- **最终状态以数据库上那次执行的结果为准**：目标库拒绝了这条语句，单子显示失败，
  而不是「已执行」。
- **外部飞书审批**：高危命令推送交互卡片，回调驱动执行；回调带签名校验 + IP 白名单，
  外发内容全量脱敏。
- **执行窗口（班车）**：按库开启、到点自动关闭、只把"需审批"降为"放行"；窗口放行的每条
  命令，审计记录指回是哪扇窗放的；窗口内执行记录单独一页回看，且**不按人收窄**——
  免审批的门免掉的是审批，也就免掉了签字的人，一份只剩"我自己跑的那两条"的回看没有监督价值。

### 3.4 变更发布流水线

流程可自定义，阶段类型含：规范审查 / 人工审批 / 备份回滚点 / 执行变更 / 执行后校验 /
人工确认 / 结果通知；可按分层限定流程。发布单以 pipeline 形式展示每阶段状态、耗时与日志。

**发布不是执行旁路**：执行阶段下发前再判一次闸门——发布单可能在审批里停了数小时，期间
字典、实例归属、发起人角色都可能变化，判定按语句下发那一刻的规则计算，并逐条写审计。
网关重启时：`running` 判失败（执行结果未知，不重跑）、`waiting` 原样保留、`pending` 重新入队。

### 3.5 数据库规范审查

**87 条内置规则**，依据公司四份规范（MySQL / TiDB / Oracle / DWS）重写，每条标注规范分级
与出处，覆盖 DML、DDL、表结构、命名、索引、安全、性能七类，按方言作用域生效。

规则的级别、开关、参数、文案均存于数据库，控制台即改即生效；系统升级只补新增规则，不覆盖
运维已调整的策略。可作为 CI 合并前门禁调用（`POST /api/v1/open/sql-review`，只审查不建单）。

它判的是"**写得对不对**"，与高危命令字典判的"**危不危险**"是两件事，互不干扰。

### 3.6 审计与哈希链

审计表回答同一句话的六个部分：**什么时候、谁、从哪台机器、对哪个库、做了什么、结果如何**。

- **单行内容**：时刻 · 操作人 + 来源 IP · 实例 + 库.表 · 命令原文 · 事件类型 · 增删改查 ·
  风险 · 结果 · 授权它的工单号 · 环境与分层双快照 · 链式校验值。
- **哈希链**：`hash = SHA256(前一行 hash ‖ 本行内容快照)`，`prev_hash` 上有唯一索引，
  链在数据库层分不了叉；改掉中间任何一行，其后每一行都对不上，改一行的代价是重写整条尾巴。
- **可校验**：`vela-gateway verify-audit`（链断退出码 2，可直接接入巡检告警）、
  `GET /api/v1/audit/verify`、审计页按钮，三个入口共用同一套判断，报告第一处断点及其性质
  （内容被改 / 中间有增删 / 按更老键集重算）。

> **能力边界已明确写入文档**：载荷为裸 SHA-256、算法公开，拥有数据库写权限者可重写整条
> 尾巴而链仍自洽。因此它挡的是"顺手改一行"，挡不住有备而来的重写。真正的核对发生在网关
> 之外——Webhook 推送到 SIEM 的副本是只进不出的，两边比对才构成核对。相关载荷生成函数
> 已导出，供链外核对工具直接调用。

### 3.7 数据安全

| 措施 | 说明 |
|---|---|
| 敏感字段脱敏 | 落在结果离开网关之前；全网关仅两处读行（终端结果与导出），两处共用同一层；端到端测试直接断言原始响应体中明文一个字节都不出现 |
| 导出加密 | 约 100MB 分卷、AES-256 加密 zip，按任务发放解压口令；失败任务不遗留孤儿文件 |
| 连接口令 | AES-GCM 静态加密；加密密钥与 JWT 密钥解耦，支持 JWT 轮换 |
| 会话安全 | 会话 TTL、空闲自动锁定、TOTP MFA（含生产操作步进验证）、登录 IP 白名单 |
| 来源 IP 防伪 | 仅信任显式配置的反向代理，客户端无法靠 `X-Forwarded-For` 伪造 |
| 安全响应头 | `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`；终止 TLS 时加 HSTS |
| 接口文档暴露面 | Swagger UI 仅在本地开发环境挂载——生产上把完整路由表交给未鉴权访客，等于提供一份攻击地图 |

### 4.1 测试体系（实测数据）

| 前端单元测试 | **225 个用例**（25 个文件） | Playwright runner 跑纯逻辑：终端行编辑器、控制字符渲染、会话日志脱敏、词条一致性等 |

| 构建期检查 | `vue-tsc` 类型检查 + vue-i18n 严格模式预编译 | 非法国际化文案直接导致构建失败，不会留到运行时 |

黑盒回归网是质量策略的核心：它不 mock 内部依赖，而是启动完整应用、通过 HTTP 接口验证
判定链、多语句处理、审批链、审计链与校验、脱敏、导出上限、执行窗口、会话安全等行为。
代价是整包运行约 20 分钟（实测 1204 秒），收益是重构内部实现不会让测试失效，而行为一旦
回退必然被捕获。

**最近一次全量验证（2026-09-18，安全复核修复后）**：后端 `go test ./...` **0 失败**；
前端 `npm run build`（含类型检查与国际化严格预编译）、**225** 个单元用例、**63** 个 e2e
用例全部通过。

### 4.2 接口契约防漂移

三个静态测试守护 OpenAPI 契约与实际路由的一致性：

- `TestOpenAPICoversEveryRoute` —— 新增路由未写进文档则失败；
- `TestOpenAPIDocumentsNoGhostRoutes` —— 文档中描述了不存在的路由则失败；
- `TestOpenAPIDeclaresGuards` —— 带守卫的路由若未在摘要中标明守卫则失败。

当前契约覆盖 **141 条路由 / 111 条路径 / 140 个操作**，与代码强制同步。文档漂移这类问题
通常要到集成方对接失败时才暴露，把它降级成一次构建失败是成本最低的处置方式。

### 4.3 安全审计

**2026-09-02 白盒代码安全审计**（针对 `backend/`，按攻击面分派 5 组审计代理研究，关键发现
逐条核实 file:line 证据）：

| 严重度 | 总数 | 已修复 | 部分处置 | 接受为设计边界 |
|---|---|---|---|---|
| High | 2 | **2** | 0 | 0 |
| Medium | 11 | 9 | 2 | 0 |
| Low | 19 | 11 | 3 | 4 |

2026-09-18 对全部发现逐条回查代码，**仍然成立的缺口当场修复**，明细与代码依据见
`docs/白盒安全审计报告.md` 第八节。本轮共修复 10 项（M-3 / M-6 / M-10 及 8 项 Low；M-8 部分处置，L-9 经复核后撤回），
并顺带发现修复了一处不在原报告内的缺陷。

**两项 High 均已闭环**。本轮修复中影响面最大的三项：

- **M-6**：MFA 宽限期原先绑定的是用户级会话代次，被盗令牌可在宽限期内绕过生产二次验证。
  现已为 JWT 签发唯一 `jti`，宽限期绑定到单个会话；无会话标识时每次都要求步进验证。
- **M-10**：敏感字段脱敏可被派生表别名绕过，而**导出**路径产出可带走的 CSV，正是
  「敏感导出需审批」要拦的东西。现对「触及敏感表 + 使用派生表/UNION/CTE」的查询强制
  转为敏感导出走审批。终端路径维持既有边界（防「顺手看到」，不防外泄）。
- **L-5**：TOTP 种子由明文改为静态加密存储，存量明文行经无前缀放行照常可用。

**仍保留的取舍（已在审计报告中说明理由）**：

- **M-11**：审计写入失败仍不阻断动作——动作已落在目标库上，回滚不了，把调用方变成失败
  只会让人以为没执行而重试。改为计数并由 `GET /healthz` 的 `auditWriteFailures` 暴露，
  代价由「失败必须看得见」补偿。
- **L-10**（审批链多步名义化）需重新设计审批链模型，建议单独立项。
- **L-12**（哈希链无密钥）与终端脱敏边界均已在 `README.md` 公开声明。

#### 回归网在本轮挡下了两次错误修改

这一轮有两处改动通过了编译、也符合审计建议，但被回归网拦下，值得记录：

1. **「自助启用 MFA 后提升令牌代次」** —— 出自审计的修复建议，实测发现它会让用户一启用
   MFA 就被踢下线：操作者本人刚用有效码证明了持有第二因子，却被打断流程重新登录，
   换不来任何防护。已撤回，改以「要求携带当前口令」列为后续项（需接口变更）。
2. **「收紧敏感字段清单的读权限」** —— 为堵一个 Low 级的字段名泄露，把读权限从终端菜单
   收成管理员专属。测试 `TestSensitive_MutationsAreAdminOnly` 当场失败，其断言旁写着理由：
   结果里出现星号时，「这一列为什么看不到」必须有一个人自己查得到的答案。已撤回。

两次都是推翻了一个有测试守着的既有设计决策。**修复建议是建议，不是规范**；而一条写清了
理由的测试，比任何评审意见都更可靠地保住了设计意图。这正是把黑盒回归网做到 165 个文件
所买到的东西。

### 4.4 模拟实现治理

项目早期曾发生一次典型误判：「批量巡检」把 88 台实例全部报为「可连」，而其中部分实例
连拨号都超时——原因是连接测试自仓库首笔提交起就是一个不拨号的桩函数，且未登记在任何
待办中，潜伏近两个月。

> 一个永远说好话的巡检比没有巡检更糟：没有巡检时人会自己去试，有一个说「可连」的巡检
> 时人不会。

由此确立了三条规矩并落为强制机制：

| 规矩 | 机制 |
|---|---|
| 生产环境下任何已实现功能必须是真实现 | 总开关 `AllowSimulation` **默认 `false`**，仅在非生产环境开启；生产下所有模拟路径一律拒绝并明确告知"问题在网关这边、不在远端" |
| 新增模拟实现必须登记 | 代码内标记 + `docs/simulated-paths.md` 清单，二者缺一即测试失败 |
| 模拟执行不得记成「已执行」 | 单设 `ResultSimulated` 状态——审计链的全部价值在于它不说假话 |

四个测试守护上述规矩，其中三个**接在 `build.sh` 中、于编译之前执行，跑不过就不出包**：

- `TestProductionServesNoSimulatedData` —— 关闭模拟后每条路径必须拒绝而非返回数据；
- `TestSimulationDefaultsToOff` —— 源码默认值必须为 `false`；
- `TestSimulatedPathsAreDocumented` —— 新增未登记 / 清单残留已删条目均失败；
- `TestAudit_SimulatedRunIsNotRecordedAsExecuted` —— 模拟执行不得写成已执行。

上述守卫均验证过"会咬人"：临时植入未登记标记、临时将默认值改为 `true`，构建即在该步
退出且不产出二进制；撤销后恢复通过。

新增代码的标准做法已改为**拒绝并说明原因**（如元数据探查、对象编译、无效对象清点、
连接探活），不再提供模拟分支——一份空清单读起来像"这台库很干净"，一句"已接入网关"
读起来像"那台库是好的"，把"我们没配凭据"说成"远端的状况"是最坏的一种失真。

### 4.5 工程实践

- **架构决策记录 14 篇**，每项重要决策留下背景、备选方案与取舍理由，避免后来者在不知情的
  情况下把有意的设计当成缺陷"修掉"。
- **数据库迁移 41 个**，按序号管理、幂等执行，并有静态守卫测试（ADR 0016）。
- **注释记录"为什么"而非"是什么"**：多处关键修复在注释中写明原先的错误写法、它为何不报错、
  以及正确写法，使同类错误不会在后续重构中复现。

## 六、运行与部署情况

- **部署形态**：`/opt/db-gateway` 目录 + systemd 托管 + 同机 Nginx 反向代理
  （终止 TLS、WebSocket 透传、长连接超时 3600 秒）。
- **升级方式**：停服 → 解包 → 执行迁移 → 启动 → 验证，全过程 1–3 分钟；纯前端变更可
  免停机热更。
- **运维规程**：已形成《上线部署 SOP》，含一页速查、三类部署场景、故障定位表、
  上线后验证清单、回滚判定（依据是否执行过迁移分两条路径）与日常巡检项。
- **日常巡检建议**：每日执行 `verify-audit`（退出码 2 直接接告警）、每日数据库备份、
  每月在备份库上校验一次哈希链、每次重启查看「审批人自检」告警。

> 「审批人自检」值得单独说明：网关每次启动会检查各审批环节是否仍有人能批。其中一种情形
> 是——审批链上恰好只有一个人且未开启自审批，则由他本人发起的工单永远无人可批。这类缺陷
> 不报任何错误，表现只是工单静静堆在待办里，因此把它做成启动期告警而非运行期错误。

## 七、存在问题与后续规划

本节如实列出当前已知的局限，不作回避。

### 7.1 已知局限

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | 审计哈希链为裸 SHA-256，算法公开 | 拥有数据库写权限者可重写整条尾巴而链仍自洽 | 改用 HMAC（引入密钥），或将链尾定期外推至网关不可写的存储；当前已通过 Webhook 推送 SIEM 部分缓解 |
| 2 | M-11：审计写入失败不阻断已发生的动作 | 极端情况下审计链出现缺口 | 已改为计数 + `GET /healthz` 暴露 `auditWriteFailures`，**非零即应告警**。改为阻断需先理顺「先写审计再执行」的顺序，属结构性调整 |
| 3 | L-10：审批链多步名义化 | 多步审批的归因与快照失效语义不严谨 | 需重新设计审批链模型，建议单独立项 |
| 4 | L-14：至静加密密钥仅告警不强制 | 弱密钥可长期存在 | 刻意如此——换密钥会让存量密文全部解不开。需配套「重置全部已存连接口令」的运维流程后才谈强制 |
| 5 | 部署模板路径与实际生产目录不一致 | systemd 模板写 `/opt/vela-gateway`，实际为 `/opt/db-gateway` | 已在 SOP 中标注，建议统一模板 |
| 6 | 后端测试整包耗时约 20 分钟 | 影响本地迭代与 CI 反馈速度 | 按包分组并行执行，或将黑盒回归网移至合并前流水线单独执行 |
| 7 | 开发环境下 5 条模拟路径对用户不可分辨 | 仅影响开发环境（生产一律拒绝，见 4.4） | 终端标注「模拟结果」，或将演示数据集整体改为真实 SQLite 文件并删除模拟分支 |

> 第 7 项不构成生产风险：`docs/simulated-paths.md` 完整登记了现存 5 条模拟路径，且构建期
> 守卫确保生产包不含可返回合成数据的路径。列出它是为了记录这笔技术债的处置方向。
>
> 原列于此处的 M-3 / M-6 / M-8 与 9 条待核实的 Low 级发现，已于 2026-09-18 逐条核实并
> 修复，不再是待办；见 `docs/白盒安全审计报告.md` 第八节。

### 7.2 后续规划

| 方向 | 内容 | 优先级 |

## 八、结论

项目已完成既定建设目标，形成一套可独立部署、可在线配置、可完整追溯的数据库访问管控网关。
系统以"统一入口 + 分层规则 + 流程闭环 + 不可否认审计"为主线，六条执行通道共用同一判定链，
不存在绕过路径；关键异常路径一律 fail-closed；核心行为由 824 个后端测试与 165 个黑盒回归
测试文件守护。

经 2026-09-02 白盒安全审计，并于 2026-09-18 对全部发现逐条复核与修复：2 项 High **均已闭环**；
11 项 Medium 中 9 项已修复、2 项部分处置；19 项 Low 中 11 项已修复、3 项部分处置、4 项作为
已说明的设计边界接受。复核过程还发现并修复了一处不在原报告内的缺陷（一条因转义丢失而从未
生效的规范审查正则），并有两处改动被回归网拦下后撤回（见 4.3）。系统具备生产运行条件，
配套《上线部署 SOP》可支撑常规运维与故障处置。

同时，审计哈希链的能力边界、安全审计文档的闭环记录，以及若干技术债，已在第七章如实列出
并给出处置建议，建议随验收一并确认排期。
