# 网关自身存储全面转 PostgreSQL

日期：2026-09-15 · 分支：`feat/postgres-storage`

## 背景

网关自身的元数据库目前是双轨的：`env=dev` 走 SQLite（`bootstrap/db.go` + GORM
AutoMigrate），`env=prod` 走 MySQL（`migrations/*.sql`，44 个 MySQL 8 方言文件）。
两条轨道意味着两份 schema 权威源——`db.go` 里那段关于 `tier_code` 重命名的注释记录
了这个设计一次真实的失效：boot 路径漏掉了改名，AutoMigrate 在已填充的 `env` 旁边
建了一个空的 `tier_code`，而空值在两处查询里都读作「放行」，于是网关带着一副失效的
管控上线且健康检查全绿。

本次把两条轨道并成一条：**PostgreSQL 是网关自身唯一的存储**。

## 范围

### 改

`backend/internal/bootstrap/`、`backend/migrations/`、`backend/configs/`、
测试建库路径、启动脚本、`docker-compose.yml`、README / DEPLOY / CLAUDE.md。

### 明确不改

- `internal/gateway/realdb.go` 及其 MySQL / TiDB / Oracle / SQLite / GaussDB(DWS)
  驱动。**纳管 MySQL 实例是产品能力**，与「网关自己把数据存在哪」是两件事。
- `docs/MySQL規範.md`、`docs/TIDB規範.md`、`docs/DWS对象设计和业务开发规范-ABLE.md`
  —— 这些是 SQL 审查规则库的输入，描述的是目标库。
- `backend/target.db` —— 演示用的目标库数据。

### 为什么应用层几乎不用动

`internal/repository` 与 `internal/service` 全部走 GORM 构建器，raw SQL 仅 2 处，
没有 `ON DUPLICATE KEY UPDATE` / `IFNULL` / `GROUP_CONCAT` / `DATE_FORMAT` 这类
MySQL 专有写法。方言集中在三个点：`migrations/*.sql`、`migrate.go` 的 `GET_LOCK`
迁移锁、`db.go` 的驱动分支。

## 一、连接层

`bootstrap/db.go` 的三分支 switch 塌成单一路径，驱动改用 `gorm.io/driver/postgres`
（底层 pgx）。

依赖变动：

- 移除 `gorm.io/driver/mysql`、`github.com/glebarez/sqlite`
- **保留** `github.com/glebarez/go-sqlite`、`github.com/go-sql-driver/mysql`、
  `github.com/lib/pq`、`github.com/sijms/go-ora/v2` —— 全部是 `realdb.go` 连目标库用的

配置：`Config.Database` 的 `mysql_dsn` + `sqlite_path` 合并为 `postgres_dsn`，
环境变量覆盖键为 `VELA_PG_DSN`（替换 `VELA_MYSQL_DSN`）。`LoadConfig` 中
`dev→sqlite / prod→mysql` 的驱动推导整段删除，`VELA_DB_DRIVER` 一并删除——不再有
可选项。`env` 字段保留，继续决定 seed、JWT 强度校验、CORS 这些**与存储无关**的语义。

默认 DSN 不写死用户名，让 libpq 回落到 OS 用户：

```
host=127.0.0.1 port=5432 dbname=vela_gateway sslmode=disable
```

同时删掉 SQLite 分支里的 `sqlDB.SetMaxOpenConns(1)`——那是 SQLite 单写者限制的
产物，留在 PG 上等于无谓地把连接池锁成串行。

## 二、Schema

### baseline

`migrations/0001_init.sql` 重写为一份 PostgreSQL baseline，表达 0001–0044 累积后的
最终形态；0002–0044 删除。`schema_migrations` 账本机制保留不变。

翻译规则：

| MySQL | PostgreSQL |
|---|---|
| `BIGINT NOT NULL AUTO_INCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| `TINYINT(1)` | `BOOLEAN` |
| `DATETIME(3) DEFAULT CURRENT_TIMESTAMP(3)` | `TIMESTAMPTZ NOT NULL DEFAULT now()` |
| `MEDIUMTEXT` / `LONGTEXT` / `TEXT` | `TEXT` |
| `CHAR(64)` | `VARCHAR(64)` |
| 表内 `UNIQUE KEY x (...)` | 独立 `CREATE UNIQUE INDEX x ON ...` |
| `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4` | 去掉 |
| `CREATE DATABASE IF NOT EXISTS` / `USE` | 去掉（建库是运行前置步骤） |

`CHAR(64)` 必须换成 `VARCHAR(64)`：PG 的 `char(n)` 是 blank-padded 语义，读回 Go
会带尾部空格，而 `audit_chain.go:142` 用的是 Go 侧字符串判等 `a.PrevHash != prev`。
SHA-256 hex 恰好 64 字符时不会触发，但这个陷阱不值得留着。

`tbl_` / `pk_` / `idx_` 命名约定保留（backend 文档 §9），无物理外键的约定保留。

`internal/model` 里的 `type:mediumtext`（8 处）改为 `type:text`——PG 没有长度分级
的 TEXT 变体，留着是误导。

### AutoMigrate 整条路径删除

`autoMigrate()`、`allModels`、`shouldAutoMigrate()` 全部删除。`Migrate()` 直接调
`RunSQLMigrations`，`OpenDB()` 中 AutoMigrate 分支及其 backfill 调用收敛到
`Migrate()` 一处。

这从根上消除了 `db.go` 注释警告过的「两个 schema 来源」问题：SQL 迁移成为唯一权威。
`automigrate_guard_test.go` 改写为断言 AutoMigrate 路径不复存在。

`RunSQLMigrations` 内 `db.AutoMigrate(&schemaMigration{})` 这一处保留——账本表自身
需要自举，且它只有两列，不参与业务 schema。

### 迁移锁

```
SELECT GET_LOCK('vela_schema_migrate', 60)   →  SELECT pg_try_advisory_lock(hashtext('vela_schema_migrate')::bigint)
SELECT RELEASE_LOCK('vela_schema_migrate')   →  SELECT pg_advisory_unlock(hashtext('vela_schema_migrate')::bigint)
```

`migrate.go` 中「必须 pin 同一条 `*sql.Conn` 端到端持有」的推理对 PG 完全成立
（advisory lock 同样是 session 级），那段实现与注释保留，只换 SQL 与 dialector 判断。

用 `pg_try_advisory_lock` 而非 `pg_advisory_lock`：后者无限阻塞，会把「另一个迁移
正在跑」变成一次没有输出的挂起。`try` 版本立即返回 boolean，外面包一个最多 60 秒的
重试循环，即可保住 MySQL 版 `GET_LOCK(..., 60)` 的语义——等待有上限，超时给出明确
错误信息。

## 三、测试

259 个测试文件改为对真实 PostgreSQL 运行，采用 **schema 隔离**而非 database 隔离。

新增 `internal/testsupport` 包，提供 `NewDB(t *testing.T) *gorm.DB`：

1. 连接固定库（默认 `host=127.0.0.1 port=5432 dbname=vela_test sslmode=disable`，
   `VELA_TEST_PG_DSN` 可覆盖）
2. `CREATE SCHEMA t_<random>`，会话 `search_path` 指向它
3. 跑 baseline 迁移
4. `t.Cleanup` 中 `DROP SCHEMA t_<random> CASCADE`

选 schema 而非 database：`CREATE DATABASE` 在 PG 上是重量级操作（要复制模板库），
schema 创建近乎免费，且允许测试并行。baseline 已去掉 `CREATE DATABASE` / `USE`，
天然适配 search_path 隔离。

42 个直接写 `gorm.Open(sqlite.Open(path))` 的测试改调 `testsupport.NewDB(t)`；
其余经 bootstrap helper 建库的自动跟随。

**连不上 PG 时测试失败，不 skip。** 静默跳过等于假绿。错误信息直接给出修复命令：
`createdb vela_test`。

代价（选择「彻底单一化」时已知）：`go test ./...` 从此需要一台运行中的 PostgreSQL，
不再零依赖。

## 四、两处行为回归及其处理

### 4.1 排序规则：大小写敏感性翻转

MySQL 侧是 `utf8mb4_unicode_ci`，字符串比较**不区分大小写**；PostgreSQL 的默认
排序规则**区分大小写**。

已确认的受影响点：`repository.go:55` 的登录查询 `Where("email = ?", email)`。
建用户时 `admin.go:767` 已 `strings.ToLower` 入库，因此在 MySQL 下输入
`Linwei@Vela.io` 能登入，迁到 PG 后同样的输入会登录失败。

**处理**：

1. 登录侧对入参同样 `strings.ToLower` 后再查
2. baseline 中 email 唯一索引建在 `lower(email)` 上：
   `CREATE UNIQUE INDEX idx_user_email ON tbl_user (lower(email));`
3. 通盘排查 `code` / `engine` / `status` / `tier_code` 等判等查询，确认没有别处
   依赖 ci 语义

不引入 `citext` 扩展：它需要 `CREATE EXTENSION` 权限，给本机开发和未来每一处部署
都加一道前置条件，而 `lower()` 函数索引达到同样效果且零依赖。

### 4.2 审计链哈希与时间类型解耦

`audit_chain.go:57` 把时间以 `a.OccurredAt.Format(time.RFC3339)` 喂进链哈希，
该格式**包含时区偏移**。

问题在于读回时 `time.Time` 挂的 Location 取决于驱动与列类型：pgx 读 `TIMESTAMPTZ`
返回会话时区，读 `TIMESTAMP`（无时区）返回 UTC。写入时用 `time.Now()`（Local，
+08:00）算出的哈希，在读侧若得到 `...Z` 形式的字符串，重算必然对不上——**每次链
校验都会失败**。这与有无存量数据无关，换任何 PG 列类型都不能单独解决。

**处理**：把哈希输入规范化，与数据库时间类型解耦。

1. 列类型用 `TIMESTAMPTZ`（语义正确：存的是绝对时刻）
2. `auditPayloadFor` 中时间改为 `a.OccurredAt.UTC().Format(time.RFC3339)`
3. `currentAuditPayloadVersion` 升至 5，沿用既有的逐版尝试机制
   （`matchAuditRow` 从新到旧试）

第 3 点是关键：项目已经为 payload 演进建好了版本机制（v1→v4 对应审计字段的四次
扩展），这次时间规范化正是它设计来承载的那类变更，不需要新机制。升版后读侧对
v5 行用 UTC 格式匹配，对历史行仍按 v1–v4 尝试。
