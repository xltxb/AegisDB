# 前端自适应布局 · 设计

日期：2026-09-16 · 状态：待实现

## 要解决的问题

控制台在 1440/1280/1024/768/390 五档宽度下**都没有页面级横向溢出**——现有 13 处断点起了作用。
问题不是撑破，是挤烂，而且挤烂的地方没人测得到：

| 位置 | 宽度 | 症状（实测） |
|---|---|---|
| 数据源页 8 列表 | 768 | 地址栏折成 6 行、表头「默认角色」断成「默认角/色」、网关策略下拉截成 `audi⌄` |
| 数据源页页头 | 768 | 三个按钮（项目管理/导入实例/新建连接）各折两行 |
| 审计页 `.page-head` | 768 | 内层横滚 638→735 |
| 设置页 `.c-card-row` | 390 | 「默认策略」标签竖成一列单字，提示文字同样 |
| 外壳 `.top-title` | 390 | 「数据库管理网关」竖成一列单字，压在页面标题上；`.shell` 自身溢出 390→423 |

另有两处**不是问题**，实现时不要动：

- 能力矩阵 `.cap-scroll`（768 下 596→937）横滚是有意设计，见
  `components/permission/CapabilityMatrix.tsx` 的注释：「分层多起来之后这张表自己横向滚，
  页面主体不跟着横滚」。
- 终端页 `.tv-grid` 的 1500/1040 两档是**栏宽微调**，不是形态切换。

## 适配下限

**桌面 + 平板 768**。不做手机抽屉导航，侧边栏 72px 图标 rail 在 768 下保留。
390 不是支持目标，但外壳在 390 下**不应自身溢出**——那是 `.top-title` 的折行行为造成的，
顺手修掉，不为 390 做专门布局。

## 一、断点口径

现有 13 处断点散在 **720/900/960/1040/1080/1100/1280/1500** 八个值上。
实测这些值分两簇：720–960（3 处）与 1040–1100（5 处）。据此收敛为**两个通用断点**：

```
narrow   ≤ 768px     只留主干列；页头按钮收进溢出菜单；卡片行上下堆叠
mid      ≤ 1080px    次要列收起；双栏页面折成单栏
wide     > 1080px    完整形态
```

**边界取 1080 而不是 1280**：现有 7 处折叠集中在 1040–1100，上推到 1280 会让
1100–1280 屏宽的用户失去今天已有的双栏密度。收敛的目的是统一口径，不是降低密度。

终端页保留自己的 1280/1500 两档，作为**写明的例外**——它是全站唯一的三栏页面，
栏宽微调与形态切换的阈值本就不该和通用页面共用一个值。

| 现值 | 选择器 | 迁到 |
|---|---|---|
| 1080 | `.chg-wrap, .pl-wrap` | mid |
| 960 | `.chg-body` | mid |
| 960 | `.pl-egrid` | mid |

### 最大宽度

`.page` 1120 / `.page-narrow` 960 / `.perm-page` 1240 / `.chg, .pl` 1320 四个硬上限
改成 `min(100% - 2 * var(--gutter), <各自上限>)`，窄屏自动让出边距，不再硬顶容器边缘。
各自的上限值**保持不变**——它们是排版决定，不是自适应问题。

## 二、表格按优先级隐列

### 现状

全站 **9 张表**，都用 CSS grid 而非 `<table>`（理由见 `components/common/Table.tsx` 的注释：
`<table>` 的列宽由内容决定，同一张表在不同数据下会跳来跳去）。其中：

- **5 张走共用 `Table`**：审计、资产、执行窗口（窗口表 + 放行记录表）、治理
- **4 张手搓 grid**：数据源、用户、环境分层（分层表 + 环境表）——它们有分组行与展开行，
  共用 `Table` 表达不了

### 接口

`Column` 加一个字段，并新增两个**纯函数**：

```ts
/** 1 = 永远在场;2 = narrow 下收起;3 = mid 与 narrow 下都收起。不写视同 1。 */
export type ColPriority = 1 | 2 | 3
export interface Column<Row> { …; priority?: ColPriority }

export type Breakpoint = 'wide' | 'mid' | 'narrow'
export function visibleColumns<R>(cols: Column<R>[], bp: Breakpoint): Column<R>[]
export function gridTemplate<R>(cols: Column<R>[]): string
```

**关键约束：grid 轨道数与单元格数必须始终一致。** 模板和单元格由同一个
`visibleColumns` 结果推出，不各算各的——这是这套改动唯一可能引入的新缺陷类别。

手搓的 4 张表把各自的 `COLS` 字符串换成同一对函数的调用，共用这条约束。

### 断点来源

```ts
/** 只做一件事:订阅 matchMedia,返回当前档。布局计算全在纯函数里,它不参与。 */
export function useBreakpoint(): Breakpoint
```

### 各表优先级

被隐的值进**行展开区**。数据源页与用户页已有行展开，不新造机制；
其余表按需要补一个展开行。

| 表 | 1（永远在场） | 2（narrow 收起） | 3（mid 起收起） |
|---|---|---|---|
| 数据源（8 列） | 勾选框、实例名、状态、操作 | 引擎 | 地址、默认角色、网关策略 |
| 审计（7 列） | 时间、命令、结果 | 执行人、风险 | 实例、审批 |
| 用户（5 列） | 用户、状态 | 角色 | 账号、最近活跃 |
| 执行窗口（6 列） | 窗口、状态、操作 | 数据库 | 时区、生效日 |
| 放行记录（5 列） | 时间、命令 | 风险 | 执行人、实例 |
| 资产（4 列） | 名称、备注 | 类型 | 索引 |
| 治理（5 列） | 字段、操作 | 脱敏方式 | 预览、豁免 |
| 环境分层（8 列） | 分层、默认角色、操作 | 连接层级 | 四个开关列 |
| 环境（4 列） | 环境、归属分层、操作 | 显示名 | —（4 列表在 mid 下不必收列） |

## 三、外壳与页头

- **`.top-title`**：narrow 下不参与折行，改单行省略。这是 390 竖排单字的直接原因。
- **`.pill-health` / `.pill-pending`**：narrow 下只留图标 + 数字，去掉文字标签。
- **页头按钮**：超过两个的，首个保持主按钮，其余收进 `⋯` 溢出菜单。
  影响数据源页（3 个）与其他同形态页头。
- **`.c-card-row`**：narrow 下由「左标题右控件」改为上下堆叠。这是 390 下
  「默认策略」竖成单字列的直接原因，影响整个设置页。
- **rail 不动**：72px 图标栏在 768 下仍然合理。

## 四、测试

两个口各盯各的，不重叠：

**单测**（`tests/unit/`，Node 无浏览器）
- `visibleColumns` 按档收列，优先级不写视同 1
- `gridTemplate` 的轨道数恒等于 `visibleColumns` 的长度——这条守住上面那个关键约束
- 9 张表的列定义各自有一列 priority 1，否则 narrow 下会出现空表

**e2e**（`e2e/responsive.spec.ts`，真浏览器）
- 在 1440 / 1080 / 768 三档遍历全部 19 个页面，断言无页面级横向溢出
- 断言关键文本没被挤成竖排单字：量 `clientWidth` 与 `scrollHeight` 的比，
  一个 4 字标题占 4 行就是塌了
- 断言 `.cap-scroll` 在 768 下**仍然**横滚——它是有意设计，不能被这轮改动"顺手修掉"

e2e 这套检查正是发现上述症状时手工量的那一套，固化下来。

## 不做的事

- 不改任何业务逻辑与接口
- 不做手机（≤480）专门布局
- 不动终端页的 1280/1500 两档栏宽
- 不把 `.cap-scroll` 的横滚"修掉"
- 不做容器查询（`@container`）：grid 模板是 JS 内联字符串，CSS 隐掉单元格后轨道仍在，
  会留空列；除非模板也搬进 CSS，那会让列定义分裂成 JS 定内容、CSS 定宽度两处
