# HUD 视觉升级 · 第二阶段 · 设计

日期：2026-09-20 · 状态：待实现
承接：`docs/superpowers/specs/2026-09-20-hud-visual-refresh-design.md` 第六节

## 要解决的问题

第一阶段把 HUD 装饰挂在了三个共用容器上 —— `.c-card`、`.c-table`、`.dash-card`。
凡是复用这三者的页面，外观自动跟上；总览页一行页面级特例都没写，效果全是共用层给的。

问题出在**没有复用它们的那些页面**。`theme.css` 里一共有 21 个 radius 14 的面板级容器，
上述三个之外的 18 个各自手写了"1px 描边 + 14px 圆角 + surface-card 底"，与卡片长得一样、
但拿不到任何装饰。结果是同一个控制台里两种气质并存：总览、设置、审计像仪表面板，
终端、变更工单、资产目录还是平的。

本轮把那 18 个补齐。

## 非目标

- **不迁移。** 不把这些容器改写成 `<Card>` 或加 `.c-card` 类。它们绝大多数根本不是卡片
  形状 —— 列表行没有卡头，终端分栏是布局容器。硬迁要大改 TSX，回归面覆盖全站最复杂的
  几个页面，收益是负的。本轮只扩展装饰层的选择器。
- **不动布局。** 与第一阶段同一条约束：栏宽、行距、断点、内距一律不改。
- **不动文字色与语义状态色 token。**
- **不碰 `.ib-empty`。** 它是虚线描边的空状态框，不是面板 —— 它要表达的是"这里没有东西",
  给它加高光线和角标等于给一个空盒子挂仪表。
- **不重做第一阶段已装饰的三个容器。**

## 一、三档待遇

装饰分三档，按容器在页面上的**角色**分，不按它长得像什么。

### 第一档 · 面板（12 个）

一页出现一两个的静态容器，就是"卡片换了个名字"。拿**完整装饰**：顶沿渐变高光线 + 右上角
L 形角标，与 `.c-card` 完全一致。

| 容器 | 页面 |
|---|---|
| `.perm-roles` | 权限 · 角色列 |
| `.set-nav` `.set-save` | 系统设置 · 左导航 / 底部保存条 |
| `.cat-side` `.cat-detail` | 数据资产 · 两栏 |
| `.rr-stat` | 风险规则 · 统计卡 |
| `.chg-detail` `.pl-editor` | 变更工单 / 变更流程 · 详情面板 |
| `.ib-side` | 审批待办 · 侧栏（**机制不同，见第二节**） |
| `.notif-panel` `.usermenu` `.conn-bulkbar` | 外壳浮层 |

### 第二档 · 列表行（4 个）

一页重复十几到二十次的卡片式行。拿**顶沿高光线 + hover 抬升**，**不拿角标**。

`.chg-item` `.pl-item` `.aj-item` `.osc-item`

不给角标的理由：一屏二十个角标是噪声，不是科技感。这是第一阶段
「整站卡片一起飘会显得廉价」那条原则的直接延伸 —— 装饰要能回答一个问题，
角标回答的是"这是一块独立面板"，而列表行不是，它们是一列同类项。
它们本来就可点，所以拿 hover 抬升。

### 第三档 · 仪器（1 外框 + 3 栏）

终端页是一个外框包三栏（树 | 终端 | 检查器），不是三张拼在一起的卡。

- **外框 `.tv-grid`**：一圈完整的四角取景框，复用登录页的 `.hud-corners`。
- **`.tv-tree` 与 `.tv-main`**：各自顶沿高光线，**不加角标**。
- **`.tv-insp`**：**不拿顶沿高光线**，改由它的面板头 `.tv-panel-head` 拿渐变分隔线
  （并入 `.c-card-head::after` 那一组）。理由见下面陷阱 3。

**三栏的类名是 `.tv-*` 不是 `.term-*`。** `theme.css` 里还留着一整段 `.term-tree` /
`.term-main` / `.term-insp`（约 615–673 行），那是终端 v1 的样式，TSX 里已无任何引用 ——
是死代码。本轮不清理它（不在范围内），但**绝不能拿它当靶子** ——
装饰挂上去会一条都匹配不到。

读作"一台分了三区的仪器"。`.hud-corners` 本来就是按可复用写的（它只依赖
`--hud-corner` / `--hud-corner-size` 和宿主的 `position: relative`），
本轮是它的第二个宿主 —— 这也顺带验证了那个类名没有写死登录页的假设。

## 二、机制与已查实的陷阱

实现方式统一是**扩展 `hud.css` 的选择器列表**，不新建机制。但五处必须按查实的事实特殊处理。

### 陷阱 1 —— 伪元素冲突不止一处，第一阶段的记录是错的

第一阶段的 spec 写过「`.perm-rcard.on::before` 是全站唯一的伪元素冲突点」。**这句话是错的。**
实测 `theme.css` 里还有两处同样的模式：

```
.chg-item.on::before        选中态左色条
.pl-item.on::before         选中态左色条
```

三处都是同一个手法 —— 选中时在左侧画一根 3px 竖条。

**后果**：第二档"列表行"里有两个容器的 `::before` 已被占用。因此**整个第二档改用 `::after`
承载高光线**，四个容器统一。不做"两个用 `::after`、两个用 `::before`"的分裂 ——
同一档待遇用两种机制，下一个维护者要读两遍才知道它们是一回事。

`::after` 在这四个容器上均未被占用（已核）。

### 陷阱 2 —— `.ib-side` 是滚动容器

```
.ib-side { overflow: auto; position: sticky; }
```

绝对定位的伪元素会跟着内容滚出可视区。它的高光线必须走 `background-image`
（`background-attachment` 默认 `scroll`，锚在元素自己的边框盒上），
与 `.c-table` 和 `.rail` 同一个做法。

这是本项目第三次遇到这个坑 —— 前两次分别在第一阶段的 Task 2 和 Task 6。
本轮的测试为此专设一条普查断言，见第三节。

### 陷阱 3 —— 终端三栏各不相同，不能一视同仁

实测（`.tv-*`，v2 的真实类名）：

| 栏 | overflow | position | 首个子元素 | 结论 |
|---|---|---|---|---|
| `.tv-tree` | `hidden` | 无 | `.tv-head`，无底色 | 补 `relative`，伪元素安全 |
| `.tv-main` | 未声明（visible） | `relative` | `.tv-edge`，绝对定位 | 伪元素安全，不动 position |
| `.tv-insp` | **`auto`** | 无（≤1280 变 absolute） | `.tv-panel-head`，**不透明底色** | 两条路都堵死，见下 |

`.tv-insp` 是本轮第四个滚动容器，所以不能用绝对定位的伪元素。而 `background-image`
这条退路也走不通 —— 它的首个子元素 `.tv-panel-head` 带 `background: var(--surface-sunken)`，
会把容器自身画在顶沿的那条线整个盖住。

**所以 `.tv-insp` 改拿另一种待遇**：它的面板头就是这一栏真正的顶沿，那条头下分隔线
并入 `.c-card-head::after` 那一组，拿渐变化。这不是退让 —— `.c-card` 有卡头就用卡头分隔线，
`.tv-insp` 有面板头，走同一条规则才是一致的。

顺带一条不要推错的：`.tv-tree` 里真正滚动的是它的孩子 `.tv-tree-list`，
栏本身是 `hidden`。不要因为"终端页会滚"就把三栏一律判成滚动容器。

### 陷阱 4 —— `.tv-grid` 里有滑入式检查器

```
.tv-grid            { overflow: hidden; position: relative; }
.tv-grid > .tv-insp { position: absolute; }   translateX(100%) 滑入
```

取景框必须 `pointer-events: none`，且其层叠位置不能挡住检查器的滑入动画。
`.hud-corners` 已经是 `pointer-events: none`，本轮只需确认它在 `.tv-grid` 里
不参与那条 transform 的层叠。

### 陷阱 5 —— 三个浮层只能拿纯伪元素

```
.notif-panel  { position: absolute; overflow: hidden; }
.usermenu     { position: fixed; }
.conn-bulkbar { position: fixed; }
```

`.notif-panel` 刚在第一阶段的收尾审查里以 Critical 出过事 —— 两个各自正确的改动
（`.main > *` 的 z-index 与 `.top` 的 `backdrop-filter`）合起来把它压到了内容之下、
并把它的全屏遮罩塌成了 54px。

因此本轮对这三个容器的装饰**只能是一条 `::before` 高光线加一条 `::after` 角标**，
**不得引入任何新的 `position`、`z-index`、`filter`、`backdrop-filter` 或 `isolation`**。
它们已经有自己的定位上下文，加装饰不该动它。

## 三、测试

除每档一条"装饰确实挂上了"的断言外，本轮补三条第一阶段**没有**的结构性守卫。
它们存在的理由是：第一阶段的四角取景框 bug 带着 30 条绿色断言上线，
因为没有一条断言问过"形状对不对"；而滚动容器的坑犯了两次，因为没有一条断言问过
"这个容器会不会滚"。

### 守卫 1 —— 滚动容器普查

对每个目标容器读 `overflow-x` / `overflow-y`；凡解析为 `auto` 或 `scroll` 的，
断言其 `::before` 与 `::after` 的 `background-image` 均为 `none`（即它必须走
元素自身的 `background-image`）。

这一条不针对某个容器，而是针对**这一类错误**。将来任何人把一个容器改成可滚动，
这条会立刻红。

### 守卫 2 —— 选中态色条普查

三处 `.on::before` 选中色条（`.perm-rcard` `.chg-item` `.pl-item`）各断言一次
宽度仍为 3px。装饰不得覆盖选中态 —— 那是这三个容器上唯一承载"现在选的是哪一个"
的视觉元素。

### 守卫 3 —— 覆盖数量断言

断言拿到面板级装饰的容器数、拿到列表行装饰的容器数各自等于预期值。
防两件事：漏掉一个容器（装饰不全），以及选择器写宽了误伤别的容器（装饰过度）。

### 既有回归

`responsive.spec.ts`（五档宽度无横向溢出、侧栏滚动不压扁）与
`reduced-motion.spec.ts` 必须保持全绿。终端页在 `responsive.spec.ts` 里有
1500/1280/1040 三档自己的断言，本轮动了它的外框与三栏，这三档是重点。

## 四、验收

### 自动化

`npm run build` + `npm run test:unit` + `npm run test:e2e` 全绿。
当前基线：build 干净、291 单测、78 e2e。

### 人工

5 个代表页 × 亮暗 = 10 张截图。选这五个不是因为它们好看，是因为它们各自能暴露一类问题：

| 页面 | 它能暴露什么 |
|---|---|
| 终端 | 全站信息密度最高的屏，也是本轮唯一的"仪器"档；装饰在这里最容易从氛围变成干扰 |
| 变更工单 | 长列表 —— 十几条高光线叠在一起是什么观感，只有真数据能回答 |
| 权限 | 唯一同时有面板档（`.perm-roles`）和选中态色条冲突的页面 |
| 资产目录 | 双栏面板，两个容器挨着，能看出高光线与角标会不会互相打架 |
| 审批待办 | 唯一的 `background-image` 机制容器（`.ib-side`），外加空状态 |

对照四条标准（与第一阶段同一套）：

1. 装饰读作底座与分层，不读作色斑与噪声。长列表页尤其看这条。
2. 暗色靠高光线与角标分层，不靠投影。
3. 终端页的信息密度没有被装饰吃掉 —— 该读的还是一眼能读。
4. 选中态（三处色条）在装饰加上之后仍然一眼可辨。

十张图过了，第二阶段收尾。

## 五、不在本轮

- `.ib-empty`（虚线空态框）—— 见非目标。
- `.scan-nums b`（脚本扫描弹窗的大数字）—— 第一阶段留下的唯一一处数字不一致。
  它在弹窗里，与本轮的容器装饰不是一类问题，单独处理。
- 把 `.hud-corners` 之外的装饰也做成可复用类。本轮两个宿主还不足以证明第三种抽象是需要的。
- **清理 `theme.css` 里终端 v1 的死样式**（`.term-tree` / `.term-main` / `.term-insp` 一段，
  约 615–673 行，TSX 无任何引用）。发现于本轮预检，但删死代码是另一件事，
  与视觉改造混在一个分支里会让回归范围说不清。单独处理。
