# 23 · Oracle 无效对象的清点与批量重编译

Status: ready-for-human（已实现，**逻辑有测试，真机未验收**）

关联 issue 15/16（对象浏览与单个编译）、issue 21（Oracle 表结构）。

## 需求

"oracle 实现一下无效对象的重新编译"。

## 背景

单个对象的重新编译早就有（树里 DDL 弹窗上的「编译」按钮）。缺的是**批量**：一次表结构
变更、一次被依赖过程的重建，能让几十个包、视图、触发器一起变成 INVALID。Oracle 会在
下次调用时**隐式**重编译，所以它们看起来还能用 —— 直到某个业务请求第一次踩上去，
编译错误才在生产流量里出现。

这就是 `utlrp` / `UTL_RECOMP` 做的事，但那两个要 SYSDBA，而网关连的是业务账号。所以
自己走一遍：清点 → 判定 → 逐个编 → 回读状态。

## 实现

后端 `gateway/oracle_invalid.go` + `service/oracle_invalid.go` + 两个路由；
前端新组件 `components/terminal/InvalidObjects.vue`。

### 四条必须守住的

1. **执行仍然走单个编译那条路**（`RealCompileObject`）。批量**不是**一条新的下发通道，
   它只是把同一件事做 N 次 —— 包括"`ALTER … COMPILE` 即使失败也返回成功、必须回读
   `all_objects.status` 与 `all_errors`"这条。另起一条更快的路，等于给自己留一个不回读
   的后门。
2. **判定一次，判的是全部语句。** 把这批要执行的 ALTER 全部拼出来交给同一个
   `strictestVerdict`：只要其中任何一条在这台实例上是 deny 或需审批，**整批都不执行**。
   逐个判、能编的先编，是最糟的形态 —— 它会在一个需要审批的库上留下"编了一半"。
3. **多轮。** 编译顺序影响结果：先编了依赖别人的那个，它照样失败；等被依赖的编好了，
   它才能过。规则是"上一轮修好了至少一个就再来一轮"，最多三轮 —— 一轮零进展说明剩下的
   是真编不过，不是顺序问题，再编只是白编 + 三倍审计噪音。
4. **逐个记审计**，不是一行"批量编译了 12 个"。审计要回答"三个月后：那天凌晨到底动了
   哪些对象、结果如何"。每个对象一行，记的是它这次的**最终**状态（中间轮次不单独记，
   与单个编译一次记一行保持一致）。

### 另外三个取舍

- **上限 200**，超出的在 `report.skipped` 里**明确报告**。悄悄只做一半的后果是有人以为
  清干净了。
- **顺带给编译加了 VIEW / MATERIALIZED VIEW**。它们同样会因底表变更而 INVALID，而且是
  批量重编译里最常见的两类，原来的 `oracleCompileSQL` 只认存储程序。视图只有一个编译
  单元，别照抄包那套"再编一次 BODY"（有测试钉住）。
- **同义词、Java 类等不进清单**。它们也会 INVALID，但 `ALTER … COMPILE` 修不了；列出来
  只会让人以为按一下就好了。

### 接口

| 方法 | 路径 | 闸 |
|---|---|---|
| GET | `/connections/{id}/objects/invalid?scope=` | `[terminal]` + 标签授权；**只读，不走 DDL 闸** |
| POST | `/connections/{id}/objects/recompile` | `[terminal]` + 标签授权 + 整批 DDL 判定 |

模拟连接（无凭据）**报错而不是回空清单** —— 一份空清单读起来是"这个 schema 很干净"，
而真相是"我根本没看"。这是这个功能最坏的失败方式。

### 前端

`InvalidObjects.vue` 挂在树里 owner 节点下（编译就是按 owner 走的），**只在真有 INVALID
时出现**：一行"0 个无效对象"挂在每个 schema 下，在一棵已经很密的树里是纯噪音，而这一行
是红的、有数字、能点 —— 它出现本身就是那条信息。点击先确认（说明这是一批 DDL），结果
逐个列出，编不过的带 `all_errors` 的行列与文本。编完按真实状态重新清点，而不是按
"我以为都修好了"更新界面。

## 回归测试

`gateway/oracle_invalid_test.go`（7 组）：多轮修好依赖顺序、一轮零进展就停（并断言编译
次数）、单个出错不拖垮整批、审计回调每对象一次且带最终结果、空批次、object_type 映射
（含"清点的类型必须都有对应编译类型"这条交叉检查）、视图/物化视图的 ALTER 写法与单元数。

编译动作是**注入**进去的（`recompileWith`）—— 没有真实 Oracle，这是唯一能钉住多轮规则
的办法，而多轮规则退化之后照样返回一份看起来正常的报告。

`bootstrap/oracle_invalid_test.go`（5 组）：非 Oracle 引擎两个端点都拒、无凭据时明说而不是
装干净、标签范围之外的人既不能编也不能看清单。

后端全量 `go test ./... -timeout 20m`（README 要求的写法）+ 前端 `npm run build`（含
`vue-tsc`）。

## 待真实环境验收

- **所有 SQL 都没有在真实 Oracle 上跑过**：`all_objects` 的清点查询、`ALTER VIEW …
  COMPILE` / `ALTER MATERIALIZED VIEW … COMPILE` 的实际行为。
- 一个真有几十个 INVALID 对象的 schema 上，三轮够不够；不够的话上限（`maxRecompilePasses`）
  要不要提。
- 200 的上限在你们最大的 schema 上是不是太小。

## 没有做

- **不做依赖排序**。理论上可以读 `all_dependencies` 拓扑排序后一轮编完，但那是一张有环
  的图（包与包体互相引用很常见），排序本身要处理环，而"多编两轮"已经解决了同一个问题。
  真实环境上如果三轮还剩很多，再考虑。
- **不做后台异步**。批量编译是变更窗口里的动作，人就在屏幕前等着看结果；做成异步任务
  反而要再造一套查看进度的界面。上限 200 就是为了让它能同步跑完。
