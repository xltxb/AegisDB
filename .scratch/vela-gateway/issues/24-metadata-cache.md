# 24 · 远端库的表清单与表结构,在本地留一份

Status: ready-for-human（已实现；SQLite 一路真机验过，MySQL / PostgreSQL / Oracle 待真实环境验收）

## 需求

"加一个本地表存储远端数据库的数据库表清单和表结构信息。"

两处岔路当场问过，答复是：**表清单 + 列结构**（不是只要表名，也不是存 DDL 原文）、
**后台定时全量**（不是手动触发、也不是浏览到哪缓存到哪）。

## 为什么

在此之前，树每展开一次就实时探一次目标库，而"在所有实例里找某张表"意味着挨个连
88 台生产实例问一遍——慢，而且把一次界面操作变成了一轮对生产的扫描。

**按列名找**则根本做不到：那意味着把每台实例的每张表都问一遍列。有了本地副本，
"哪些表里有 id_card 这一列"才成为一次普通查询。

## 这份数据是什么，不是什么

它是**只读副本，不是真相**。判定、执行、导出一律仍然走实时的目标库——一份可能过期
的结构如果被拿去做判断，它就从"快"变成了"错"。

所以每一行都带 `synced_at`，界面必须把"这份数据是什么时候的"显示出来：一个不说明
年龄的缓存，读的人会当成现状。

## 三张表

| 表 | 一行是 |
|---|---|
| `tbl_meta_table` | 一张表（或视图）：库 / schema / 表名 / 类型 / 注释 |
| `tbl_meta_column` | 一列：序号 / 名字 / 类型 / 可空 / 默认值 / 注释 / 是否主键 |
| `tbl_meta_sync` | 每台实例最近一次同步的结果：起止时间、库/表/列数、失败原因 |

第三张不是可有可无的：没有它，"这台实例为什么一张表都没有"没有答案——是还没轮到
它、连不上、账号没权限，还是它真的空着？这四种在界面上长得一模一样，而只有第一种
是正常的。所以 `sync` 为 null（没同步过）和 `sync.err` 非空（同步失败）在接口上是
分开的两件事。

## 刻意的取舍

**一台实例尽可能少的查询。** 按表去问列，843 张表就是 843 次往返，定时任务这么跑
等于周期性地对生产发起扫描。MySQL / Oracle 用全库字典视图，两条查询覆盖整台实例；
SQLite 用表值函数 `pragma_table_info` 把 pragma 展开成一次连接查询。

**PostgreSQL 家族只同步连接上配置的那个库。** 它的目录按库隔离，读别的库必须重新
建连接，而连接凭据未必在每个库上都成立。口径与树的浏览一致（见 `RealSchema` 的 pg
分支），不另立一套。要覆盖更多库就为它们各配一条连接。

**整台实例先删后插，一次事务。** 增量更新在这里是错的方向：一次同步拿到的是一张
完整的照片，用它整个替换天然就把消失的表带走了；增量则要额外回答"哪些行该删"，
答错的表现是缓存里留着一张早已不存在的表，而它看起来和真表一模一样。事务保证中途
失败时缓存要么是旧的那份、要么是新的那份，不会是"删了一半"——一个只剩一半表的缓存
比一个过期的缓存糟得多，过期的至少还是自洽的。

**不做外键。** 同步是整台删了重写，外键只会把那次删除变成一场级联风暴；而这份数据
本来就没有引用完整性可言。列靠与表相同的四元组定位。

**截断不算失败。** 超过 20 万行列信息就截断，但把这件事写进 `sync.err`——悄悄少收
一半，表现是"某些表没有列"，那看起来和"这张表真的没有列"一模一样。

## 定时任务的边界

这是网关里少数几个**主动去连生产库**的东西，所以每条边界都往"少做一点"定：

- **默认关**（`meta.sync.enabled`）。打开它意味着这台网关会周期性地登录你的每一台
  生产实例，那必须是一次明确的决定，不能因为升级了一个版本就自己开始跑。
- **启动时不跑**。进程重启很常见，每次重启都顺手扫一遍所有生产库，会让"重启网关"
  变成一个有副作用的动作。第一轮等到间隔到点。
- **间隔每轮重读**（`meta.sync.intervalHours`，默认 24）。按启动时那个值把 ticker
  钉死的话，改了设置要重启才生效。
- **限并发**（`meta.sync.concurrency`，默认 2，上限 8）。88 台同时探查是对自己生产
  集群的一次压力测试。
- **跳维护态**：`status=maint` 是人为标的"别碰"，定时任务不该是那个例外。
- **跳模拟连接**：没有凭据就没有远端，写一份空清单进去等于宣布这台库是空的。
- **一台失败不影响别台**：整轮中止的表现是"某天之后所有实例的元数据都停在同一时刻"，
  而原因藏在第一台上。

手动同步（`POST /connections/{id}/metadata/sync`）要 admin：定时的那条默认关着，
手动这一下同样是让网关去登录一台生产实例。

## 接口

| 方法 | 路径 | 闸 |
|---|---|---|
| GET | `/metadata/search?q=&limit=` | `[terminal]` + 标签授权（收在 SQL 里） |
| GET | `/connections/{id}/metadata?database=` | `[terminal]` + 标签授权 |
| POST | `/connections/{id}/metadata/sync` | `[db · admin]` + 标签授权 |

检索的范围**收在 SQL 里**而不是取回来再筛：后者会让分页的总数和实际行数对不上
（与 `approvalScope` 同一条理由）。表名和列名本身就是信息——"哪个库里有 id_card
这一列"是一个不该白送的答案。

## 回归测试

`gateway/metadata_test.go`（4 组，**跑在真实 SQLite 上**）：表/视图/内部表的区分、
列的类型/可空/默认值/主键/序号、库名口径与树一致、空库不是错误、**没有凭据时报错
而不是返回空清单**（空清单读起来是"这台库很干净"，那是这个功能最坏的一种谎）。

`bootstrap/metadata_sync_test.go`（5 组，真实 HTTP + 真实 SQLite 目标库）：同步后
读回、**先删后插**（远端删掉的表必须从缓存消失）、按列名检索、范围收口（够不到的人
既不能同步也看不到列名）、没同步过的实例 `sync` 为 null。

`bootstrap/metadata_sweep_test.go`（3 组）：默认关、打开后确实会同步、跳维护态。

## 待真实环境验收

- **MySQL / PostgreSQL / Oracle 的那三条 SQL 都没在真机上跑过**（本机只有 SQLite）。
  重点：Oracle 的 `DATA_DEFAULT`（LONG）退路、PG 的 `unnest(indkey) WITH ORDINALITY`
  主键判定、MySQL 的 `column_key='PRI'`。
- 一台几千张表的实例上，两条字典查询的实际耗时与 5 分钟上限是否够。
- 20 万行的列上限在你们最大的实例上是不是太小。

## 没有做

- **树和搜索还没改用这份缓存**。那是一次行为变更（快 vs 可能过期），要单独决定：
  缓存命中时怎么标注年龄、未同步的实例怎么退回实时探查。这次只把数据准备好。
- **列级的变更历史**（这次同步与上次的差异）。要留历史就不能"先删后插"，是另一种
  存储形态；而"看一眼现在长什么样"是这次要的东西。
- **前端界面**。接口是通的，页面留到确认这份数据在你们环境里靠谱之后再做。
